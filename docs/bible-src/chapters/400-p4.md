# Leçon 13 — La CI/CD « maison » d'AWS et le serverless

## Les AWS Developer Tools

| Service | Rôle | Équivalent |
|---|---|---|
| **CodeCommit** | dépôt Git hébergé | GitHub — *fermé aux nouveaux clients depuis juillet 2024* |
| **CodeConnections** (ex-CodeStar Connections) | relie AWS à GitHub, GitLab ou Bitbucket | — |
| **CodeBuild** | exécute des builds dans des conteneurs éphémères, décrits par un `buildspec.yml` | un runner GitHub Actions / un agent Jenkins |
| **CodeDeploy** | déploie sur EC2, sur des serveurs sur site, sur Lambda ou sur ECS (avec blue/green), décrit par un `appspec.yml` | un script de déploiement + des stratégies |
| **CodePipeline** | enchaîne les étapes Source → Build → Deploy (avec approbations) | le Jenkinsfile / le workflow |
| **CodeArtifact** | dépôt d'artefacts (Maven, npm, PyPI…) | JFrog, Nexus |
| **ECR** | registre d'images | Docker Hub |
| **Systems Manager Parameter Store** / **Secrets Manager** | stockage de paramètres et de secrets | Jenkins Credentials, Key Vault |

### Le `buildspec.yml` (CodeBuild)

```yaml
version: 0.2
env:
  parameter-store:                    # lit des valeurs dans SSM Parameter Store
    DOCKER_USER: /myapp/docker/username
    DOCKER_PASS: /myapp/docker/password
phases:
  install:
    runtime-versions: { nodejs: 20 }
  pre_build:
    commands:
      - echo "$DOCKER_PASS" | docker login -u "$DOCKER_USER" --password-stdin
  build:
    commands:
      - docker build -t monimage:$CODEBUILD_RESOLVED_SOURCE_VERSION .
  post_build:
    commands:
      - docker push monimage:$CODEBUILD_RESOLVED_SOURCE_VERSION
artifacts:                            # ce qui est transmis à l'étape suivante du pipeline
  files: ['appspec.yml', 'scripts/**/*']
```

### Le `appspec.yml` (CodeDeploy sur EC2)

```yaml
version: 0.0
os: linux
files:
  - source: /
    destination: /opt/monapp
hooks:                                # scripts exécutés à chaque phase du déploiement
  ApplicationStop:  [{ location: scripts/stop.sh,  timeout: 300, runas: root }]
  AfterInstall:     [{ location: scripts/start.sh, timeout: 300, runas: root }]
  ValidateService:  [{ location: scripts/check.sh, timeout: 120, runas: root }]
```

L'**agent CodeDeploy** installé sur chaque instance récupère le paquet de déploiement et exécute les *hooks* dans l'ordre : `ApplicationStop` → `DownloadBundle` → `BeforeInstall` → `Install` → `AfterInstall` → `ApplicationStart` → `ValidateService`.

## Le serverless

**Serverless** ne veut pas dire « sans serveur », mais « **sans serveur à gérer** » : tu fournis du code ou une configuration, le fournisseur gère entièrement l'exécution, la mise à l'échelle (y compris jusqu'à zéro) et la disponibilité. Tu paies **à l'usage réel** (à la requête, à la milliseconde), pas à l'heure.

| Brique | Service AWS | Remarque |
|---|---|---|
| Calcul | **Lambda** | une fonction exécutée à chaque événement ; 15 minutes maximum par exécution |
| API HTTP | **API Gateway** (REST ou HTTP API) | reçoit les requêtes et déclenche les Lambda |
| Base relationnelle | **Aurora Serverless v2** | s'adapte à la charge (en ACU) ; la v2 peut descendre à 0 ACU selon les versions |
| Base NoSQL | **DynamoDB** | entièrement serverless, paiement à la requête |
| Stockage | **S3** | |
| Files / événements | **SQS**, **SNS**, **EventBridge** | |
| Conteneurs | **Fargate**, **App Runner** | (projet 04) |

:::why Les avantages et les pièges
**Avantages** : aucun serveur à patcher, mise à l'échelle automatique, coût nul quand rien ne se passe, haute disponibilité intégrée.

**Pièges** : *cold start* (la première invocation après une période d'inactivité est plus lente), limites (durée, taille du paquet), débogage moins direct, coûts qui peuvent dépasser des serveurs classiques à très fort trafic constant, et dépendance forte au fournisseur (*vendor lock-in*).
:::

## GitLab CI en bref

GitLab intègre la CI/CD dans le même produit que le dépôt. Le pipeline se décrit dans **`.gitlab-ci.yml`** à la racine :

```yaml
stages: [build, test, deploy]          # ordre des étapes

variables:
  APP_ENV: staging

build-job:
  stage: build
  image: node:20                       # chaque job tourne dans un conteneur
  script:
    - npm ci
    - npm run build
  artifacts:
    paths: [dist/]                     # transmis aux jobs suivants

test-job:
  stage: test
  image: node:20
  script: [npm test]

deploy-job:
  stage: deploy
  script: [./deploy.sh]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"  # seulement sur main
  when: manual                         # bouton manuel
  environment: production
```

Les jobs d'un même *stage* tournent en parallèle ; les *stages* s'enchaînent. Les **variables CI/CD** (secrets) se définissent dans *Settings → CI/CD → Variables* (cocher *Masked* et *Protected*). Les **runners** exécutent les jobs : partagés (fournis par GitLab.com, avec un quota de minutes gratuites) ou auto-hébergés.
