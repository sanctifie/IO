## Ce qu'on construit

```ascii
           Terraform crée ──► VPC + SG + 3 instances
                                 │
       ┌─────────────────────────┼──────────────────────────────┐
       │ Ansible controller  ──SSH (playbooks)──► Jenkins master + Jenkins agent
       └────────────────────────────────────────────────────────┘

  git push ──webhook──► JENKINS MASTER (Multibranch Pipeline : une branche = un pipeline)
                              │ délègue au
                              ▼
                        JENKINS AGENT (label "maven" : JDK, Maven, Docker, kubectl, helm)
                         1. mvn deploy        → jar
                         2. tests unitaires   → rapports surefire / jacoco
                         3. analyse           → SonarCloud ──► Quality Gate OK ?
                         4. publication jar   → JFrog (dépôt Maven)
                         5. docker build/push → JFrog (registre Docker)
                         6. helm install      → EKS (namespace sample-app)
                                                   │ pull de l'image avec un imagePullSecret
                                                   ▼
                                             Pods sample-app ◄── Prometheus ◄── Grafana
```

L'application est une petite API Spring Boot (`demo-workshop`) qui expose des informations sur des dépôts GitHub.

## Partie A — Infrastructure, configuration et CI

### Étape 1 — Provisionner l'infrastructure avec Terraform

Crée `projects/06-advanced-cicd/terraform/` dans ton dépôt IO, avec ce `main.tf` :

```hcl
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = "eu-west-3"
  default_tags { tags = { Project = "io-06" } }
}

variable "my_ip"    { description = "Ton IP publique en /32, ex: 82.64.10.5/32" }
variable "key_name" { default = "io-key" }

# --- Réseau : un VPC, un subnet public, une sortie Internet ---
resource "aws_vpc" "main" {
  cidr_block           = "10.6.0.0/16"
  enable_dns_hostnames = true
  tags = { Name = "io-06-vpc" }
}

resource "aws_internet_gateway" "igw" { vpc_id = aws_vpc.main.id }

resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.6.1.0/24"
  map_public_ip_on_launch = true
  availability_zone       = "eu-west-3a"
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.igw.id
  }
}

resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}

# --- Pare-feu : SSH et Jenkins depuis ton IP, tout le trafic interne au VPC ---
resource "aws_security_group" "devops" {
  name   = "io-06-sg"
  vpc_id = aws_vpc.main.id

  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [var.my_ip]
  }
  ingress {
    from_port   = 8080
    to_port     = 8080
    protocol    = "tcp"
    cidr_blocks = [var.my_ip]          # ajoute les IP des webhooks GitHub si besoin (voir projet 05)
  }
  ingress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = [aws_vpc.main.cidr_block]
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

# --- Image Ubuntu 24.04 la plus récente ---
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]   # Canonical
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }
}

# --- Les 3 machines ---
locals {
  servers = {
    ansible        = "t3.micro"
    jenkins-master = "t3.small"
    jenkins-agent  = "t3.medium"   # Maven + Docker ont besoin de mémoire
  }
}

resource "aws_instance" "server" {
  for_each               = local.servers
  ami                    = data.aws_ami.ubuntu.id
  instance_type          = each.value
  key_name               = var.key_name
  subnet_id              = aws_subnet.public.id
  vpc_security_group_ids = [aws_security_group.devops.id]
  root_block_device { volume_size = 20 }
  tags = { Name = "io-06-${each.key}" }
}

output "public_ips"  { value = { for k, s in aws_instance.server : k => s.public_ip } }
output "private_ips" { value = { for k, s in aws_instance.server : k => s.private_ip } }
```

```bash
cd projects/06-advanced-cicd/terraform
terraform init                                         # télécharge le provider AWS
terraform plan  -var="my_ip=$(curl -s ifconfig.me)/32" # montre ce qui va être créé
terraform apply -var="my_ip=$(curl -s ifconfig.me)/32" # crée (tape "yes")
terraform output
```

:::why Ce que tu viens de faire
En 100 lignes de texte, tu as décrit un réseau, un pare-feu et trois serveurs. Le fichier est versionné, relisible, et `terraform destroy` supprime **tout** proprement. Compare avec le projet 02, où tu as tout créé à la main. La leçon 10 t'expliquera chaque bloc. Retiens déjà : `resource` = quelque chose à créer, `data` = quelque chose à lire, `variable` = un paramètre, `output` = une valeur à afficher, `for_each` = créer plusieurs ressources à partir d'une liste.
:::

### Étape 2 — SSH sans mot de passe entre Ansible et les nœuds

Le nœud Ansible doit pouvoir se connecter aux deux serveurs Jenkins. On copie **temporairement** ta clé sur le contrôleur Ansible (c'est le seul cas acceptable dans ce projet d'apprentissage ; en entreprise on utilise une clé dédiée ou SSM) :

```bash
scp -i ~/.ssh/io-key.pem ~/.ssh/io-key.pem ubuntu@<IP_PUB_ANSIBLE>:~/.ssh/io-key.pem
ssh -i ~/.ssh/io-key.pem ubuntu@<IP_PUB_ANSIBLE>
chmod 400 ~/.ssh/io-key.pem
sudo apt update && sudo apt install -y ansible
ansible --version
```

*(Variante de l'énoncé : générer une clé avec `ssh-keygen` sur le contrôleur et la copier sur chaque nœud avec `ssh-copy-id`. Sur EC2, l'authentification par mot de passe est désactivée, donc `ssh-copy-id` ne marche pas directement : il faudrait ajouter la clé publique à la main dans `~/.ssh/authorized_keys` de chaque nœud.)*

Crée l'inventaire `~/ansible/hosts.ini` avec les **IP privées** :

```ini
[jenkins_master]
master ansible_host=10.6.1.X

[jenkins_agent]
agent ansible_host=10.6.1.Y

[all:vars]
ansible_user=ubuntu
ansible_ssh_private_key_file=~/.ssh/io-key.pem
ansible_ssh_common_args='-o StrictHostKeyChecking=accept-new'
```

```bash
cd ~/ansible
ansible all -i hosts.ini -m ping
# master | SUCCESS => {"ping": "pong"}
# agent  | SUCCESS => {"ping": "pong"}
```

### Étape 3 — Configurer Jenkins master et agent avec Ansible

`jenkins-master.yml` :

```yaml
- name: Installer le contrôleur Jenkins
  hosts: jenkins_master
  become: true
  tasks:
    - name: Java 21
      ansible.builtin.apt:
        name: [fontconfig, openjdk-21-jre]
        update_cache: true

    - name: Clé du dépôt Jenkins
      ansible.builtin.get_url:
        url: https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key
        dest: /etc/apt/keyrings/jenkins-keyring.asc

    - name: Dépôt Jenkins
      ansible.builtin.apt_repository:
        repo: "deb [signed-by=/etc/apt/keyrings/jenkins-keyring.asc] https://pkg.jenkins.io/debian-stable binary/"
        filename: jenkins

    - name: Installer Jenkins
      ansible.builtin.apt:
        name: jenkins
        update_cache: true

    - name: Démarrer Jenkins
      ansible.builtin.systemd:
        name: jenkins
        state: started
        enabled: true
```

`jenkins-agent.yml` — l'agent est le serveur de **build** : il lui faut Java, Maven, Git et Docker.

```yaml
- name: Préparer l'agent Jenkins (serveur de build Maven + Docker)
  hosts: jenkins_agent
  become: true
  tasks:
    - name: Paquets de build
      ansible.builtin.apt:
        name: [openjdk-21-jdk, maven, git, docker.io, unzip]
        update_cache: true

    - name: Docker démarré
      ansible.builtin.systemd:
        name: docker
        state: started
        enabled: true

    - name: ubuntu peut utiliser docker (les builds Jenkins tourneront sous ubuntu)
      ansible.builtin.user:
        name: ubuntu
        groups: docker
        append: true

    - name: Dossier de travail de l'agent
      ansible.builtin.file:
        path: /home/ubuntu/jenkins
        state: directory
        owner: ubuntu
        group: ubuntu
```

```bash
ansible-playbook -i hosts.ini jenkins-master.yml
ansible-playbook -i hosts.ini jenkins-agent.yml
ansible-playbook -i hosts.ini jenkins-agent.yml    # relance : tout est "ok", rien "changed" → idempotent
```

:::info Maven d'Ubuntu ou Maven récent ?
Le paquet `maven` d'Ubuntu 24.04 fournit Maven 3.8.x, suffisant ici. Le Jenkinsfile d'origine utilise `/opt/apache-maven-3.9.4` : si tu veux exactement cette version, ajoute au playbook une tâche `get_url` + `unarchive` qui télécharge et décompresse l'archive dans `/opt`.
:::

### Étape 4 — Relier l'agent au contrôleur

1. Ouvre `http://<IP_PUB_MASTER>:8080`, débloque Jenkins (`sudo cat /var/lib/jenkins/secrets/initialAdminPassword`), installe les plugins suggérés, crée ton admin.
2. *Manage Jenkins → Nodes → Built-In Node → Configure* : **Number of executors = 0** (aucun build sur le contrôleur).
3. *Manage Jenkins → Credentials → Add* : *SSH Username with private key*, ID **`agent-ssh`**, user `ubuntu`, clé privée = contenu de `io-key.pem`.
4. *Nodes → New Node* : nom `maven-agent`, *Permanent Agent* →
   - *Number of executors* : 2 ; *Remote root directory* : `/home/ubuntu/jenkins` ;
   - *Labels* : **`maven`** (c'est ce que demande `agent { node { label 'maven' } }` dans le Jenkinsfile) ;
   - *Launch method* : **Launch agents via SSH** ; *Host* : IP **privée** de l'agent ; *Credentials* : `agent-ssh` ; *Host Key Verification Strategy* : *Non verifying* (acceptable pour l'exercice).
5. *Save* → l'agent passe en ligne en quelques secondes (voir son log).

:::why Le contrôleur copie lui-même l'agent
Avec « Launch agents via SSH », le contrôleur se connecte à la machine, y dépose `agent.jar` et le lance. Il n'y a donc **rien** à installer côté agent à part Java : c'est pour cela que le playbook de l'énoncé, qui crée un service `jenkins-agent` à la main, n'est pas nécessaire avec cette méthode.
:::

### Étape 5 — Credentials GitHub et Multibranch Pipeline

1. Fork (ou copie) l'application `DevOps-Project-06` dans un dépôt GitHub à toi : `demo-workshop`.
2. Crée un **fine-grained token** GitHub (lecture du contenu de ce dépôt, lecture des webhooks).
3. Jenkins → *Credentials → Add* → *Username with password* : user = ton pseudo GitHub, password = le token, ID **`github-cred`**.
4. *New Item* → nom `demo-workshop` → **Multibranch Pipeline** → *Branch Sources → Add source → GitHub* → credentials `github-cred` → URL du dépôt → *Save*.

Jenkins **scanne** le dépôt : il crée un sous-job pour **chaque branche** qui contient un `Jenkinsfile`, et en crée automatiquement de nouveaux quand tu crées une branche.

### Étape 6 — Déclencher le scan par webhook

Installe le plugin **Multibranch Scan Webhook Trigger**. Dans la configuration du job multibranch → *Scan Multibranch Pipeline Triggers* → coche **Scan by webhook** → *Trigger token* : `demo-workshop-token`.

GitHub → dépôt → *Settings → Webhooks → Add* : URL `http://<IP_PUB_MASTER>:8080/multibranch-webhook-trigger/invoke?token=demo-workshop-token`, type JSON, événements *push*.

### Étape 7 — SonarCloud et tests

1. SonarCloud : crée l'organisation et le projet (comme au projet 01), génère un token.
2. Jenkins → *Credentials* → *Secret text*, ID **`sonar-token`**.
3. Plugin **SonarQube Scanner** → *Manage Jenkins → System → SonarQube servers* : nom **`sonar-server`**, URL `https://sonarcloud.io`, token `sonar-token`.
4. *Manage Jenkins → Tools → SonarQube Scanner installations* : nom **`sonar-scanner`**, *Install automatically*.
5. À la racine du dépôt, `sonar-project.properties` :


6. Dans SonarCloud : *Administration → Webhooks* → URL `http://<IP_PUB_MASTER>:8080/sonarqube-webhook/` (permet à Jenkins de connaître le résultat de la Quality Gate sans attendre indéfiniment).

### Étape 8 — Publier le jar dans JFrog

1. JFrog : crée un dépôt local Maven **`maven-libs-release-local`** et un dépôt local **Docker** **`docker-local`**. Génère un *access token*.
2. Jenkins → *Credentials* → *Username with password*, ID **`jfrog-cred`** (ton user JFrog + token).
3. Installe le plugin **Artifactory** (JFrog). *(Il est utilisé par l'étape « Jar Publish » du Jenkinsfile d'origine via `Artifactory.newServer`.)*

:::info Pourquoi le jar est dans `jarstaging/`
Le `pom.xml` contient `<distributionManagement>` vers `file://jarstaging` : `mvn deploy` ne publie pas sur Internet, il « déploie » le jar dans un dossier local `jarstaging/` du workspace. C'est ensuite l'étape *Jar Publish* qui envoie ce dossier vers JFrog avec le plugin Artifactory, en y ajoutant des métadonnées (numéro de build, commit). Deux étapes, deux responsabilités.
:::

### Étape 9 — Image Docker et Jenkinsfile complet

Le `Dockerfile` d'origine utilise `openjdk:8`, une image **dépréciée et retirée**. Remplace-le :

```dockerfile
FROM eclipse-temurin:8-jre
WORKDIR /app
COPY jarstaging/com/satish/demo-workshop/2.1.2/demo-workshop-2.1.2.jar app.jar
EXPOSE 8000
ENTRYPOINT ["java", "-jar", "app.jar"]
```

Installe le plugin **Docker Pipeline**. Voici le Jenkinsfile complet, adapté et commenté :

```groovy
def registry  = 'https://<ton-nom>.jfrog.io'
def imageName = '<ton-nom>.jfrog.io/docker-local/sample_app'
def version   = '2.1.2'

pipeline {
    agent { node { label 'maven' } }

    stages {
        stage('Build') {
            steps {
                sh 'mvn -B clean deploy -Dmaven.test.skip=true'   // compile + "déploie" dans jarstaging/
            }
        }
        stage('Tests unitaires') {
            steps {
                sh 'mvn -B surefire-report:report'                // lance les tests et produit le rapport
            }
        }
        stage('Analyse SonarCloud') {
            environment { scannerHome = tool 'sonar-scanner' }
            steps {
                withSonarQubeEnv('sonar-server') {
                    sh "${scannerHome}/bin/sonar-scanner"
                }
            }
        }
        stage('Quality Gate') {
            steps {
                timeout(time: 10, unit: 'MINUTES') {
                    waitForQualityGate abortPipeline: true       // stoppe le pipeline si la porte est rouge
                }
            }
        }
        stage('Publication du jar') {
            steps {
                script {
                    def server = Artifactory.newServer url: registry + '/artifactory', credentialsId: 'jfrog-cred'
                    def uploadSpec = """{
                      "files": [{
                        "pattern": "jarstaging/(*)",
                        "target": "maven-libs-release-local/{1}",
                        "flat": "false",
                        "props": "buildid=${env.BUILD_ID};commitid=${env.GIT_COMMIT}",
                        "exclusions": ["*.sha1", "*.md5"]
                      }]
                    }"""
                    def buildInfo = server.upload(uploadSpec)
                    buildInfo.env.collect()
                    server.publishBuildInfo(buildInfo)
                }
            }
        }
        stage('Build image Docker') {
            steps {
                script { app = docker.build("${imageName}:${version}") }
            }
        }
        stage('Push image Docker') {
            steps {
                script {
                    docker.withRegistry(registry, 'jfrog-cred') { app.push() }
                }
            }
        }
        // Partie B : décommenter après l'étape 11
        // stage('Déploiement Helm') {
        //     steps { sh 'helm upgrade --install sample-app ./sample-app -n sample-app --create-namespace' }
        // }
    }
}
```

:::check Fin de la partie A
- Un `git push` sur `main` déclenche le scan puis le pipeline de la branche `main`.
- SonarCloud affiche l'analyse, avec la couverture de tests (Jacoco).
- JFrog contient le jar (avec les propriétés `buildid`/`commitid`) et l'image `sample_app:2.1.2`.
- Crée une branche `feature/test`, pousse-la : un nouveau sous-job apparaît automatiquement.
:::

## Partie B — Kubernetes et monitoring

### Étape 10 — Le cluster EKS

Le plus simple et le plus fiable est **eksctl** (voir annexe A.8). Depuis ton poste ou l'agent :

```bash
eksctl create cluster --name io-06 --region eu-west-3 \
  --nodegroup-name workers --node-type t3.medium --nodes 2 --managed
```

*(L'énoncé crée l'EKS avec Terraform : c'est exactement ce que fait le projet 19, en détail. Tu peux revenir ici ensuite et remplacer eksctl par Terraform.)*

Sur l'agent Jenkins, installe **kubectl**, **AWS CLI v2** et **Helm** (commandes de la partie 0, étape 5), puis donne-lui accès au cluster. Le plus propre : un **rôle IAM** attaché à l'instance agent, autorisé dans le cluster par une *access entry* :

```bash
# Depuis ton poste (admin du cluster)
aws eks create-access-entry --cluster-name io-06 --principal-arn arn:aws:iam::<compte>:role/<role-agent>
aws eks associate-access-policy --cluster-name io-06 --principal-arn arn:aws:iam::<compte>:role/<role-agent> \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy --access-scope type=cluster

# Sur l'agent (en tant qu'ubuntu)
aws eks update-kubeconfig --region eu-west-3 --name io-06
kubectl get nodes
```

### Étape 11 — Déployer l'image depuis JFrog

Kubernetes doit s'authentifier auprès du registre privé JFrog pour télécharger l'image. On crée un **secret de type docker-registry** et on le référence dans le Deployment (`imagePullSecrets`).

Extrais le chart fourni et adapte-le :

```bash
tar xzf sample-app-1.0.1.tgz        # crée le dossier sample-app/ (chart Helm)
```

Dans `sample-app/templates/deployment.yaml`, mets **ton** image (`<ton-nom>.jfrog.io/docker-local/sample_app:2.1.2`) et vérifie `imagePullSecrets: [{ name: dockercred }]`.

:::danger Des secrets en clair dans le chart d'origine
Le `deployment.yaml` d'origine contient des clés d'API Twitter **en clair** (`CONSUMER_SECRET`, `ACCESS_TOKEN_SECRET`…), et `secret.yaml` contient des identifiants de registre encodés en base64 (ce n'est **pas** du chiffrement : `echo <valeur> | base64 -d` les révèle). **Supprime-les** du chart. Crée le secret du registre en ligne de commande, hors Git :

```bash
kubectl create namespace sample-app
kubectl create secret docker-registry dockercred -n sample-app \
  --docker-server=<ton-nom>.jfrog.io \
  --docker-username=<user-jfrog> \
  --docker-password=<token-jfrog>
```
et retire `templates/secret.yaml` du chart. En production, on utilise un outil comme **External Secrets Operator** (qui lit AWS Secrets Manager) ou **Sealed Secrets**.
:::

Décommente l'étape *Déploiement Helm* du Jenkinsfile, pousse. Vérifie :

```bash
kubectl get pods,svc -n sample-app
kubectl port-forward -n sample-app svc/sample-app-service 8000:8000
curl http://localhost:8000/        # depuis la machine où tourne port-forward
```

Le service est de type `NodePort` (port 30082 sur chaque nœud). Pour l'exposer à Internet, change-le en `LoadBalancer` (AWS crée un load balancer, payant) ou utilise un Ingress (projet 15).

### Étape 12 — Prometheus et Grafana

On installe la pile **kube-prometheus-stack** (Prometheus, Alertmanager, Grafana, exporters, tableaux de bord prêts à l'emploi) avec Helm. Détails en annexe A.10.

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm install monitoring prometheus-community/kube-prometheus-stack -n monitoring --create-namespace
kubectl get pods -n monitoring

# Accès à Grafana sans load balancer (gratuit) :
kubectl port-forward -n monitoring svc/monitoring-grafana 3000:80
# mot de passe admin :
kubectl get secret -n monitoring monitoring-grafana -o jsonpath="{.data.admin-password}" | base64 -d; echo
```

Ouvre `http://localhost:3000` (utilisateur `admin`) → *Dashboards* → *Kubernetes / Compute Resources / Cluster* : CPU et mémoire du cluster, par namespace, par pod.

*(L'énoncé passe les services Prometheus et Grafana en `LoadBalancer` pour y accéder depuis le navigateur. Ça marche, mais chaque service crée un load balancer payant et expose l'outil sur Internet. Le `port-forward` est gratuit et privé.)*

## Dépannage

:::fix
- **L'agent reste hors ligne** : regarde son log dans Jenkins. `Connection refused/timed out` → IP privée erronée ou SG. `java: not found` → Java absent sur l'agent (playbook non exécuté).
- **`waitForQualityGate` attend jusqu'au timeout** : le webhook SonarCloud → Jenkins n'est pas configuré, ou Jenkins n'est pas joignable depuis Internet.
- **`docker: permission denied` dans le pipeline** : l'utilisateur ubuntu a été ajouté au groupe docker **après** le démarrage de l'agent. Déconnecte puis reconnecte l'agent dans Jenkins (*Disconnect* / *Launch agent*).
- **Pod en `ImagePullBackOff`** : `kubectl describe pod …` → `401 Unauthorized` (secret `dockercred` faux ou dans un autre namespace) ou `not found` (nom d'image ou tag faux).
- **`helm install` : « cannot re-use a name that is still in use »** : utilise `helm upgrade --install`, rejouable à l'infini.
- **`error: You must be logged in to the server (Unauthorized)`** avec kubectl : l'identité IAM utilisée n'a pas d'access entry dans le cluster.
:::

## Nettoyage

:::clean
