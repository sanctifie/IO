## Ce qu'on construit

Ton premier déploiement de **conteneur** dans le cloud : une petite application web Python (Django) est empaquetée en image Docker, stockée dans **ECR** (le registre d'images d'AWS), puis exécutée par **ECS** (le service d'orchestration de conteneurs d'AWS).

```ascii
 Ton poste                          AWS
 ┌──────────────┐  docker push   ┌──────────────────┐
 │ Dockerfile   │ ─────────────► │  ECR             │  registre privé d'images
 │ docker build │                │  django-app:v1   │
 └──────────────┘                └────────┬─────────┘
                                          │ pull
                                 ┌────────▼─────────────────────────────┐
                                 │  ECS cluster                         │
                                 │  Service "django" (1 à N tâches)     │
                                 │   └─ Tâche = conteneur django:8000   │ ◄── http://<IP>:8000/hello/
                                 │  (Fargate : pas de serveur à gérer)  │
                                 └──────────────────────────────────────┘
                                          │ logs
                                          ▼  CloudWatch Logs
```

## Les concepts

| Notion ECS | Ce que c'est | Équivalent Kubernetes (pour plus tard) |
|---|---|---|
| **Cluster** | un regroupement logique où tournent les tâches | cluster |
| **Task definition** | la « fiche » qui décrit un ou plusieurs conteneurs : image, CPU, mémoire, ports, variables, logs | spécification de Pod |
| **Task** (tâche) | une instance en cours d'exécution d'une task definition | Pod |
| **Service** | maintient N tâches en vie, les remplace si elles plantent, les relie à un load balancer | Deployment + Service |
| **Launch type** | où tournent les tâches : **Fargate** (serverless, AWS gère les machines) ou **EC2** (tes propres instances dans le cluster) | nœuds |

:::why Fargate ou EC2 ?
Le dépôt d'origine utilise des instances EC2 dans le cluster. Avec **Fargate**, tu n'as **aucun serveur** à créer, mettre à jour ou dimensionner : tu dis « 0,25 vCPU et 512 Mo » et AWS s'occupe du reste. C'est le choix le plus simple pour commencer et la tendance actuelle. Le mode EC2 reste utile pour maîtriser finement les coûts à grande échelle ou utiliser du matériel spécifique (GPU). On fait Fargate, et on te montre la variante EC2 en bonus.
:::

## Étape 2 — Moderniser le Dockerfile

Le Dockerfile d'origine utilise `python:3.9` (fin de vie) et une liste de dépendances sans versions. Voici une version propre :

```text
# requirements.txt — figer les versions rend le build reproductible
Django==5.2.*
gunicorn==23.*
```

```dockerfile
FROM python:3.12-slim

# Pas de fichiers .pyc, logs affichés immédiatement (utile pour CloudWatch)
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1

WORKDIR /usr/src/app

COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd -m django && chown -R django /usr/src/app
USER django

EXPOSE 8000

# gunicorn : un vrai serveur d'applications, contrairement à "runserver" (réservé au développement)
CMD ["gunicorn", "hello_world_django_app.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "2"]
```

Et un `.dockerignore` :

```text
__pycache__/
*.pyc
.git
db.sqlite3
```

:::why Pourquoi `0.0.0.0` et pas `127.0.0.1` ?
`127.0.0.1` (*localhost*) n'accepte que les connexions venant **de l'intérieur du conteneur**. `0.0.0.0` signifie « écouter sur toutes les interfaces réseau », ce qui permet aux connexions extérieures (redirigées par Docker ou par AWS) d'arriver. Une application qui écoute sur `127.0.0.1` dans un conteneur est injoignable : erreur classique.
:::

:::warn Le `SECRET_KEY` et `ALLOWED_HOSTS = ["*"]`
`settings.py` contient une clé secrète en clair et accepte n'importe quel nom d'hôte. Acceptable pour un « Hello World », **pas** en production : la clé doit venir d'une variable d'environnement (`os.environ["DJANGO_SECRET_KEY"]`), alimentée par Secrets Manager, et `ALLOWED_HOSTS` doit lister les vrais domaines.
:::

## Étape 3 — Construire et tester en local

```bash
docker build -t hello-world-django-app:v1 .
docker images | grep hello-world-django-app
docker run -d --name django -p 8000:8000 hello-world-django-app:v1
curl http://localhost:8000/hello/
# <html><body>Hello World</body></html>
docker logs django
docker rm -f django
```

:::tip Toujours tester en local d'abord
Si ça ne marche pas sur ton poste, ça ne marchera pas dans le cloud, et les erreurs y sont plus longues à diagnostiquer. Cette règle vaut pour tout le parcours.
:::

:::warn Mac avec puce Apple (M1/M2/M3…)
Ton Mac construit des images **ARM**. Fargate tourne par défaut en **x86_64**. Une image ARM lancée sur x86 plante avec `exec format error`. Construis pour la bonne architecture : `docker build --platform linux/amd64 -t …`. (Autre option : choisir l'architecture ARM64 dans la task definition, moins chère.)
:::

## Étape 4 — Créer le dépôt ECR et y pousser l'image

```bash
export AWS_REGION=eu-west-3
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export REPO=hello-world-django-app
export REGISTRY=$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com

# 1. Créer le dépôt (avec scan de vulnérabilités à chaque push)
aws ecr create-repository --repository-name $REPO \
  --image-scanning-configuration scanOnPush=true --region $AWS_REGION

# 2. Authentifier Docker auprès d'ECR (jeton valable 12 heures)
aws ecr get-login-password --region $AWS_REGION | docker login --username AWS --password-stdin $REGISTRY

# 3. Donner à l'image son nom complet ECR, puis la pousser
docker tag hello-world-django-app:v1 $REGISTRY/$REPO:v1
docker push $REGISTRY/$REPO:v1
```

:::why Ce qui se passe à l'étape 2
ECR n'a pas de mot de passe fixe. `aws ecr get-login-password` utilise **tes identifiants AWS** (profil configuré en partie 0) pour obtenir un jeton temporaire, qui est passé à `docker login` via l'entrée standard (`--password-stdin`, pour qu'il n'apparaisse ni à l'écran ni dans l'historique). Le dépôt d'origine te faisait exporter tes clés d'accès en variables : avec un profil SSO ou `aws configure`, c'est inutile.
:::

Dans la console : **ECR → Repositories → hello-world-django-app** → l'image `v1` apparaît, avec le résultat du scan de vulnérabilités.

## Étape 5 — Créer le cluster ECS

Console → **Elastic Container Service → Clusters → Create cluster** :
- Nom : `io-django-cluster`.
- *Infrastructure* : **AWS Fargate (serverless)** uniquement.
- *Monitoring* : tu peux activer *Container Insights* (payant au-delà d'un certain volume ; laisse désactivé pour l'exercice).

## Étape 6 — Créer la task definition

**ECS → Task definitions → Create new task definition** :

| Champ | Valeur |
|---|---|
| Family | `django-task` |
| Launch type | AWS Fargate |
| OS / Architecture | Linux / X86_64 |
| CPU / Memory | 0.25 vCPU / 0.5 GB |
| Task execution role | *Create new role* (ou `ecsTaskExecutionRole`) |
| Container – name | `django` |
| Container – image URI | `<ACCOUNT_ID>.dkr.ecr.eu-west-3.amazonaws.com/hello-world-django-app:v1` |
| Port mappings | 8000 / TCP |
| Log collection | *Use log collection* → CloudWatch (coché par défaut) |

:::why Le « task execution role »
C'est le rôle IAM qu'**ECS lui-même** utilise pour **démarrer** ta tâche : télécharger l'image depuis ECR et écrire les logs dans CloudWatch. À ne pas confondre avec le **task role**, qui donne des droits **à ton application** (par exemple lire un bucket S3). Deux rôles, deux usages : encore le moindre privilège.
:::

## Étape 7 — Créer le service

Dans le cluster → onglet *Services* → **Create** :

- *Compute options* : Launch type **FARGATE**.
- *Application type* : **Service** ; *Task definition* : `django-task` (dernière révision) ; nom `django-service` ; *Desired tasks* : **1**.
- *Networking* : VPC par défaut, ses subnets publics, **Public IP : activé**.
- *Security group* : crée `django-sg` avec une règle entrante **TCP 8000 depuis My IP** (ou `0.0.0.0/0` pour un test rapide).
- *Load balancing* : aucun pour l'instant.

Après une à deux minutes, la tâche passe à l'état **RUNNING**. Clique sur la tâche → onglet *Networking* → **Public IP**.

:::check
```bash
curl http://<IP_PUBLIQUE_DE_LA_TACHE>:8000/hello/
```
Tu dois voir « Hello World ». Dans l'onglet *Logs* de la tâche (ou CloudWatch → log group `/ecs/django-task`), tu vois les lignes de gunicorn.
:::

## Étape 8 — Mettre à jour l'application (le vrai cycle de vie)

Modifie `views.py` (par exemple « Hello World v2 »), puis :

```bash
docker build -t $REGISTRY/$REPO:v2 .
docker push $REGISTRY/$REPO:v2
```

Crée une **nouvelle révision** de la task definition avec l'image `:v2` (*Create new revision*), puis mets à jour le service (*Update service* → révision la plus récente → *Force new deployment*). ECS démarre la nouvelle tâche, attend qu'elle soit saine, puis arrête l'ancienne : c'est un **rolling update**.

:::tip Le faire en CLI
```bash
aws ecs update-service --cluster io-django-cluster --service django-service \
  --task-definition django-task --force-new-deployment
```
C'est exactement la commande qu'un pipeline CI/CD exécutera (projet 23).
:::

## Étape 9 (recommandée) — Un load balancer devant le service

L'IP publique d'une tâche **change à chaque redéploiement**. En vrai, on place un **ALB** devant :

1. Crée un SG `django-alb-sg` (HTTP 80 depuis `0.0.0.0/0`) et modifie `django-sg` : 8000 **depuis `django-alb-sg`** uniquement.
2. Recrée (ou mets à jour) le service avec *Load balancing* → **Application Load Balancer** → *Create a new load balancer* `django-alb`, listener HTTP 80, target group `django-tg` (type **IP**, port 8000), *health check path* **`/hello/`**.
3. Passe le nombre de tâches à 2 : l'ALB répartit la charge.

:::warn Le health check sur `/`
Si tu laisses le chemin de health check par défaut (`/`), l'ALB reçoit une 404, juge les tâches malades, et ECS les redémarre en boucle. Le health check doit viser une URL qui répond 200 : ici `/hello/`. En entreprise, chaque application expose une route dédiée (`/health`, `/healthz`, `/actuator/health`).
:::

## Variante — le mode EC2 (comme dans le dépôt d'origine)

Lors de la création du cluster, choisis *Amazon EC2 instances* : AWS crée un Auto Scaling Group d'instances avec l'AMI optimisée ECS (type `t3.micro`, 1 instance). Dans la task definition, choisis *Launch type* **EC2**, mode réseau *bridge* et un *host port* (par exemple 8000 → 8000). La tâche est placée sur l'instance, joignable via l'IP publique **de l'instance**. Tu vois ainsi ce que Fargate te cache : des serveurs à gérer, mettre à jour et dimensionner.

## Dépannage

:::fix
- **La tâche passe de PENDING à STOPPED** : clique sur la tâche arrêtée → *Stopped reason*. Causes classiques :
  - `CannotPullContainerError` : URI d'image erronée, tag inexistant, ou pas d'accès Internet/ECR (tâche dans un subnet privé sans NAT, ou *Public IP* désactivée en subnet public).
  - `exec format error` dans les logs : image ARM sur x86 (voir l'encadré Mac).
  - `Essential container in task exited` : l'application plante au démarrage → lis les logs CloudWatch.
- **`curl` ne répond pas** : le SG n'autorise pas le port 8000 depuis ton IP, ou tu as oublié `/hello/`.
- **`no basic auth credentials` au `docker push`** : le `docker login` a expiré (12 h) ou visait une autre région.
- **`Bad Request (400)`** de Django : `ALLOWED_HOSTS` ne contient pas le nom utilisé.
:::

## Nettoyage

:::clean
1. Service : passe *Desired tasks* à 0, puis **Delete service**.
2. Si créés : ALB `django-alb` et target group `django-tg`.
3. **Delete cluster** `io-django-cluster` (en mode EC2, cela supprime aussi l'ASG et l'instance ; vérifie dans CloudFormation qu'aucune pile ne reste).
4. ECR : `aws ecr delete-repository --repository-name hello-world-django-app --force`.
5. Task definitions : *Deregister* puis *Delete* les révisions (gratuit, mais c'est plus propre).
6. Log group `/ecs/django-task` dans CloudWatch, et les Security Groups créés.
:::
