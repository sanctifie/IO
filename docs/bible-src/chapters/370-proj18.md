# Projet 18 — Pipeline Jenkins GitOps pour une application Java : Maven, SonarQube, Docker, Argo CD

:::card
| | |
|---|---|
| Niveau | ★★★☆☆ Intermédiaire |

| Dépôt d'origine | `DevOps-Project-18` (`spring-boot-app/` avec `JenkinsFile` et `Dockerfile`, `spring-boot-app-manifests/`) — inspiré de *Jenkins-Zero-To-Hero* d'Abhishek Veeramalla |

## Ce qu'on construit

```ascii
 git push ──► Jenkins (EC2)
               agent = conteneur Docker "maven + docker CLI" (socket Docker de l'hôte monté)
               1. mvn clean package
               2. mvn sonar:sonar ──► SonarQube (conteneur sur la même EC2)
               3. docker build + push ──► Docker Hub  <toi>/ultimate-cicd:<BUILD_NUMBER>
               4. sed replaceImageTag → <BUILD_NUMBER> dans deployment.yml, git commit + push
                                │
                                ▼ dépôt Git (dossier spring-boot-app-manifests)
 Ton poste : cluster kind ◄── Argo CD surveille ce dossier, synchronise ──► Deployment + Service
```

La grande différence avec le projet 16 : **un seul pipeline** fait la CI et met à jour le manifest (pas de job CD séparé), et l'**agent Jenkins est un conteneur** jetable.

## Les concepts

:::why Un agent Jenkins Docker
```groovy
agent {
  docker {
    image 'abhishekf5/maven-abhishek-docker-agent:v1'
    args '--user root -v /var/run/docker.sock:/var/run/docker.sock'
  }
}
```
Jenkins lance un **conteneur** à partir de cette image (qui contient JDK, Maven et le client Docker), exécute toutes les étapes dedans, puis le supprime. Avantages : pas d'outils à installer sur le serveur Jenkins, environnement de build identique à chaque fois, versions faciles à changer. Le montage de `/var/run/docker.sock` permet au conteneur d'utiliser le **Docker de l'hôte** pour construire l'image de l'application (on parle de *Docker-outside-of-Docker*). Attention : cela donne au build un accès équivalent à root sur l'hôte.
:::

:::why Le marqueur `replaceImageTag`
Dans `spring-boot-app-manifests/deployment.yml`, l'image est écrite `…/ultimate-cicd:replaceImageTag`. Le pipeline remplace ce mot par le numéro de build avec `sed`, puis commit. **Problème** : au build suivant, le mot `replaceImageTag` n'existe plus (il a été remplacé par `1`), donc `sed` ne remplace plus rien ! Le dépôt d'origine a ce défaut. On le corrige à l'étape 4 avec une expression régulière qui remplace **n'importe quel** tag.
:::

## Étape 1 — Le serveur Jenkins + SonarQube

Instance Ubuntu 24.04 **`t3.large`** (8 Go : Jenkins + SonarQube + builds), 30 Go, ports 22, 8080 et 9000 depuis ton IP (et 8080 depuis GitHub pour le webhook).

```bash
# Java + Jenkins : annexe A.3
# Docker, et droits pour l'utilisateur jenkins (il doit lancer des conteneurs d'agent)
sudo apt install -y docker.io
sudo usermod -aG docker jenkins
sudo usermod -aG docker ubuntu
sudo systemctl restart jenkins

# SonarQube en conteneur (rapide, base embarquée : suffisant pour un lab)
echo "vm.max_map_count=524288" | sudo tee /etc/sysctl.d/99-sonar.conf && sudo sysctl --system
sudo docker run -d --name sonarqube --restart unless-stopped -p 9000:9000 \
  -v sonar_data:/opt/sonarqube/data sonarqube:community
```

Plugins Jenkins : **Docker Pipeline**, **SonarQube Scanner** (pas indispensable ici car le pipeline appelle `mvn sonar:sonar` directement).

## Étape 2 — Préparer ton dépôt

Crée un dépôt GitHub `java-gitops` et copies-y les dossiers `spring-boot-app/` et `spring-boot-app-manifests/` du projet 18.

```text
java-gitops/
├── spring-boot-app/
│   ├── JenkinsFile
│   ├── Dockerfile
│   ├── pom.xml
│   └── src/
└── spring-boot-app-manifests/
    ├── deployment.yml
    └── service.yml
```

Dans `spring-boot-app-manifests/deployment.yml`, remplace l'image par `<toi-dockerhub>/ultimate-cicd:replaceImageTag`.

Dans `spring-boot-app/Dockerfile`, remplace `FROM adoptopenjdk/openjdk11:alpine-jre` (projet AdoptOpenJDK arrêté, images plus maintenues) par **`FROM eclipse-temurin:11-jre`**, son successeur officiel.

| ID | Type | Contenu |
|---|---|---|
| `sonarqube` | Secret text | token généré dans SonarQube (*My Account → Security*) |
| `docker-cred` | Username with password | pseudo Docker Hub + access token |
| `github` | Secret text | token GitHub avec *Contents: Read and write* sur `java-gitops` |

## Étape 4 — Le Jenkinsfile, adapté

Le Jenkinsfile d'origine contient des chemins vers le dépôt de l'auteur (`java-maven-sonar-argocd-helm-k8s/…`), son IP SonarQube, son pseudo Docker Hub et son identité Git. Voici la version adaptée à ta structure :

```groovy
pipeline {
  agent {
    docker {
      image 'abhishekf5/maven-abhishek-docker-agent:v1'
      args '--user root -v /var/run/docker.sock:/var/run/docker.sock'
    }
  }
  environment {
    SONAR_URL    = "http://<IP_PRIVEE_EC2>:9000"
    DOCKER_IMAGE = "<toi-dockerhub>/ultimate-cicd:${BUILD_NUMBER}"
    GIT_REPO     = "github.com/<toi>/java-gitops"
  }
  stages {
    stage('Build et tests') {
      steps {
        sh 'cd spring-boot-app && mvn -B clean package'
      }
    }
    stage('Analyse SonarQube') {
      steps {
        withCredentials([string(credentialsId: 'sonarqube', variable: 'SONAR_AUTH_TOKEN')]) {
          sh 'cd spring-boot-app && mvn -B sonar:sonar -Dsonar.token=$SONAR_AUTH_TOKEN -Dsonar.host.url=$SONAR_URL'
        }
      }
    }
    stage('Image Docker') {
      steps {
        script {
          sh 'cd spring-boot-app && docker build -t $DOCKER_IMAGE .'
          docker.withRegistry('https://index.docker.io/v1/', 'docker-cred') {
            docker.image("${DOCKER_IMAGE}").push()
          }
        }
      }
    }
    stage('Mise à jour du manifest') {
      steps {
        withCredentials([string(credentialsId: 'github', variable: 'GITHUB_TOKEN')]) {
          sh '''
            git config user.email "jenkins@exemple.com"
            git config user.name  "Jenkins"
            # remplace le tag quel qu'il soit (replaceImageTag, 12, 13…) par le numéro de build
            sed -i -E "s#(ultimate-cicd:).*#\\1${BUILD_NUMBER}#" spring-boot-app-manifests/deployment.yml
            git add spring-boot-app-manifests/deployment.yml
            git commit -m "ci: image ultimate-cicd:${BUILD_NUMBER} [skip ci]"
            git push https://${GITHUB_TOKEN}@${GIT_REPO} HEAD:main
          '''
        }
      }
    }
  }
}
```

:::warn La boucle infinie
Le pipeline pousse un commit dans **le même dépôt** que celui qui le déclenche. Avec un webhook, ce commit relance le pipeline, qui pousse un commit, qui relance… Solutions : déclencher uniquement sur les changements de `spring-boot-app/` (option *Additional Behaviours → Polling ignores commits in certain paths* / *Included Regions*), ignorer les commits de l'utilisateur Jenkins, ou — le plus propre — **mettre les manifests dans un dépôt séparé** (comme au projet 16). Le `[skip ci]` dans le message est respecté par certains outils (GitHub Actions, GitLab), mais pas nativement par Jenkins.
:::

Jenkins → *New Item* `java-gitops` → **Pipeline** → *Pipeline script from SCM* → Git → ton dépôt → *Script Path* : **`spring-boot-app/JenkinsFile`** → *Save* → *Build Now*.

:::check
- Le build passe ; SonarQube (`http://<IP>:9000`) montre le projet `spring-boot-demo` analysé.
- Docker Hub contient `ultimate-cicd:1`.
- Dans GitHub, un commit « ci: image ultimate-cicd:1 » a modifié `deployment.yml`.
:::

## Étape 5 — Argo CD sur un cluster local

Sur **ton poste** (Docker Desktop ou Docker dans WSL) :

```bash
kind create cluster --name gitops          # (ou : minikube start)
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl -n argocd rollout status deploy/argocd-server
argocd admin initial-password -n argocd    # (CLI argocd : voir projet 16) ou la commande kubectl de la leçon 12
kubectl -n argocd port-forward svc/argocd-server 8443:443
```

Crée l'Application (dans un fichier `app.yaml`, c'est plus reproductible que les clics) :

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: spring-boot-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/<toi>/java-gitops.git
    targetRevision: main
    path: spring-boot-app-manifests
  destination:
    server: https://kubernetes.default.svc
    namespace: default
  syncPolicy:
    automated: { prune: true, selfHeal: true }
```

```bash
kubectl apply -f app.yaml
kubectl get pods
kubectl port-forward svc/spring-boot-app-service 8080:80      # nom et port : voir service.yml
```

Ouvre `http://localhost:8080` : l'application Spring Boot répond.

:::why Argo CD n'a pas besoin d'être joignable depuis Internet
Ton cluster kind est sur ton poste, invisible depuis Internet, et ça fonctionne quand même : c'est **Argo CD qui va chercher** les changements sur GitHub (pull), et les nœuds qui vont chercher l'image sur Docker Hub. C'est l'un des grands avantages du modèle GitOps : on peut déployer dans des clusters privés sans ouvrir aucun port entrant.
:::

## Étape 6 — Boucle complète

Modifie un texte de `spring-boot-app/src/main/resources/templates/index.html`, commit, push → Jenkins construit `ultimate-cicd:2` et met à jour le manifest → Argo CD (synchro toutes les 3 minutes par défaut, ou bouton *Refresh*) déploie la nouvelle version.

## Dépannage

:::fix
- **`docker: permission denied` au lancement de l'agent** : l'utilisateur `jenkins` n'est pas dans le groupe `docker`, ou Jenkins n'a pas été redémarré après l'ajout.
- **`mvn sonar:sonar` : `Not authorized`** : token invalide ; **`Connection refused`** : utilise l'IP **privée** de l'EC2 (depuis un conteneur, `localhost` désigne le conteneur lui-même, pas l'hôte !).
- **`git push` : 403** : token GitHub sans droit d'écriture ; **`nothing to commit`** : le `sed` n'a rien remplacé (vérifie le nom d'image dans `deployment.yml`).
- **Pods `ImagePullBackOff` dans kind** : nom d'image erroné, ou image construite en ARM sur un Mac M1 et nœud x86 (rare avec kind, qui utilise l'architecture de ton poste).
:::

## Nettoyage

:::clean
`kind delete cluster --name gitops` ; *terminate* l'EC2 Jenkins ; supprime le webhook GitHub. Garde le dépôt et l'image.
:::
