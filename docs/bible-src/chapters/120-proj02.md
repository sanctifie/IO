## Ce qu'on construit

Un site web hautement disponible et capable de grandir tout seul :

- un **VPC « bastion »** (`192.168.0.0/16`) qui contient uniquement la machine d'administration ;
- un **VPC « application »** (`172.32.0.0/16`) qui contient des serveurs web **privés**, répartis sur 2 zones, gérés par un **Auto Scaling Group** (2 à 4 instances) ;
- un **Network Load Balancer** public qui distribue le trafic ;
- un **Transit Gateway** qui relie les deux VPC pour que le bastion puisse administrer les serveurs ;
- les **Flow Logs** des deux VPC dans CloudWatch, pour l'audit réseau ;
- une **Golden AMI** qui contient Apache, Git, l'agent CloudWatch et l'agent SSM ;
- un **bucket S3** qui contient la configuration de l'application.

## Les concepts du projet

:::why Pourquoi deux VPC séparés ?
C'est une pratique courante en entreprise : un **VPC de gestion** (ou « shared services ») contient les outils d'administration (bastion, outils de monitoring, VPN), et des **VPC applicatifs** contiennent les charges de production. On isole ainsi les accès : même si une application est compromise, elle n'a pas de chemin direct vers les outils d'admin, et inversement on contrôle précisément les flux autorisés entre les deux.
:::

:::why Pourquoi un Transit Gateway plutôt qu'un VPC Peering ?
Pour **deux** VPC, un *peering* suffirait et serait moins cher. Mais un peering ne relie que deux VPC, et il n'est pas transitif (si A↔B et B↔C, A ne peut pas joindre C). Quand une entreprise a 10, 50 ou 200 VPC, elle utilise un **Transit Gateway** : un routeur central auquel tous les VPC se raccordent (topologie en étoile). Le projet te fait manipuler le vrai outil.
:::

:::why Pourquoi un NLB et pas un ALB ?
Le projet demande un NLB. Un ALB conviendrait aussi parfaitement pour un site web (et c'est ce que tu utiliseras dans les projets suivants). Le NLB a la particularité de **conserver l'adresse IP du client** jusqu'à l'instance et de travailler en TCP pur.
:::

## Plan d'adressage

Écris-le **avant** de cliquer. C'est le travail de l'architecte réseau.

| VPC | Subnet | CIDR | AZ | Type | Contient |
|---|---|---|---|---|---|
| bastion `192.168.0.0/16` | `bastion-public-a` | `192.168.1.0/24` | a | public | bastion |
| app `172.32.0.0/16` | `app-public-a` | `172.32.1.0/24` | a | public | NAT GW, nœud NLB |
| app | `app-public-b` | `172.32.2.0/24` | b | public | nœud NLB |
| app | `app-private-a` | `172.32.3.0/24` | a | privé | serveurs web, attachement TGW |
| app | `app-private-b` | `172.32.4.0/24` | b | privé | serveurs web, attachement TGW |

:::tip Règle d'or de l'adressage
Les plages des VPC qu'on veut relier **ne doivent pas se chevaucher**. `192.168.0.0/16` et `172.32.0.0/16` sont disjointes : c'est bon. Si les deux VPC utilisaient `10.0.0.0/16`, le routage entre eux serait impossible.
:::

:::info `172.32.0.0/16` n'est pas une plage privée !
Les plages privées sont `172.16.0.0` à `172.31.255.255`. `172.32.x.x` est en réalité une plage **publique** appartenant à quelqu'un d'autre. Dans un VPC isolé, ça fonctionne, mais tes serveurs ne pourraient pas joindre les vraies machines qui utilisent ces adresses sur Internet. Le dépôt d'origine utilise cette plage, on la garde pour coller au projet, mais **en entreprise, utilise une plage privée** (par exemple `10.32.0.0/16`).
:::

## Étape 1 — Créer la Golden AMI

**1.1 — Lancer une instance de construction.** Dans le VPC par défaut : Amazon Linux 2023, `t3.micro`, key pair `io-key`, SSH depuis My IP, nom `ami-builder`.

**1.2 — Créer un rôle IAM pour l'instance.** IAM → Roles → *Create role* → *AWS service* → *EC2* → attache :
- `AmazonSSMManagedInstanceCore` (Session Manager),
- `CloudWatchAgentServerPolicy` (envoi des métriques et logs).

Nom : `io-web-role`. Puis EC2 → ton instance → *Actions → Security → Modify IAM role* → `io-web-role`.

**1.3 — Installer les logiciels.**

```bash
ssh -i ~/.ssh/io-key.pem ec2-user@<IP>
sudo dnf update -y
sudo dnf install -y httpd git amazon-cloudwatch-agent
aws --version                       # l'AWS CLI v2 est préinstallée sur Amazon Linux 2023
systemctl status amazon-ssm-agent   # l'agent SSM aussi
sudo systemctl enable httpd         # Apache démarrera automatiquement au boot
```

**1.4 — Configurer l'agent CloudWatch pour envoyer la mémoire et le disque.**

```bash
sudo tee /opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json > /dev/null <<'EOF'
{
  "agent": { "metrics_collection_interval": 60 },
  "metrics": {
    "namespace": "IO/WebServers",
    "append_dimensions": { "InstanceId": "${aws:InstanceId}", "AutoScalingGroupName": "${aws:AutoScalingGroupName}" },
    "metrics_collected": {
      "mem":  { "measurement": ["mem_used_percent"] },
      "disk": { "measurement": ["used_percent"], "resources": ["/"] }
    }
  }
}
EOF
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
  -a fetch-config -m ec2 -s -c file:/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json
sudo systemctl enable amazon-cloudwatch-agent
```

:::why Le `<<'EOF' ... EOF`
C'est un **heredoc** : tout le texte entre les deux `EOF` est envoyé à la commande (ici `tee`, qui l'écrit dans le fichier). Les guillemets autour de `'EOF'` empêchent Bash d'interpréter les `${...}` : ils arrivent tels quels dans le fichier, et c'est l'agent CloudWatch qui les remplacera par l'ID de l'instance.
:::

Après 2 à 3 minutes : CloudWatch → *Metrics → All metrics* → namespace `IO/WebServers` → tu dois voir `mem_used_percent`.

**1.5 — Créer l'AMI.** EC2 → ton instance → *Actions → Image and templates → Create image* → nom `io-golden-web-v1` → *Create image*. Attends l'état **Available** (EC2 → AMIs), puis **termine** l'instance `ami-builder`.

## Étape 2 — Préparer l'application et sa configuration

**2.1 — Mettre le code dans ton dépôt IO.** Copie le dossier `html-web-app` du dépôt d'origine dans `projects/02-vpc/app/` de ton dépôt, puis pousse-le.

```bash
cd ~/IO
git clone --depth 1 https://github.com/ZaheerrAhmed/DevOps-Projects /tmp/dp
mkdir -p projects/02-vpc && cp -r /tmp/dp/DevOps-Project-02/html-web-app projects/02-vpc/app
git add projects/02-vpc && git commit -m "Projet 02 : application web" && git push
```

*(Le dépôt d'origine parle de Bitbucket ; GitHub fait exactement la même chose.)*

**2.2 — Créer le bucket de configuration.**

```bash
BUCKET=io-02-config-<ton-prenom>
aws s3 mb s3://$BUCKET --region eu-west-3
echo 'APP_ENV=production
APP_MESSAGE=Bienvenue sur le site du projet 02' > app.env
aws s3 cp app.env s3://$BUCKET/app.env
```

**2.3 — Donner au rôle le droit de lire ce bucket, et rien d'autre.** IAM → Roles → `io-web-role` → *Add permissions → Create inline policy* → onglet JSON :

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "s3:GetObject",  "Resource": "arn:aws:s3:::io-02-config-<ton-prenom>/*" },
    { "Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::io-02-config-<ton-prenom>" }
  ]
}
```

Nom : `read-io-02-config`. C'est le « *Do not grant S3 Full Access* » de l'énoncé.

## Étape 3 — Construire les deux VPC

Tu peux utiliser l'assistant **VPC → Create VPC → « VPC and more »**, qui crée VPC, subnets, tables de routage, IGW et NAT en une fois. Mais **fais-le une première fois à la main** : c'est en créant chaque brique que tu comprends comment elles s'assemblent.

**3.1 — VPC bastion.**

1. VPC → *Your VPCs* → *Create VPC* → *VPC only* → nom `io-bastion-vpc`, CIDR `192.168.0.0/16`.
2. *Subnets* → *Create subnet* → VPC `io-bastion-vpc` → nom `bastion-public-a`, AZ `eu-west-3a`, CIDR `192.168.1.0/24`.
3. *Internet gateways* → *Create* → `io-bastion-igw` → *Actions → Attach to VPC* → `io-bastion-vpc`.
4. *Route tables* → *Create* → `bastion-public-rt` dans `io-bastion-vpc` → *Routes → Edit routes → Add route* : `0.0.0.0/0` → *Internet Gateway* `io-bastion-igw`. Puis *Subnet associations* → associe `bastion-public-a`.
5. Sur le subnet : *Actions → Edit subnet settings* → coche **Enable auto-assign public IPv4 address**.

**3.2 — VPC application.**

1. VPC `io-app-vpc`, CIDR `172.32.0.0/16`.
2. Quatre subnets selon le plan d'adressage (`app-public-a/b`, `app-private-a/b`).
3. IGW `io-app-igw` attachée à `io-app-vpc`.
4. Table `app-public-rt` : `0.0.0.0/0` → `io-app-igw`, associée aux **deux subnets publics**.
5. **NAT Gateway** : *NAT gateways → Create* → nom `io-app-nat`, subnet **`app-public-a`**, *Connectivity type* : Public → **Allocate Elastic IP** → *Create*.
6. Table `app-private-rt` : `0.0.0.0/0` → *NAT Gateway* `io-app-nat`, associée aux **deux subnets privés**.

:::warn La NAT Gateway va dans le subnet PUBLIC
C'est l'erreur la plus courante du projet. La NAT Gateway a besoin d'une route vers l'IGW pour sortir : elle doit être dans un subnet **public**. Ce sont les tables de routage des subnets **privés** qui pointent vers elle.
:::

:::info Haute disponibilité de la NAT
Ici, une seule NAT Gateway (dans l'AZ a) sert les deux subnets privés. Si l'AZ a tombe, les serveurs de l'AZ b perdent leur accès Internet sortant. En production, on met **une NAT Gateway par AZ**, chacune avec sa propre table de routage privée. On ne le fait pas ici pour diviser le coût par deux.
:::

## Étape 4 — Relier les VPC avec un Transit Gateway

1. VPC → *Transit gateways* → *Create* → nom `io-tgw`, laisse les options par défaut (*Default route table association* et *propagation* activées) → *Create*. Attends l'état **Available** (quelques minutes).
2. *Transit gateway attachments* → *Create* :
   - `io-tgw-att-bastion` : TGW `io-tgw`, type VPC, VPC `io-bastion-vpc`, subnet `bastion-public-a`.
   - `io-tgw-att-app` : VPC `io-app-vpc`, subnets **`app-private-a` et `app-private-b`** (un par AZ).
3. **Ajouter les routes dans les VPC** (le TGW sait router entre ses attachements, mais les VPC doivent savoir qu'il faut passer par lui) :
   - `bastion-public-rt` : `172.32.0.0/16` → *Transit Gateway* `io-tgw`.
   - `app-private-rt` : `192.168.0.0/16` → `io-tgw`.

:::why Le routage, c'est toujours dans les deux sens
Le bastion envoie un paquet vers `172.32.3.15` : sa table de routage dit « `172.32.0.0/16` → TGW ». Le TGW le livre dans le VPC app. Le serveur répond vers `192.168.1.20` : **sa** table de routage doit dire « `192.168.0.0/16` → TGW ». Sans cette route retour, la réponse part vers la NAT (route par défaut) et se perd. Quand une connexion entre deux réseaux échoue, vérifie **toujours l'aller ET le retour**.
:::

## Étape 5 — Les Flow Logs

1. CloudWatch → *Log groups* → *Create log group* → `/io/vpc-flow-logs`, rétention **3 jours** (pour limiter le coût).
2. Dans ce groupe, crée deux *log streams* : `bastion-vpc` et `app-vpc`. *(En pratique, AWS crée automatiquement un stream par interface réseau ; créer ces deux streams sert surtout à respecter l'énoncé.)*
3. Rôle IAM pour les Flow Logs : IAM → *Create role* → *Custom trust policy* :

```json
{
  "Version": "2012-10-17",
  "Statement": [{ "Effect": "Allow", "Principal": { "Service": "vpc-flow-logs.amazonaws.com" }, "Action": "sts:AssumeRole" }]
}
```

   Ajoute une politique inline autorisant `logs:CreateLogGroup`, `logs:CreateLogStream`, `logs:PutLogEvents`, `logs:DescribeLogGroups`, `logs:DescribeLogStreams` sur `*`. Nom du rôle : `io-flowlogs-role`.

4. VPC → `io-bastion-vpc` → onglet *Flow logs* → *Create flow log* → *Filter* : **All** → destination *CloudWatch Logs* → groupe `/io/vpc-flow-logs` → rôle `io-flowlogs-role`. Recommence pour `io-app-vpc`.

Une ligne de Flow Log ressemble à ceci :

```text
2 123456789012 eni-0a1b2c3d 82.64.10.5 192.168.1.20 51234 22 6 12 3400 1696400000 1696400060 ACCEPT OK
   compte       interface   IP source   IP dest      port src/dst proto paquets octets début fin  décision
```

Le champ `REJECT` est précieux pour diagnostiquer un Security Group trop restrictif.

## Étape 6 — Le bastion

1. Security Group `io-bastion-sg` dans `io-bastion-vpc` : entrée **SSH 22 depuis My IP**. *(L'énoncé dit « depuis Internet » ; restreindre à ton IP est bien plus sûr.)*
2. Lance une instance : Amazon Linux 2023, `t3.micro`, VPC `io-bastion-vpc`, subnet `bastion-public-a`, SG `io-bastion-sg`, key pair `io-key`, nom `io-bastion`.
3. **Elastic IP** : EC2 → *Elastic IPs* → *Allocate* → *Actions → Associate* → instance `io-bastion`.

## Étape 7 — Le Launch Template

**7.1 — Security Group des serveurs web** (`io-web-sg`, dans `io-app-vpc`) :

| Type | Port | Source | Pourquoi |
|---|---|---|---|
| SSH | 22 | `io-bastion-sg`… | *voir l'encadré ci-dessous* |
| HTTP | 80 | `io-nlb-sg` (créé à l'étape 9) | seul le load balancer peut joindre les serveurs |

:::warn Référencer un Security Group d'un autre VPC
Une règle de SG ne peut référencer un SG d'un **autre** VPC qu'à travers un *peering* (et, plus récemment, via certains Transit Gateways selon la configuration). Le plus simple et le plus fiable ici : source **`192.168.1.0/24`** (le subnet du bastion) pour le port 22.
:::

**7.2 — Le user data** : le script exécuté au premier démarrage de chaque serveur.

```bash
#!/bin/bash
set -euxo pipefail
exec > /var/log/user-data.log 2>&1          # tout tracer pour pouvoir déboguer

BUCKET=io-02-config-<ton-prenom>
REPO=https://github.com/<ton-pseudo-github>/IO.git

# 1. Récupérer le code et le placer à la racine du serveur web
git clone --depth 1 "$REPO" /tmp/io
cp -r /tmp/io/projects/02-vpc/app/* /var/www/html/

# 2. Récupérer la configuration depuis S3 (grâce au rôle IAM, sans aucune clé)
aws s3 cp "s3://$BUCKET/app.env" /etc/app.env
source /etc/app.env

# 3. Afficher quelle instance a répondu (utile pour voir le load balancing)
TOKEN=$(curl -sX PUT http://169.254.169.254/latest/api/token -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
IID=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-id)
AZ=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/placement/availability-zone)
echo "<p>$APP_MESSAGE — servi par $IID ($AZ)</p>" > /var/www/html/whoami.html

systemctl restart httpd
```

:::why `169.254.169.254` ?
C'est le **service de métadonnées** d'EC2 (IMDS) : une adresse spéciale, joignable uniquement depuis l'instance, qui lui donne des informations sur elle-même (ID, AZ, rôle IAM…). Le `TOKEN` correspond à **IMDSv2**, la version sécurisée, obligatoire par défaut sur les nouvelles AMI.
:::

**7.3 — Créer le Launch Template.** EC2 → *Launch Templates* → *Create* :

- Nom `io-web-lt` ; coche *Provide guidance… Auto Scaling*.
- AMI : **My AMIs** → `io-golden-web-v1`.
- Type : `t3.micro`. Key pair : `io-key`.
- *Network settings* : **ne choisis pas de subnet** (c'est l'ASG qui décidera), SG `io-web-sg`.
- *Advanced details* : *IAM instance profile* `io-web-role` ; *Metadata version* : V2 only ; *User data* : colle le script.

## Étape 8 — Target Group et Auto Scaling Group

1. EC2 → *Target Groups* → *Create* → type **Instances**, nom `io-web-tg`, protocole **TCP 80**, VPC `io-app-vpc`. *Health checks* : protocole HTTP, chemin `/`. Ne sélectionne aucune instance → *Create*.
2. EC2 → *Auto Scaling Groups* → *Create* :
   - Nom `io-web-asg`, Launch Template `io-web-lt`.
   - VPC `io-app-vpc`, subnets **`app-private-a` et `app-private-b`**.
   - *Attach to an existing load balancer* → *Choose from your load balancer target groups* → `io-web-tg`.
   - Coche *Turn on Elastic Load Balancing health checks* (ainsi une instance dont le site ne répond plus sera remplacée, pas seulement une instance éteinte).
   - Capacité : **désirée 2, min 2, max 4**.
   - *Scaling policy* : *Target tracking*, *Average CPU utilization* = **50 %**.

En 2 à 3 minutes, deux instances apparaissent, une dans chaque AZ.

## Étape 9 — Le Network Load Balancer

1. Security Group `io-nlb-sg` dans `io-app-vpc` : entrée **TCP 80 depuis `0.0.0.0/0`**.
2. EC2 → *Load Balancers* → *Create* → **Network Load Balancer** :
   - Nom `io-web-nlb`, *Internet-facing*, IPv4.
   - VPC `io-app-vpc`, mappings : `app-public-a` et `app-public-b`.
   - Security group : `io-nlb-sg`. *(Un SG ne peut être ajouté à un NLB qu'**à sa création**.)*
   - *Listener* TCP 80 → `io-web-tg`.
3. Reviens sur `io-web-sg` et ajoute la règle HTTP 80 depuis `io-nlb-sg`.
4. Target Groups → `io-web-tg` → onglet *Targets* : attends que les 2 instances soient **healthy**.

## Étape 10 — Route 53 (optionnel, si tu as un domaine)

Route 53 → *Hosted zones* → ta zone → *Create record* : nom `projet02`, type **CNAME**, valeur = le *DNS name* du NLB. *(Encore mieux : type A avec **Alias** vers le NLB.)* Sans domaine, utilise directement le nom DNS du NLB.

## Validation

:::check
**1. Depuis Internet** : ouvre `http://<DNS-du-NLB>/` → la page de l'application s'affiche. Ouvre `http://<DNS-du-NLB>/whoami.html` plusieurs fois (navigation privée, ou `curl` en boucle) : l'ID d'instance change d'une requête à l'autre.

```bash
for i in $(seq 1 10); do curl -s http://<DNS-du-NLB>/whoami.html; done
```

**2. Par le bastion, en SSH** : on utilise le **transfert d'agent SSH** pour rebondir sans copier la clé privée sur le bastion.

```bash
ssh-add ~/.ssh/io-key.pem                          # charger la clé dans l'agent local
ssh -A ec2-user@<EIP-du-bastion>                   # -A : transférer l'agent
ssh ec2-user@172.32.3.x                            # depuis le bastion, vers un serveur privé (IP visible dans la console)
# ou en une commande, depuis ton poste :
ssh -J ec2-user@<EIP-du-bastion> ec2-user@172.32.3.x    # -J = ProxyJump
```

**3. Par Session Manager** : EC2 → une instance web → *Connect* → onglet **Session Manager** → *Connect*. Un terminal s'ouvre sans SSH ni bastion.

**4. Auto-réparation** : *terminate* une des instances web. Dans les minutes qui suivent, l'ASG en relance une nouvelle, qui rejoint le Target Group.

**5. Montée en charge** (bonus) : connecte-toi à une instance et lance `sudo dnf install -y stress-ng && stress-ng --cpu 2 --timeout 600`. Au bout de quelques minutes, l'ASG ajoute des instances (onglet *Activity*).

**6. Flow Logs** : CloudWatch → `/io/vpc-flow-logs` → des lignes `ACCEPT` et `REJECT` apparaissent.
:::

:::danger Ne copie jamais ta clé privée sur le bastion
Copier `io-key.pem` sur le bastion (`scp`) est tentant, mais si le bastion est compromis, l'attaquant récupère la clé de **toutes** tes machines. Le transfert d'agent (`-A`) ou `ProxyJump` (`-J`) gardent la clé sur ton poste.
:::

## Dépannage

:::fix
- **Targets `unhealthy`** : connecte-toi à une instance (Session Manager) et regarde `/var/log/user-data.log`. Causes typiques : le `git clone` échoue (dépôt privé, ou pas de route vers la NAT), le `aws s3 cp` échoue (`AccessDenied` : politique IAM ou nom de bucket incorrect), Apache n'est pas démarré, ou le SG `io-web-sg` n'autorise pas le port 80 depuis le NLB.
- **Le user data ne s'est pas exécuté** : il doit commencer exactement par `#!/bin/bash`. Les logs système sont dans `/var/log/cloud-init-output.log`.
- **Le bastion n'arrive pas à joindre les serveurs** : vérifie les deux routes TGW (aller et retour), l'état *Available* des attachements, et la règle SSH de `io-web-sg` (source `192.168.1.0/24`).
- **Session Manager indique « instance not connected »** : rôle sans `AmazonSSMManagedInstanceCore`, ou pas d'accès sortant (NAT absente ou mal routée). Patiente aussi 2 à 3 minutes après le démarrage.
- **Les instances n'ont pas Internet** : la NAT est-elle dans un subnet public ? La table privée pointe-t-elle vers la NAT ? Les subnets privés sont-ils bien associés à cette table ?
:::

## Nettoyage

:::clean
Dans **cet ordre** (les dépendances empêchent sinon certaines suppressions) :
1. Auto Scaling Group `io-web-asg` → *Delete* (termine les instances).
2. Load balancer `io-web-nlb`, puis Target Group `io-web-tg`.
3. Instance `io-bastion` → *Terminate* ; puis **libère l'Elastic IP** (*Release*).
4. **NAT Gateway** `io-app-nat` → *Delete*, puis libère son Elastic IP.
5. Transit Gateway : supprime les **deux attachements**, puis le TGW.
6. Flow logs, puis le log group `/io/vpc-flow-logs`.
7. Les deux VPC (*Delete VPC* supprime aussi subnets, tables de routage et IGW).
8. Bucket S3 (`aws s3 rb s3://io-02-config-<prenom> --force`).
9. Garde l'AMI `io-golden-web-v1` si tu veux la réutiliser (le stockage du snapshot coûte quelques centimes par mois), sinon *Deregister* l'AMI **et** supprime son snapshot (EC2 → Snapshots).
:::

## Pour aller plus loin

- Remplace le NLB par un **ALB** et compare.
- Ajoute **HTTPS** avec un certificat gratuit **ACM** (nécessite un domaine).
- Supprime complètement le bastion et le port 22 : administre uniquement par Session Manager (c'est la tendance actuelle).
- Remplace la NAT Gateway par des **VPC endpoints** S3 et SSM : les serveurs n'ont plus du tout besoin d'Internet (mais il faut alors fournir le code autrement, par exemple via S3).
- Refais tout le projet en **Terraform** une fois la partie 3 terminée. Tu verras la différence : 1 heure de clics contre `terraform apply`.
