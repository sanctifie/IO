# Projet 20 — Déployer du Terraform sur Azure avec un pipeline Azure DevOps

:::card
| | |
|---|---|
| Niveau | ★★★☆☆ Intermédiaire |
| Durée | 3 à 5 heures |
| Coût | quelques centimes (Service Bus Standard ~0,013 $/h, stockage de l'état) |
| Compétences | service principal (ou fédération d'identité), RBAC Azure, backend Terraform `azurerm`, variable groups et secrets, **templates** de pipeline réutilisables, environnements et **approbations**, déploiement multi-environnements |
| Prérequis | Projet 07 |
| Dépôt d'origine | `DevOps-Project-20` : `terraform/` (Service Bus + 2 files), `deploy/tfdemo-env01-terraform.yml`, `deploy/templates/terraform-template.yml` |

## Ce qu'on construit

Un pipeline Terraform **propre et réutilisable** sur Azure, qui déploie un **Azure Service Bus** (un service de files de messages) avec deux files. L'accent est mis sur les points que les tutoriels survolent : les **droits** de l'identité de déploiement, la gestion des **secrets**, l'**approbation** avant `apply`, et le **passage à plusieurs environnements** sans copier-coller.

```ascii
 Azure Repos
   terraform/       (main.tf, servicebus.tf, variables.tf, providers.tf, env01.tfvars, env02.tfvars)
   deploy/
     templates/terraform-template.yml   ← la logique plan/apply, écrite UNE fois
     tfdemo-env01-terraform.yml         ← pipeline env01 : appelle le template avec ses paramètres
     tfdemo-env02-terraform.yml         ← pipeline env02 : idem
                │
                ▼  agent hébergé (ubuntu-latest)
   Stage Plan ─► Stage Apply (job "deployment" lié à l'environnement env01 → APPROBATION)
                │ identité : tfdemo-spn (Contributor sur l'abonnement, Storage Blob Data Contributor sur l'état)
                ▼
   tfstate-tfdemo-rg / tfstatetfdemostg / tfstate / tfdemo.env01.tfstate
   tfdemo-env01-rg : Service Bus namespace « tfdemo-env01-sbns » + queue01 + queue02
```

:::why Azure Service Bus en deux mots
Une **file de messages** permet à deux applications de communiquer de façon **asynchrone** : l'une dépose des messages (une commande à traiter), l'autre les consomme à son rythme. Si le consommateur tombe, les messages attendent dans la file au lieu d'être perdus. C'est l'équivalent d'**Amazon SQS** ou de **RabbitMQ** (que tu as vu dans Robot Shop).
:::

## Étape 1 — L'identité de déploiement

Le tutoriel d'origine crée une **App registration** `tfdemo-spn` avec un **secret client**. Méthode :

1. Portail Azure → **Microsoft Entra ID** → *App registrations* → *New registration* → `tfdemo-spn`.
2. Note l'**Application (client) ID** et le **Directory (tenant) ID**.
3. *Certificates & secrets → New client secret* → description `ADO`, expiration courte → **note la valeur** (affichée une seule fois).

:::tip Mieux : la fédération d'identité, sans secret
Comme au projet 07, tu peux créer une *service connection* Azure Resource Manager en **Workload Identity Federation** et utiliser la tâche `AzureCLI@2` avec `addSpnToEnvironment: true` pour fournir à Terraform des identifiants **temporaires** (variables `ARM_USE_OIDC=true`, `ARM_OIDC_TOKEN`…). Plus de secret qui expire ou qui fuit. On suit ici la méthode du tutoriel (plus simple à comprendre), puis on te montre la variante en fin de projet.
:::

## Étape 2 — Le stockage de l'état et les droits

```bash
az group create -n tfstate-tfdemo-rg -l francecentral
az storage account create -n tfstatetfdemo$RANDOM -g tfstate-tfdemo-rg -l francecentral --sku Standard_LRS
az storage container create --name tfstate --account-name <nom-du-storage> --auth-mode login
```

Puis deux **attributions de rôles** pour `tfdemo-spn` :

| Rôle | Scope | Pourquoi |
|---|---|---|
| **Storage Blob Data Contributor** | le storage account de l'état | lire/écrire le fichier d'état |
| **Contributor** | l'abonnement | créer les groupes de ressources et le Service Bus |

```bash
SPN_ID=<application-client-id>
SUB=$(az account show --query id -o tsv)
az role assignment create --assignee $SPN_ID --role "Storage Blob Data Contributor" \
  --scope $(az storage account show -n <nom-du-storage> --query id -o tsv)
az role assignment create --assignee $SPN_ID --role "Contributor" --scope /subscriptions/$SUB
```

:::why Le moindre privilège, version Azure
*Contributor* sur tout l'abonnement, c'est large. Alternative proposée par le tutoriel : **créer à l'avance** le groupe de ressources cible et donner *Contributor* **uniquement sur ce groupe**. Terraform ne crée alors plus le groupe (on le lit avec un bloc `data "azurerm_resource_group"`). Plus de travail initial, beaucoup moins de risque.
:::

## Étape 3 — Le code Terraform

Importe le dossier `DevOps-Project-20` dans un dépôt Azure Repos. Points à adapter :

**`terraform/providers.tf`** — le backend pointe vers le storage de l'état ; ajoute `use_azuread_auth = true` pour s'authentifier par Entra ID plutôt que par clé de stockage :

```hcl
terraform {
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.0" }
    random  = { source = "hashicorp/random",  version = "~> 3.0" }
  }
  backend "azurerm" {
    resource_group_name  = "tfstate-tfdemo-rg"
    storage_account_name = "<nom-du-storage>"
    container_name       = "tfstate"
    key                  = "tfdemo.env01.tfstate"
    use_azuread_auth     = true
  }
}
provider "azurerm" {
  features {}
  # subscription_id est obligatoire avec azurerm v4 : fourni par la variable d'environnement ARM_SUBSCRIPTION_ID
}
```

:::warn azurerm v3 → v4
Le dépôt utilise `azurerm ~> 3.0`. Avec la v4 (actuelle), quelques attributs ont été renommés : dans `azurerm_servicebus_queue`, `enable_batched_operations` → `batched_operations_enabled`, `enable_partitioning` → `partitioning_enabled`, `enable_express` → `express_enabled`. Si `terraform validate` signale un argument inconnu, c'est presque toujours un renommage de ce type : consulte la page de la ressource dans la documentation du provider (section *Upgrade guide*). Tu peux aussi garder `~> 3.0` pour coller au tutoriel.
:::

**Le fichier de variables** : le pipeline attend `tfdemo.env01.tfvars`, **absent du dépôt**. Crée-le dans `terraform/` :

```hcl
project     = "tfdemo"
environment = "env01"
location    = "francecentral"
```

(Les noms exacts des variables sont dans `variables.tf`.)

## Étape 4 — Le variable group des secrets

Azure DevOps → *Pipelines → Library → + Variable group* → nom **`Terraform_SPN`** :

| Variable | Valeur | Secret ? |
|---|---|---|
| `ARM_CLIENT_ID` | Application (client) ID | non |
| `ARM_TENANT_ID` | Directory (tenant) ID | non |
| `ARM_SUBSCRIPTION_ID` | ID de l'abonnement | non |
| `ARM_CLIENT_SECRET` | la valeur du secret | **oui** (cadenas) |

Le provider `azurerm` lit **automatiquement** ces variables d'environnement `ARM_*` pour s'authentifier.

:::warn Les variables secrètes ne sont pas des variables d'environnement
Azure DevOps expose automatiquement les variables **non secrètes** comme variables d'environnement des scripts. Les variables **secrètes**, non : il faut les passer explicitement avec `env:`. C'est pour cela que le template contient :
```yaml
env:
  ARM_CLIENT_SECRET: $(ARM_CLIENT_SECRET)   # this needs to be explicitly set as it's a sensitive value
```
Oublier ce bloc donne une erreur d'authentification déroutante, alors que la variable « existe » bien.
:::

## Étape 5 — Les pipelines : un template, plusieurs environnements

**`deploy/templates/terraform-template.yml`** — la logique commune, paramétrée :

```yaml
parameters:
- name: rootFolder
  type: string
- name: tfvarsFile
  type: string
- name: adoEnvironment
  type: string

stages:
- stage: Terraform_Plan
  jobs:
  - job: Terraform_Plan
    pool: { vmImage: ubuntu-latest }
    steps:
    - script: |
        terraform init -input=false
        terraform plan -input=false -var-file ${{ parameters.tfvarsFile }} -out=tfplan
      displayName: Terraform plan
      workingDirectory: ${{ parameters.rootFolder }}
      env:
        ARM_CLIENT_SECRET: $(ARM_CLIENT_SECRET)
    - publish: ${{ parameters.rootFolder }}/tfplan      # amélioration : on garde le plan validé
      artifact: tfplan

- stage: Terraform_Apply
  dependsOn: Terraform_Plan
  condition: succeeded()
  jobs:
  - deployment: Terraform_Apply
    pool: { vmImage: ubuntu-latest }
    environment: ${{ parameters.adoEnvironment }}        # ← l'approbation se configure sur cet environnement
    strategy:
      runOnce:
        deploy:
          steps:
          - checkout: self
          - download: current
            artifact: tfplan
          - script: |
              terraform init -input=false
              terraform apply -input=false $(Pipeline.Workspace)/tfplan/tfplan
            displayName: Terraform apply
            workingDirectory: ${{ parameters.rootFolder }}
            env:
              ARM_CLIENT_SECRET: $(ARM_CLIENT_SECRET)
```

**`deploy/tfdemo-env01-terraform.yml`** — le pipeline de l'environnement env01 :

```yaml
name: Terraform - deploy Service Bus to env01
trigger: none

variables:
  - group: Terraform_SPN
  - name: rootFolder
    value: 'terraform/'
  - name: tfvarsFile
    value: 'tfdemo.env01.tfvars'
  - name: adoEnvironment
    value: 'env01'

stages:
- template: templates/terraform-template.yml
  parameters:
    rootFolder: $(rootFolder)
    tfvarsFile: $(tfvarsFile)
    adoEnvironment: $(adoEnvironment)
```

:::why Le template, c'est le « DRY » des pipelines
*Don't Repeat Yourself.* La logique plan/apply est écrite **une seule fois**. Chaque environnement n'est qu'un petit fichier de paramètres. Corriger ou améliorer le template profite à tous les environnements. Jenkins a l'équivalent avec les *shared libraries*, GitHub Actions avec les *reusable workflows*, GitLab avec `include:`.
:::

:::info Amélioration par rapport à l'original
Dans le template d'origine, le stage *Apply* relance un `terraform apply` complet : le plan qui est appliqué n'est **pas forcément** celui qu'on a approuvé (si quelque chose a changé entre-temps). Publier le plan comme artefact et appliquer **ce fichier** garantit que l'on applique exactement ce qui a été relu.
:::

## Étape 6 — Créer l'environnement et l'approbation

1. *Pipelines → Environments → New environment* → nom **`env01`**, ressource : *None*.
2. `env01` → ⋮ → **Approvals and checks** → **Approvals** → ajoute-toi comme approbateur.
3. *Pipelines → New pipeline → Azure Repos Git* → ton dépôt → *Existing YAML* → `deploy/tfdemo-env01-terraform.yml` → *Run*.

Le stage *Plan* s'exécute ; lis le plan dans les logs. Le stage *Apply* affiche **« Waiting for approval »** : clique *Review* → *Approve*.

:::check
- Portail Azure : groupe `tfdemo-env01-rg` contenant le namespace Service Bus `tfdemo-env01-sbns` avec `queue01` et `queue02`.
- Le conteneur `tfstate` contient `tfdemo.env01.tfstate`.
- *Environments → env01* : l'historique des déploiements.
:::

## Étape 7 — Passer à l'échelle : un deuxième environnement

1. Copie `tfdemo.env01.tfvars` en `tfdemo.env02.tfvars` (`environment = "env02"`).
2. Copie `tfdemo-env01-terraform.yml` en `tfdemo-env02-terraform.yml` et change les **trois** valeurs (`tfvarsFile`, `adoEnvironment`, et la **clé d'état**).
3. **La clé d'état doit être différente** par environnement, sinon env02 écraserait l'état d'env01. Comme la clé est écrite dans `providers.tf`, le plus propre est de la **passer à l'init** : `terraform init -backend-config="key=tfdemo.env02.tfstate"`. Ajoute un paramètre `stateKey` au template.
4. Crée l'environnement `env02` (avec ou sans approbation : on approuve souvent la production, pas les environnements de test).

## Variante — sans aucun secret (Workload Identity Federation)

Remplace les étapes `script` par une tâche `AzureCLI@2` utilisant la service connection fédérée du projet 07 :

```yaml
- task: AzureCLI@2
  inputs:
    azureSubscription: 'azure-devops-journey-service-connection'
    scriptType: bash
    scriptLocation: inlineScript
    addSpnToEnvironment: true          # expose servicePrincipalId, tenantId, idToken au script
    workingDirectory: ${{ parameters.rootFolder }}
    inlineScript: |
      export ARM_CLIENT_ID=$servicePrincipalId
      export ARM_TENANT_ID=$tenantId
      export ARM_SUBSCRIPTION_ID=$(az account show --query id -o tsv)
      export ARM_USE_OIDC=true
      export ARM_OIDC_TOKEN=$idToken
      terraform init -input=false
      terraform plan -input=false -var-file ${{ parameters.tfvarsFile }} -out=tfplan
```

Plus de variable `ARM_CLIENT_SECRET`, plus de secret à faire tourner.

## Dépannage

:::fix
- **`AuthorizationFailed` lors du `init`** (accès au blob) : rôle *Storage Blob Data Contributor* manquant (les rôles de **données** sont distincts des rôles de **gestion** comme *Contributor*). La propagation d'un rôle peut prendre quelques minutes.
- **`subscription ID could not be determined`** : azurerm v4 exige `ARM_SUBSCRIPTION_ID`.
- **`Invalid client secret provided`** : secret expiré ou mal copié ; ou `ARM_CLIENT_SECRET` non passé en `env:`.
- **`Unsupported argument`** : renommages azurerm v3 → v4 (voir l'encadré de l'étape 3).
- **`Saved plan is stale`** : un autre `apply` a modifié l'état entre le plan et l'apply ; relance le pipeline.
:::
