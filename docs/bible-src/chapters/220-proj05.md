# Projet 05 — Déployer du code dans un conteneur Docker avec Jenkins

:::card
| | |
|---|---|
| Niveau | ★★☆☆☆ Débutant+ |
| Durée | 5 à 8 heures |
| Coût | ~0,03 $/h (une `t3.small` pour Jenkins, une `t3.micro` pour Docker) |
| Compétences | installer et configurer Jenkins, plugins, credentials, intégration GitHub (webhook), Maven dans Jenkins, hôte Docker, Dockerfile Tomcat, déploiement par SSH, premier pipeline de bout en bout |
| Prérequis | Leçons 5 (Docker), 6 (CI/CD), 7 (Jenkins) |
| Dépôt d'origine | `DevOps-Project-05` (application `hello-world` : Maven multi-modules, `.war`) |

## Ce qu'on construit

Une chaîne complètement automatisée : tu modifies le code, tu fais `git push`, et deux minutes plus tard la nouvelle version tourne dans un conteneur Docker, sans aucune action manuelle.

```ascii
  Toi ── git push ──► GitHub ── webhook ──► ┌──────────────────────────┐
                                             │ Serveur JENKINS (EC2)   │
                                             │ 1. git clone            │
                                             │ 2. mvn package → .war   │
                                             │ 3. scp .war + Dockerfile │──SSH──┐
                                             └──────────────────────────┘       │
                                                                                 ▼
                                             ┌──────────────────────────────────────────┐
                                             │ HÔTE DOCKER (EC2)                        │
                                             │ 4. docker build -t regapp:<build> .      │
                                             │ 5. docker rm -f registerapp              │
                                             │ 6. docker run -p 8087:8080 regapp:<build>│◄── http://<IP>:8087/webapp/
                                             └──────────────────────────────────────────┘
```

:::info Ce qui change par rapport au dépôt d'origine
Le tutoriel d'origine (2023) utilise Amazon Linux 2, Java 11, un job *Freestyle* et le plugin **Publish Over SSH** avec **authentification par mot de passe** (en modifiant `sshd_config`). Nous faisons la même chose de manière plus moderne et plus sûre : Ubuntu 24.04, Java 21, un **Jenkinsfile** (pipeline versionné avec le code) et une **clé SSH** gérée par le plugin **SSH Agent**. Le résultat fonctionnel est identique.
:::

## Étape 1 — Le serveur Jenkins

**1.1 — Lancer l'instance.** Ubuntu 24.04, **`t3.small`** (2 Go de RAM ; Jenkins + Maven sont à l'étroit en dessous), 20 Go de disque, key pair `io-key`, nom `jenkins`. Security Group `jenkins-sg` : **22** depuis My IP, **8080** depuis My IP.

:::warn Le webhook GitHub a besoin d'atteindre Jenkins
Pour que GitHub prévienne Jenkins à chaque push, le port 8080 doit être joignable **depuis les serveurs de GitHub**. Deux options : ouvrir 8080 aux plages d'IP de GitHub (liste publiée sur `https://api.github.com/meta`, clé `hooks`), ou, plus simple pour l'exercice, ouvrir 8080 à `0.0.0.0/0` **avec un mot de passe admin solide**. Ne laisse pas ce serveur en ligne plus longtemps que nécessaire.
:::

**1.2 — Installer Java et Jenkins.** Applique la recette de l'**annexe A.3**. En résumé :

```bash
ssh -i ~/.ssh/io-key.pem ubuntu@<IP_JENKINS>
sudo hostnamectl set-hostname jenkins
sudo apt update && sudo apt install -y fontconfig openjdk-21-jre git
sudo wget -O /etc/apt/keyrings/jenkins-keyring.asc https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key
echo "deb [signed-by=/etc/apt/keyrings/jenkins-keyring.asc] https://pkg.jenkins.io/debian-stable binary/" \
  | sudo tee /etc/apt/sources.list.d/jenkins.list > /dev/null
sudo apt update && sudo apt install -y jenkins
sudo systemctl enable --now jenkins
sudo cat /var/lib/jenkins/secrets/initialAdminPassword
```

:::tip Si `apt update` se plaint d'une clé (NO_PUBKEY)
Le projet Jenkins renouvelle régulièrement sa clé de signature. Va sur `https://pkg.jenkins.io/debian-stable/` : la page indique le nom exact du fichier de clé en vigueur. Remplace `jenkins.io-2023.key` en conséquence.
:::

**1.3 — Premier démarrage.** Ouvre `http://<IP_JENKINS>:8080`, colle le mot de passe initial, choisis **Install suggested plugins**, crée ton utilisateur admin (mot de passe fort), garde l'URL proposée.

**1.4 — Plugins supplémentaires.** *Manage Jenkins → Plugins → Available plugins* : installe **GitHub Integration** (ou *GitHub*), **Pipeline: Stage View**, **SSH Agent**. *(Maven est utilisé via `sh`, pas besoin du plugin Maven Integration pour un pipeline.)*

**1.5 — Déclarer Maven.** *Manage Jenkins → Tools → Maven installations → Add Maven* : nom **`maven3`**, coche *Install automatically* (dernière version 3.9.x). Jenkins téléchargera Maven tout seul au premier build. *(Le tutoriel d'origine installe Maven à la main dans `/opt` et configure `JAVA_HOME`, `M2`, `M2_HOME` dans `.bash_profile` : c'est possible, mais l'installation automatique est plus simple et reproductible.)*

De même, *JDK installations* → nom **`jdk21`**, `JAVA_HOME` = `/usr/lib/jvm/java-21-openjdk-amd64`.

## Étape 2 — L'hôte Docker

**2.1 — Lancer l'instance.** Ubuntu 24.04, `t3.micro`, nom `dockerhost`, SG `dockerhost-sg` : **22** depuis My IP **et depuis le SG `jenkins-sg`**, **8081–9000** depuis My IP.

**2.2 — Installer Docker et créer l'utilisateur de déploiement.**

```bash
ssh -i ~/.ssh/io-key.pem ubuntu@<IP_DOCKERHOST>
sudo hostnamectl set-hostname dockerhost
sudo apt update && sudo apt install -y docker.io
sudo systemctl enable --now docker

sudo useradd -m -s /bin/bash dockeradmin
sudo usermod -aG docker dockeradmin          # peut utiliser docker sans sudo
sudo mkdir -p /opt/docker && sudo chown dockeradmin:dockeradmin /opt/docker
```

**2.3 — Comprendre Tomcat en conteneur** (l'étape « manuelle » du tutoriel, très formatrice) :

```bash
sudo docker run -d --name tomcat-test -p 8081:8080 tomcat:9.0-jdk17
curl -I http://localhost:8081      # 404 : webapps est vide dans l'image officielle !
sudo docker exec -it tomcat-test bash
  ls /usr/local/tomcat/webapps          # vide
  ls /usr/local/tomcat/webapps.dist     # les applications par défaut sont ici
  cp -R webapps.dist/* webapps/ && exit
curl -I http://localhost:8081      # 200 : la page d'accueil de Tomcat s'affiche
sudo docker rm -f tomcat-test
```

:::why Pourquoi la correction disparaît si on recrée le conteneur
Le `cp` a été fait **dans le conteneur**, pas dans l'**image**. Un nouveau conteneur repart de l'image d'origine, sans ta modification. La seule façon durable de modifier un conteneur, c'est de **construire une nouvelle image** avec un Dockerfile. C'est le principe de l'**immuabilité** : on ne modifie jamais un conteneur qui tourne, on en déploie un nouveau.
:::

**2.4 — Le Dockerfile de l'application.** Il sera envoyé par Jenkins avec le `.war`, donc il vit **dans le dépôt Git** :

```dockerfile
FROM tomcat:9.0-jdk17
# webapps est vide dans l'image officielle : on y remet les applications par défaut (optionnel)
RUN cp -R /usr/local/tomcat/webapps.dist/* /usr/local/tomcat/webapps
# Déployer notre application
COPY ./*.war /usr/local/tomcat/webapps/
```

## Étape 3 — Préparer le dépôt GitHub

```bash
cd ~ && git clone git@github.com:<toi>/regapp.git   # crée d'abord le dépôt vide "regapp" sur GitHub
cp -r /tmp/dp/DevOps-Project-05/hello-world/* regapp/ && cd regapp
```

**Mettre à jour le `pom.xml` racine.** Il compile pour Java 1.7 avec un plugin de 2010 : refusé par les JDK récents. Dans le bloc `maven-compiler-plugin` du `<build><plugins>` :

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <version>3.13.0</version>
  <configuration>
    <release>8</release>
  </configuration>
</plugin>
```

*(Supprime aussi la version `2.3.2` du même plugin plus bas dans le fichier, dans la section `reporting`, si elle crée un conflit.)* Vérifie en local si tu as Maven : `mvn -B clean package` doit produire `webapp/target/webapp.war`.

Ajoute le `Dockerfile` de l'étape 2.4 à la racine, puis le **Jenkinsfile** :

```groovy
pipeline {
    agent any
    tools {
        jdk 'jdk21'
        maven 'maven3'
    }
    environment {
        DOCKER_HOST_IP = '<IP_PRIVEE_DU_DOCKERHOST>'
        DEPLOY_DIR     = '/opt/docker'
    }
    triggers {
        githubPush()          // déclenché par le webhook GitHub
    }
    stages {
        stage('Build') {
            steps {
                sh 'mvn -B clean package'
            }
        }
        stage('Copier vers l\'hôte Docker') {
            steps {
                sshagent(credentials: ['dockerhost-ssh']) {
                    sh '''
                      scp -o StrictHostKeyChecking=no webapp/target/*.war Dockerfile \
                          dockeradmin@$DOCKER_HOST_IP:$DEPLOY_DIR/
                    '''
                }
            }
        }
        stage('Construire et lancer le conteneur') {
            steps {
                sshagent(credentials: ['dockerhost-ssh']) {
                    sh '''
                      ssh -o StrictHostKeyChecking=no dockeradmin@$DOCKER_HOST_IP "
                        cd $DEPLOY_DIR &&
                        docker build -t regapp:$BUILD_NUMBER . &&
                        docker rm -f registerapp || true &&
                        docker run -d --name registerapp -p 8087:8080 regapp:$BUILD_NUMBER
                      "
                    '''
                }
            }
        }
    }
    post {
        success { echo "Application : http://<IP_PUBLIQUE_DOCKERHOST>:8087/webapp/" }
    }
}
```

```bash
git add . && git commit -m "Pipeline Jenkins : build Maven + déploiement Docker" && git push
```

:::why `docker rm -f registerapp || true`
Le tutoriel d'origine se contente de `docker run -d --name registerapp …`. Ça marche **une fois** : au deuxième build, Docker refuse (`Conflict. The container name "/registerapp" is already in use`) et le pipeline échoue. Il faut d'abord supprimer l'ancien conteneur. `|| true` évite l'échec au tout premier déploiement, quand le conteneur n'existe pas encore. **Un déploiement automatisé doit fonctionner à la 1ʳᵉ comme à la 100ᵉ exécution.**
:::

:::why Taguer l'image avec `$BUILD_NUMBER`
Chaque build produit `regapp:1`, `regapp:2`, `regapp:3`… On sait exactement quelle version tourne, et revenir en arrière consiste à relancer l'image précédente. Avec `regapp:v1` toujours identique, on écrase l'historique.
:::

## Étape 4 — La clé SSH Jenkins → hôte Docker

```bash
# Sur le serveur Jenkins : générer une paire de clés dédiée
ssh-keygen -t ed25519 -f ~/dockerhost_deploy -N "" -C "jenkins-deploy"
cat ~/dockerhost_deploy.pub       # copie cette ligne
```

```bash
# Sur l'hôte Docker : l'autoriser pour dockeradmin
sudo -u dockeradmin mkdir -p /home/dockeradmin/.ssh
echo "<la ligne copiée>" | sudo -u dockeradmin tee -a /home/dockeradmin/.ssh/authorized_keys
sudo chmod 700 /home/dockeradmin/.ssh && sudo chmod 600 /home/dockeradmin/.ssh/authorized_keys
```

Dans Jenkins : *Manage Jenkins → Credentials → System → Global credentials → Add credentials* :
- *Kind* : **SSH Username with private key** ; *ID* : **`dockerhost-ssh`** ; *Username* : `dockeradmin` ;
- *Private Key* : *Enter directly* → colle le contenu de `~/dockerhost_deploy` (la clé **privée**).

Puis **supprime** les fichiers de clé du disque du serveur Jenkins : `rm ~/dockerhost_deploy*`. Elle est désormais chiffrée dans Jenkins.

## Étape 5 — Le job et le webhook

**5.1 — Créer le job.** *New Item* → nom `regapp-pipeline` → **Pipeline** → OK. Section *Pipeline* : *Definition* **Pipeline script from SCM** → SCM **Git** → URL `https://github.com/<toi>/regapp.git` (dépôt public : pas de credentials ; sinon un jeton GitHub) → branche `*/main` → *Script Path* `Jenkinsfile` → **Save**. Lance une première fois **Build Now** (nécessaire pour que Jenkins lise le Jenkinsfile et enregistre le trigger).

**5.2 — Le webhook.** Sur GitHub : dépôt → *Settings → Webhooks → Add webhook* :
- *Payload URL* : `http://<IP_PUBLIQUE_JENKINS>:8080/github-webhook/` (le `/` final est obligatoire) ;
- *Content type* : `application/json` ; événement : *Just the push event*.

GitHub envoie un ping : une coche verte doit apparaître à côté du webhook.

:::tip Si le webhook est impossible
Remplace `githubPush()` par `pollSCM('H/2 * * * *')` dans le Jenkinsfile : Jenkins interroge GitHub toutes les 2 minutes. C'est le « Poll SCM » du tutoriel d'origine. Moins réactif, mais ça marche même si Jenkins n'est pas joignable depuis Internet.
:::

## Étape 6 — Le test de bout en bout

Modifie `webapp/src/main/webapp/index.jsp` (change le titre), puis `git commit -am "Nouveau titre" && git push`.

:::check
- Dans Jenkins, un build démarre seul en quelques secondes ; la vue *Stage View* montre les 3 étapes au vert.
- Sur l'hôte Docker : `docker ps` montre `registerapp` basé sur `regapp:<numéro du build>` ; `docker images` liste les versions successives.
- `http://<IP_PUBLIQUE_DOCKERHOST>:8087/webapp/` affiche ta page modifiée.
:::

## Dépannage

:::fix
- **`Permission denied (publickey)` à l'étape scp** : la clé publique n'est pas dans `authorized_keys` de `dockeradmin`, mauvais ID de credential, ou permissions trop larges sur `.ssh`.
- **`Connection timed out` à l'étape scp** : le SG `dockerhost-sg` n'autorise pas le port 22 depuis `jenkins-sg`, ou tu as mis l'IP publique au lieu de l'IP privée (les deux instances sont dans le même VPC : utilise l'IP **privée**).
- **`permission denied while trying to connect to the Docker daemon socket`** : `dockeradmin` n'est pas dans le groupe `docker`, ou la session a été ouverte avant l'ajout.
- **`Source option 7 is no longer supported`** : le `pom.xml` n'a pas été mis à jour (étape 3).
- **Le webhook a une croix rouge** : Jenkins n'est pas joignable depuis Internet (SG), ou l'URL ne se termine pas par `/github-webhook/`. GitHub affiche la réponse reçue dans *Recent Deliveries*.
- **Jenkins très lent, ou le build s'arrête sans raison** : manque de mémoire. Ajoute 2 Go de swap (`sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile`) ou passe en `t3.medium`.
:::

## Nettoyage

:::clean
1. Supprime le webhook GitHub (sinon GitHub enverra des requêtes en échec).
2. *Terminate* les instances `jenkins` et `dockerhost`.
3. Supprime les Security Groups `jenkins-sg` et `dockerhost-sg`.
4. Garde le dépôt `regapp` : il resservira.
:::

## Pour aller plus loin

- Pousse l'image dans **Docker Hub** ou **ECR** au lieu de la construire sur l'hôte de déploiement : « construire une fois, déployer partout » (c'est la démarche des projets suivants).
- Ajoute une étape `mvn test` séparée et publie les rapports JUnit (`junit '**/target/surefire-reports/*.xml'`).
- Remplace l'hôte Docker par un déploiement Kubernetes : les fichiers `regapp-deploy.yml` et `regapp-service.yml` du dépôt d'origine sont prêts (projet 16).
- Mets Jenkins derrière un reverse proxy Nginx avec HTTPS.
