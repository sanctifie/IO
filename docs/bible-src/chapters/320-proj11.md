## Ce qu'on construit

Une architecture web **2-tiers** (serveurs web + base de données) complète, sécurisée et scalable, **entièrement décrite en Terraform** et découpée en modules.

```ascii
 Utilisateur ──► Route 53 (DNS) ──► CloudFront (CDN, HTTPS via ACM) ──► WAF (pare-feu applicatif)
                                              │
                                              ▼
 VPC 10.0.0.0/16   ┌────────── ALB (subnets publics 10.0.1.0/24, 10.0.2.0/24) ─────────────┐
                   │                                                                       │
                   │   Auto Scaling Group (min 2, max 4) : EC2 Ubuntu + Apache (deploy.sh) │
                   │   NAT Gateway par AZ                                                  │
                   └───────────────────────────────┬───────────────────────────────────────┘
                                                   │ 3306
                     RDS MySQL (subnets privés 10.0.3.0/24, 10.0.4.0/24)
 IAM : rôle SSM pour les instances          État Terraform : S3 + verrou
```

| Module | Contenu |
|---|---|
| `aws-vpc` | VPC, IGW, 2 subnets publics, 2 privés, 2 EIP, 2 NAT Gateways, 4 tables de routage |
| `security-group` | SG de l'ALB (80/443 depuis Internet), du web (80 depuis l'ALB), de la DB (3306 depuis le web) |
| `aws-rds` | subnet group + instance MySQL |
| `alb-tg` | Application Load Balancer, target group, listener |
| `aws-iam` | rôle, politique et instance profile pour SSM |
| `aws-autoscaling` | Launch Template (Ubuntu, user data `deploy.sh`), ASG, politiques de scaling + alarmes CPU |
| `aws-waf-cdn-acm-route53` | certificat ACM, distribution CloudFront, Web ACL WAF, enregistrements Route 53 |

## Étape 1 — Récupérer et lire le code

```bash
cd ~/IO/projects && mkdir 11-terraform-2tier && cd 11-terraform-2tier
cp -r /tmp/dp/DevOps-Project-11/* .
tree -L 2
```

**Lis chaque module avant de lancer quoi que ce soit.** Pour chaque fichier, identifie : les `variable` (entrées), les `resource` (ce qui est créé), les `data` (ce qui est lu), les `output`. Ce travail de lecture est exactement ce que tu feras en entreprise en arrivant sur un projet existant.

:::warn Trois pièges dans le code d'origine
1. **Les chemins des modules.** `main.tf` appelle `source = "../modules/aws-vpc"` et `deploy.sh` est chargé avec `filebase64("../modules/…")`. Ces chemins sont relatifs **au dossier où l'on lance Terraform**. Ils supposent que `main.tf` est dans un **sous-dossier** (par exemple `main/`). Avec la structure du dépôt (tout à la racine), `terraform init` échoue avec `Unreadable module directory`. Solution : crée un dossier `main/` et déplaces-y `main.tf`, `variables.tf`, `backend.tf` et `variables.tfvars`. Tu lanceras Terraform depuis `main/`.
2. **Le mot de passe de la base** est en clair dans `variables.tfvars` (`RDS-PWD = "Admin1234"`). Retire-le du fichier et fournis-le autrement (étape 3).
3. **Les modules se trouvent mutuellement par leurs tags** (`data "aws_subnet"` avec un filtre `tag:Name`) et enchaînent des `depends_on`. Ça marche, mais c'est fragile. La bonne pratique est de **passer les sorties d'un module en entrée du suivant** (`subnet_id = module.vpc.public_subnet_ids[0]`). Bon exercice de refactoring une fois que tout fonctionne.
:::

## Étape 2 — Préparer le backend (état distant)

`backend.tf` stocke l'état dans S3 avec une table DynamoDB pour le verrou. Mets à jour avec **ton** bucket, et modernise le verrou :

```hcl
terraform {
  backend "s3" {
    bucket       = "io-tfstate-<prenom>"            # bucket créé à la leçon 10
    key          = "projet-11/terraform.tfstate"
    region       = "eu-west-3"
    encrypt      = true
    use_lockfile = true                             # remplace dynamodb_table (Terraform >= 1.10)
  }
  required_version = ">= 1.10"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}
```

*(Si tu préfères garder `dynamodb_table = "Lock-Files"` comme l'original : crée la table `aws dynamodb create-table --table-name Lock-Files --attribute-definitions AttributeName=LockID,AttributeType=S --key-schema AttributeName=LockID,KeyType=HASH --billing-mode PAY_PER_REQUEST`.)*

Vérifie aussi le bloc `provider "aws"` (région). **Attention** : pour CloudFront, le certificat ACM et la Web ACL WAF doivent être créés en **`us-east-1`** (exigence d'AWS pour les services « globaux »). Regarde comment le module `aws-waf-cdn-acm-route53` gère la région ; le plus simple pour ce projet est de tout déployer en `us-east-1`.

## Étape 3 — Les variables

Ouvre `variables.tfvars` et adapte : noms, CIDR (garde-les), **domaine** (`DOMAIN-NAME`). Puis le mot de passe :

Terraform lit automatiquement toute variable d'environnement `TF_VAR_<nom>` comme valeur de la variable `<nom>`. Problème : la variable s'appelle `RDS-PWD`, et Bash n'accepte pas de tiret dans un nom de variable d'environnement. Renomme-la donc **`RDS_PWD`** (dans `variables.tf`, dans l'appel du module dans `main.tf`) et ajoute `sensitive = true` à sa déclaration pour qu'elle n'apparaisse jamais dans les sorties de `plan` :

```hcl
variable "RDS_PWD" {
  type      = string
  sensitive = true
}
```

```bash
# Jamais dans un fichier commité : saisie masquée, puis variable d'environnement
read -s TF_VAR_RDS_PWD && export TF_VAR_RDS_PWD
```

:::info Pas de nom de domaine ?
Les modules ACM, CloudFront et Route 53 exigent un domaine que tu contrôles (un `.com` coûte ~15 $/an dans Route 53, et la *hosted zone* 0,50 $/mois). Sans domaine, **commente le bloc `module "route53"`** dans `main.tf` : tu auras toute l'architecture sauf la couche CDN/DNS, et tu accéderas au site par le nom DNS de l'ALB.
:::

## Étape 4 — Init, plan, apply

```bash
cd main
terraform init                                      # télécharge le provider, initialise le backend S3
terraform fmt -recursive ..                         # formatage
terraform validate
terraform plan  -var-file=variables.tfvars -out=plan.tfplan
terraform apply plan.tfplan
```

:::why `-out=plan.tfplan`
Sauvegarder le plan puis appliquer **ce fichier** garantit que ce qui est appliqué est exactement ce que tu as relu, même si quelque chose a changé entre-temps. C'est la pratique standard en CI (le plan est relu sur la pull request, puis appliqué tel quel).
:::

Lis le plan : combien de ressources ? Repère les NAT Gateways, l'instance RDS, la distribution CloudFront. L'`apply` prend **15 à 25 minutes** (RDS et CloudFront sont les plus lents).

## Étape 6 — Comprendre les briques « edge »

:::why CloudFront, WAF et ACM
- **CloudFront** est le **CDN** d'AWS : des centaines de points de présence dans le monde gardent une copie des contenus et servent les utilisateurs au plus près, ce qui réduit la latence et la charge des serveurs.
- **ACM** (*Certificate Manager*) fournit gratuitement des certificats TLS, renouvelés automatiquement. La validation se fait par un enregistrement DNS (créé ici automatiquement dans Route 53).
- **WAF** (*Web Application Firewall*) filtre les requêtes HTTP : injections SQL, XSS, robots, limitation de débit par IP… grâce à des règles gérées par AWS (*AWS Managed Rules*).
- **Route 53** fait pointer ton domaine vers CloudFront avec un enregistrement **Alias**.
:::

## Dépannage

:::fix
- **`Unreadable module directory`** : voir le piège n°1 (chemins relatifs).
- **`Error acquiring the state lock`** : un `apply` précédent a été interrompu. Vérifie qu'aucun autre n'est en cours, puis `terraform force-unlock <LOCK_ID>`.
- **`InvalidParameterValue: … password`** pour RDS : le mot de passe ne respecte pas les règles (8 caractères minimum, sans `/`, `"`, `@`, espace).
- **ACM reste en `Pending validation`** : la zone Route 53 n'est pas celle qui fait autorité pour ton domaine (vérifie les serveurs de noms chez ton registrar).
- **`WAFUnavailableEntityException` / certificat introuvable pour CloudFront** : la Web ACL ou le certificat ne sont pas en `us-east-1`.
- **L'ASG crée des instances qui ne deviennent jamais healthy** : `deploy.sh` a échoué. Session Manager → `sudo cat /var/log/cloud-init-output.log`.
:::

## Nettoyage

:::clean
```bash
cd main
terraform destroy -var-file=variables.tfvars
```
Vérifie ensuite dans la console : NAT Gateways et Elastic IPs (supprimées ?), snapshots RDS finaux éventuels, distribution CloudFront (sa suppression peut prendre 15 minutes). Garde le bucket d'état et la *hosted zone* si tu as un domaine.
:::
