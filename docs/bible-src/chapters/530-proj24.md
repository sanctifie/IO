## Ce qu'on construit

Une application **ASP.NET Core** qui affiche en temps réel les métriques de la machine où elle tourne (CPU, mémoire, informations système), livrée par le même type de pipeline DevSecOps que le projet 09 :

```ascii
 GitHub ──► Jenkins : clean → checkout → SonarQube → Quality Gate → Trivy fs → OWASP DC
                       → make image (docker build) → Trivy image → make push (Docker Hub)
                       → docker run :5000 → (Kubernetes : kubectl apply K8S/deployment.yaml, NodePort)
```

La nouveauté : le pipeline appelle un **Makefile** (`make image`, `make push`) au lieu de commandes `docker` directes.

## Les concepts

:::why Le Makefile comme interface commune
Ouvre `DotNet-monitoring/makefile` : il définit des **cibles** (`lint`, `image`, `push`, `run`, `test`, `deploy`…) avec des variables surchargeables :

```makefile
IMAGE_REG  ?= docker.io
IMAGE_REPO ?= writetoritika/dotnet-monitoring
IMAGE_TAG  ?= latest

image: ## 🔨 Build container image from Dockerfile
	docker build . --file build/Dockerfile --tag $(IMAGE_REG)/$(IMAGE_REPO):$(IMAGE_TAG)
```

Le même `make image` fonctionne sur le poste du développeur **et** dans le pipeline : la logique de build est écrite **une seule fois**, dans le dépôt, et le pipeline reste simple. `?=` signifie « valeur par défaut, sauf si on en fournit une » : `make image IMAGE_REPO=moi/dotnet-monitoring IMAGE_TAG=42`. Tape `make help` pour voir les cibles documentées.
:::

## Étape 1 — Préparer le dépôt

:::warn L'URL Git du tutoriel ne fonctionne pas
Le Jenkinsfile d'origine fait `git url: 'https://github.com/devcloudninjas/DevOps-Projects/tree/master/DevOps-Project-24/DotNet-monitoring'`. **On ne peut pas cloner un sous-dossier** d'un dépôt GitHub avec cette URL (`/tree/...` est une page web, pas un dépôt Git). Il faut un dépôt dont l'application est **à la racine**.
:::

```bash
mkdir dotnet-monitoring && cp -r /tmp/dp/DevOps-Project-24/DotNet-monitoring/. dotnet-monitoring/
cd dotnet-monitoring && git init && git add . && git commit -m "Application DotNet-monitoring"
git branch -M main
git remote add origin git@github.com:<toi>/dotnet-monitoring.git && git push -u origin main
```

Dans le `makefile`, remplace `IMAGE_REPO ?= writetoritika/dotnet-monitoring` par **ton** pseudo Docker Hub. Dans `K8S/deployment.yaml`, l'image aussi.

## Étape 3 — Le pipeline

```groovy
pipeline {
    agent any
    tools { jdk 'jdk17' }
    environment {
        SCANNER_HOME = tool 'sonar-scanner'
        IMAGE_REPO   = '<toi-dockerhub>/dotnet-monitoring'
    }
    stages {
        stage('Clean workspace') { steps { cleanWs() } }
        stage('Checkout') {
            steps { git branch: 'main', url: 'https://github.com/<toi>/dotnet-monitoring.git' }
        }
        stage('Analyse SonarQube') {
            steps {
                withSonarQubeEnv('sonar-server') {
                    sh '$SCANNER_HOME/bin/sonar-scanner -Dsonar.projectName=Dotnet-Webapp -Dsonar.projectKey=Dotnet-Webapp'
                }
            }
        }
        stage('Quality Gate') {
            steps { script { waitForQualityGate abortPipeline: false, credentialsId: 'Sonar-token' } }
        }
        stage('Trivy FS') { steps { sh 'trivy fs . > trivy-fs_report.txt' } }
        stage('OWASP Dependency-Check') {
            steps {
                withCredentials([string(credentialsId: 'nvd-api-key', variable: 'NVD_KEY')]) {
                    dependencyCheck additionalArguments: "--scan ./ --format XML --nvdApiKey ${NVD_KEY}", odcInstallation: 'DP-Check'
                }
                dependencyCheckPublisher pattern: '**/dependency-check-report.xml'
            }
        }
        stage('Image Docker') {
            steps {
                script {
                    withDockerRegistry(credentialsId: 'docker', toolName: 'docker') {
                        sh 'make image IMAGE_REPO=$IMAGE_REPO IMAGE_TAG=$BUILD_NUMBER'
                    }
                }
            }
        }
        stage('Trivy image') {
            steps { sh 'trivy image docker.io/$IMAGE_REPO:$BUILD_NUMBER > trivy.txt' }
        }
        stage('Push') {
            steps {
                script {
                    withDockerRegistry(credentialsId: 'docker', toolName: 'docker') {
                        sh 'make push IMAGE_REPO=$IMAGE_REPO IMAGE_TAG=$BUILD_NUMBER'
                    }
                }
            }
        }
        stage('Déployer en conteneur') {
            steps {
                sh '''
                  docker rm -f dotnet || true
                  docker run -d --name dotnet -p 5000:5000 docker.io/$IMAGE_REPO:$BUILD_NUMBER
                '''
            }
        }
    }
}
```

:::warn Les noms d'images Docker sont en minuscules
Le tutoriel utilise `NotHarshhaa/dotnet-monitoring` : Docker **refuse** les majuscules dans un nom de dépôt (`invalid reference format: repository name must be lowercase`). Ton pseudo Docker Hub est toujours en minuscules dans les noms d'images.
:::

:::check
- `http://<IP>:5000` : l'application affiche les informations et la charge CPU/mémoire **du conteneur**. Lance une charge (`docker exec dotnet sh -c "yes > /dev/null &"`) et observe la courbe monter.
- SonarQube : projet *Dotnet-Webapp* ; Jenkins : graphique Dependency-Check.
- Docker Hub : `dotnet-monitoring:<numéro de build>`.
:::

## Étape 4 — Kubernetes

1. Cluster kubeadm master + worker (**annexe A.6**), comme au projet 09.
2. `K8S/deployment.yaml` contient un Deployment (port 5000) et un Service **NodePort** (port 80 → 5000, NodePort attribué automatiquement).
3. Ajoute le credential kubeconfig (*Secret file* `k8s`) et le stage :

```groovy
stage('Déployer sur Kubernetes') {
    steps {
        withKubeConfig(credentialsId: 'k8s') {
            sh 'kubectl apply -f K8S/deployment.yaml'
            sh 'kubectl set image deployment/dotnet-app-deployment dotnet-app=docker.io/$IMAGE_REPO:$BUILD_NUMBER'
            sh 'kubectl rollout status deployment/dotnet-app-deployment --timeout=120s'
        }
    }
}
```

```bash
kubectl get svc dotnet-app-service      # repère le NodePort (30000-32767)
```

Ouvre `http://<IP_WORKER>:<NodePort>` (pense au Security Group).

:::why `kubectl set image` après `apply`
Le fichier YAML contient l'image `…:latest`. Avec `kubectl apply` seul, Kubernetes ne voit **aucun changement** d'un build à l'autre (le texte est identique) et ne redéploie pas, même si l'image `latest` a changé sur Docker Hub. `kubectl set image` avec le numéro de build modifie réellement le Deployment et déclenche un rolling update traçable. C'est une raison de plus pour ne jamais déployer `latest`.
:::

## Dépannage

:::fix
- **`make: command not found`** dans Jenkins : `sudo apt install make`.
- **`invalid reference format`** : majuscules dans le nom d'image.
- **SonarQube analyse peu de choses** : pour une analyse C# complète, SonarQube recommande le *SonarScanner for .NET* (`dotnet sonarscanner begin/end` autour d'un `dotnet build`). Le scanner générique utilisé ici analyse surtout les fichiers non compilés. Bonne piste d'amélioration.
- **Port 5000 injoignable** : Security Group, ou l'application écoute sur un autre port (vérifie `EXPOSE` dans `build/Dockerfile` et `docker logs dotnet`).
:::

:::clean
*Terminate* les instances (Jenkins, master, worker), SG, volumes.
:::
