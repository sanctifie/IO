## Ce qu'on construit

Le même type de pipeline AWS que le projet 21, mais avec une stratégie de déploiement **sans interruption** et **avec retour arrière instantané** : le **blue/green**.

```ascii
 GitHub ──► CodePipeline
             ├─ Source  (CodeConnections)
             ├─ Build   CodeBuild : SonarQube + Trivy fs + docker build + push ECR + Trivy image
             │          artefacts : taskdef.json, appspec.yaml, imageDetail.json
             └─ Deploy  CodeDeploy « Amazon ECS (Blue/Green) »
                                   │
         ┌─────────────────────────┴─────────────────────────────┐
         │ ALB  listener :80  ───────► TG-1 (BLEU : version actuelle, tâches v1)
         │                     (bascule)
         │                     ───────► TG-2 (VERT : nouvelle version, tâches v2)
         └───────────────────────────────────────────────────────┘
   1. CodeDeploy démarre les tâches v2 dans TG-2 (sans trafic)
   2. Les health checks passent → le listener bascule de TG-1 vers TG-2
   3. Les tâches v1 restent un moment (retour arrière possible), puis sont arrêtées
```

## Les concepts

:::why Le déploiement blue/green
Deux environnements identiques : **bleu** (la version en production) et **vert** (la nouvelle version). On déploie la nouvelle version **à côté** de l'ancienne, on la teste, puis on **bascule le trafic** d'un coup (au niveau du load balancer). Si un problème apparaît, on rebascule vers le bleu en quelques secondes, sans redéployer.

Comparé au **rolling update** (projets 04, 08) où les anciennes instances sont remplacées progressivement : le blue/green coûte temporairement le double de ressources, mais offre un **retour arrière instantané** et aucun mélange de versions. Il existe aussi le **canary** : envoyer d'abord 10 % du trafic à la nouvelle version, puis augmenter si tout va bien (CodeDeploy le propose : `CodeDeployDefault.ECSCanary10Percent5Minutes`).
:::

:::why Les trois fichiers d'un déploiement ECS blue/green
L'action *Amazon ECS (Blue/Green)* de CodePipeline attend dans l'artefact :
- **`taskdef.json`** : la task definition, avec un **marqueur** `<IMAGE1_NAME>` à la place de l'image ;
- **`appspec.yaml`** : indique à CodeDeploy quel conteneur et quel port enregistrer dans le load balancer, avec un marqueur `<TASK_DEFINITION>` ;
- **`imageDetail.json`** : produit par le build, contient l'URI de l'image qui vient d'être poussée (`{"ImageURI": "…:42"}`).

CodePipeline remplace les marqueurs, enregistre une **nouvelle révision** de la task definition et la passe à CodeDeploy. Le `appspec.yaml` du dépôt d'origine contient un ARN de task definition **codé en dur** (`…task-definition/swiggy:1`) : chaque déploiement redéploierait la révision 1, jamais la nouvelle image. On corrige ça.
:::

## Étape 1 — Le serveur SonarQube

EC2 Ubuntu `t3.medium`, port 9000 ouvert **depuis Internet** (CodeBuild tourne hors de ton VPC par défaut et doit le joindre — à restreindre en production en plaçant CodeBuild dans ton VPC). Installe Docker et lance SonarQube (projet 09, étape 2). Crée un projet `swiggy` et un **token**.

## Étape 2 — Le code et les paramètres

1. Dépôt GitHub `swiggy-clone` avec le contenu de `DevOps-Project-23/Swiggy_clone`.
2. Dépôt **ECR** : `aws ecr create-repository --repository-name swiggy --image-scanning-configuration scanOnPush=true`.
3. Paramètres SSM :

```bash
aws ssm put-parameter --name /cicd/sonar/sonar-token --type SecureString --value '<token-sonar>'
aws ssm put-parameter --name /cicd/sonar/url         --type String       --value 'http://<IP_SONAR>:9000'
```

4. **Dockerfile** : celui d'origine lance `npm start` (serveur de développement, port 3000). Garde-le pour coller au projet (le port 3000 est utilisé partout), ou applique le Dockerfile durci du projet 13 (et adapte le port à 8080 dans la task definition et l'`appspec.yaml`).

## Étape 3 — Le `buildspec.yaml`, réécrit

Le `buildspec.yaml` d'origine est **presque entièrement commenté** (rien n'est construit) et son bloc `post_build` est mal indenté (hors de `phases`). Voici une version fonctionnelle :

```yaml
version: 0.2

env:
  parameter-store:
    SONAR_TOKEN: /cicd/sonar/sonar-token
    SONAR_URL:   /cicd/sonar/url
  variables:
    REPO_NAME: swiggy

phases:
  install:
    runtime-versions:
      nodejs: 20
      java: corretto17
    commands:
      - curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh -s -- -b /usr/local/bin
      - npm install -g sonarqube-scanner
  pre_build:
    commands:
      - ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
      - REGISTRY=$ACCOUNT_ID.dkr.ecr.$AWS_DEFAULT_REGION.amazonaws.com
      - IMAGE_URI=$REGISTRY/$REPO_NAME:$CODEBUILD_RESOLVED_SOURCE_VERSION
      - aws ecr get-login-password | docker login --username AWS --password-stdin $REGISTRY
      - echo "Analyse SonarQube"
      - sonar-scanner -Dsonar.projectKey=swiggy -Dsonar.sources=src -Dsonar.host.url=$SONAR_URL -Dsonar.token=$SONAR_TOKEN
      - echo "Scan Trivy du code"
      - trivy fs --format table -o trivyfs.txt .
  build:
    commands:
      - docker build -t $IMAGE_URI .
      - trivy image --format table -o trivyimage.txt $IMAGE_URI
      - trivy image --severity CRITICAL --exit-code 1 --ignore-unfixed $IMAGE_URI    # bloque si CRITICAL corrigeable
  post_build:
    commands:
      - docker push $IMAGE_URI
      - printf '{"ImageURI":"%s"}' $IMAGE_URI > imageDetail.json

artifacts:
  files:
    - appspec.yaml
    - taskdef.json
    - imageDetail.json

reports:                                  # rapports consultables dans la console CodeBuild
  security:
    files: [trivyfs.txt, trivyimage.txt]
    file-format: CUCUMBERJSON             # (format indicatif ; sinon publier les fichiers dans S3)
```

:::why `$CODEBUILD_RESOLVED_SOURCE_VERSION`
C'est le **hash du commit** construit. Utilisé comme tag d'image, il relie chaque image à un commit précis : on sait toujours exactement quel code tourne en production. C'est bien plus traçable que `latest`.
:::

*(La section `reports` attend des formats précis (JUnit, Cucumber…). Si elle pose problème, supprime-la et copie plutôt les rapports dans un bucket S3 en `post_build`.)*

Le rôle de service CodeBuild a besoin de : lire les paramètres SSM (`ssm:GetParameters` sur `/cicd/*`), pousser dans ECR (politique `AmazonEC2ContainerRegistryPowerUser`), et le **mode privilégié** activé (pour Docker). Le tutoriel donne `AmazonSSMFullAccess` et `AmazonS3FullAccess` : beaucoup trop large, limite aux ressources nécessaires.

## Étape 4 — `taskdef.json` et `appspec.yaml`

À la racine du dépôt, **`taskdef.json`** :

```json
{
  "family": "swiggy",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "512",
  "memory": "1024",
  "executionRoleArn": "arn:aws:iam::<compte>:role/ecsTaskExecutionRole",
  "containerDefinitions": [
    {
      "name": "swiggy",
      "image": "<IMAGE1_NAME>",
      "essential": true,
      "portMappings": [{ "containerPort": 3000, "protocol": "tcp" }],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/swiggy",
          "awslogs-region": "eu-west-3",
          "awslogs-stream-prefix": "swiggy",
          "awslogs-create-group": "true"
        }
      }
    }
  ]
}
```

Et **`appspec.yaml`** (remplace celui d'origine) :

```yaml
version: 0.0
Resources:
  - TargetService:
      Type: AWS::ECS::Service
      Properties:
        TaskDefinition: <TASK_DEFINITION>
        LoadBalancerInfo:
          ContainerName: "swiggy"
          ContainerPort: 3000
```

*(Le tutoriel utilise un cluster ECS en mode **EC2** avec des `t2.medium`. **Fargate** fonctionne de la même façon et évite de gérer des instances ; c'est ce que décrit le `taskdef.json` ci-dessus. Si tu préfères EC2, mets `"requiresCompatibilities": ["EC2"]` et `"networkMode": "awsvpc"` ou `"bridge"` selon ton cluster.)*

## Étape 5 — ALB, deux target groups, cluster et service

1. **Deux target groups** de type **IP** (Fargate), port 3000, VPC par défaut, health check `/` : `swiggy-tg-1` et `swiggy-tg-2`.
2. **ALB** `swiggy-alb` (Internet-facing, subnets publics, SG HTTP 80), listener **HTTP 80 → `swiggy-tg-1`**. *(Optionnel : un listener de test sur 8080 → `swiggy-tg-2`, pour tester la version verte avant bascule.)*
3. **Rôle CodeDeploy pour ECS** : IAM → *Create role* → *CodeDeploy* → cas d'usage **CodeDeploy - ECS** (politique `AWSCodeDeployRoleForECS`) → `io-23-codedeploy-ecs`.
4. **Cluster ECS** `swiggy-cluster` (Fargate).
5. **Enregistre une première task definition** à la main (remplace `<IMAGE1_NAME>` par une image existante, par exemple celle du premier build CodeBuild lancé à la main) : `aws ecs register-task-definition --cli-input-json file://taskdef-initial.json`.
6. **Service** : cluster → *Create service* → Fargate, task definition `swiggy`, 1 tâche → *Deployment options* : **Blue/green deployment (powered by AWS CodeDeploy)** → rôle `io-23-codedeploy-ecs` → *Load balancing* : ALB `swiggy-alb`, listener 80, **target group 1 : `swiggy-tg-1`**, **target group 2 : `swiggy-tg-2`** → SG des tâches : 3000 depuis le SG de l'ALB.

La création du service crée automatiquement une **application** et un **deployment group** dans CodeDeploy (`AppECS-swiggy-cluster-<service>`).

:::check
`http://<DNS-de-l'ALB>` affiche l'application ; l'onglet du navigateur s'appelle « Swiggy Application ». Dans EC2 → *Target groups*, `swiggy-tg-1` a une cible *healthy*, `swiggy-tg-2` aucune.
:::

## Étape 6 — Le pipeline

*CodePipeline → Create pipeline* :
- **Source** : GitHub via CodeConnections, branche `main`.
- **Build** : CodeBuild (le projet de l'étape 3).
- **Deploy** : fournisseur **Amazon ECS (Blue/Green)** → application et deployment group CodeDeploy créés à l'étape 5 → *Amazon ECS task definition* : `BuildArtifact`, fichier `taskdef.json` → *AWS CodeDeploy AppSpec file* : `BuildArtifact`, `appspec.yaml` → *Dynamically update task definition image* : `BuildArtifact`, marqueur **`IMAGE1_NAME`**.

## Étape 7 — Observer une bascule blue/green

Modifie un texte visible de l'application (par exemple le titre de `public/index.html`), commit, push. Suis le déploiement dans **CodeDeploy → Deployments** :

1. *Deploying replacement task set* : les tâches de la nouvelle version démarrent dans `swiggy-tg-2`.
2. *Rerouting production traffic* : le listener 80 pointe maintenant vers `swiggy-tg-2`.
3. *Wait* (durée configurable dans le deployment group, par défaut une heure → réduis-la à 5 minutes) : l'ancienne version reste disponible.
4. *Terminate original task set*.

Pendant l'attente, le bouton **Stop and roll back deployment** ramène instantanément le trafic vers l'ancienne version. Essaie-le une fois !

:::check
- Recharge `http://<DNS-ALB>` pendant le déploiement : aucune erreur, puis la nouvelle version apparaît d'un coup.
- Le listener 80 de l'ALB alterne entre TG-1 et TG-2 à chaque déploiement.
- ECR contient une image par commit ; les rapports Trivy et l'analyse SonarQube sont disponibles.
:::

## Étape 8 (optionnelle) — Notification

Le tutoriel envoie un e-mail via **SES** (`aws ses send-email`), ce qui exige de vérifier les adresses dans SES (et de sortir du *sandbox* pour écrire à d'autres adresses). Plus simple : une **règle de notification** sur le pipeline (*Settings → Notifications → Create notification rule*) vers un topic **SNS** auquel tu es abonné par e-mail, sur les événements *Failed* et *Succeeded*.

## Dépannage

:::fix
- **Le déploiement échoue avec « The ECS service cannot be updated due to an unexpected error »** : le service n'a pas été créé avec le contrôleur de déploiement **CODE_DEPLOY** (il faut le recréer, ce réglage ne se modifie pas).
- **`Invalid action configuration: … IMAGE1_NAME`** : le marqueur dans `taskdef.json` doit être exactement `<IMAGE1_NAME>` et le nom dans l'action `IMAGE1_NAME`.
- **Nouvelles tâches jamais saines** : SG des tâches (3000 depuis l'ALB), health check, ou l'application met longtemps à démarrer (`npm start` compile au démarrage : augmente le *health check grace period*).
- **CodeBuild : `sonar-scanner: Connection refused`** : SonarQube injoignable depuis CodeBuild (port 9000, IP publique).
- **CodeBuild : `exit status 1` au Trivy image** : c'est voulu, une faille CRITICAL corrigeable a été trouvée. Lis `trivyimage.txt`.
:::
