# Projet 28 — DevSecOps : déployer une interface de chatbot OpenAI sur EKS avec Jenkins et Terraform

:::card
| | |
|---|---|
| Niveau | ★★★★☆ Avancé |
| Durée | 6 à 10 heures |
| Coût | Jenkins `t3.large` + EKS + nœuds + load balancer : ~0,30 $/h. **Utilisation de l'API OpenAI facturée à part** (quelques centimes pour des tests) |
| Compétences | serveur Jenkins créé par Terraform, pipeline Terraform paramétré (apply/destroy) pour EKS, pipeline DevSecOps pour une application Next.js, déploiement sur EKS, gestion d'une clé d'API d'IA |
| Prérequis | Projets 09 et 19 (c'est la combinaison des deux) |
| Dépôt d'origine | `DevOps-Project-28/Chatbot-UI` : application Next.js (*Chatbot UI*), `EKS-TF/`, `JenkinsFile/EKS-Jenkinsfile`, `JenkinsFile/Chatbot-Jenkinsfile`, `k8s/chatbot-ui.yaml` |
:::

## Ce qu'on construit

Une interface web de type ChatGPT (projet open source *Chatbot UI*) qui envoie les conversations à l'**API d'OpenAI**, livrée par une chaîne DevSecOps complète :

```ascii
 1. Terraform (poste) ──► EC2 Jenkins + SonarQube + Trivy + Terraform + kubectl
 2. Job "eks-terraform" (paramètres : File-Name, Terraform-Action) ──► EKS (VPC, rôles, cluster, node group)
 3. Job "chatbot" : checkout → npm install → SonarQube → Quality Gate → OWASP DC → Trivy fs
                    → docker build/push (Docker Hub) → Trivy image → docker run :3000
                    → kubectl apply k8s/chatbot-ui.yaml ──► EKS : Deployment + Service LoadBalancer :80
                                                                ▼
                                                   navigateur ──► Chatbot UI ──► API OpenAI
```

## Ce qui est nouveau par rapport aux projets 09 et 19

1. **Deux pipelines** dans le même dépôt : un pour l'infrastructure (`EKS-Jenkinsfile`), un pour l'application (`Chatbot-Jenkinsfile`).
2. Le pipeline Terraform est **paramétré** avec la syntaxe `properties([parameters([...])])` (équivalent du bloc `parameters {}` déclaratif).
3. L'application a besoin d'une **clé d'API d'IA**, à gérer comme un vrai secret.

## Étape 1 — Le dépôt

:::warn Même piège qu'au projet 24
Les Jenkinsfiles font `git url: 'https://github.com/devcloudninjas/DevOps-Projects/DevOps-Project-28/Chatbot-UI.git'` : cette URL n'existe pas (on ne clone pas un sous-dossier). Copie le dossier `Chatbot-UI` à la racine d'un dépôt à toi :
```bash
mkdir chatbot-ui && cp -r /tmp/dp/DevOps-Project-28/Chatbot-UI/. chatbot-ui/ && cd chatbot-ui
git init && git add . && git commit -m "Chatbot UI" && git branch -M main
git remote add origin git@github.com:<toi>/chatbot-ui.git && git push -u origin main
```
:::

Dans `k8s/chatbot-ui.yaml`, remplace l'image `sreedhar8897/chatbot:latest` par `<toi-dockerhub>/chatbot:latest`.

## Étape 2 — Le serveur Jenkins

Comme au projet 19 (Terraform du serveur, ou instance à la main) : Ubuntu `t3.large` 30 Go, avec Jenkins, Docker, SonarQube (conteneur), Trivy, **Terraform**, **AWS CLI**, **kubectl**. Donne à l'instance un **rôle IAM** (plutôt que le credential `aws-key` d'access keys du tutoriel) : le plugin *Pipeline: AWS Steps* et les commandes `aws`/`terraform` utiliseront automatiquement le rôle.

Outils Jenkins : `jdk17`, **`node19`** dans le Jenkinsfile → déclare plutôt une LTS (`node20`) et adapte le nom ; `sonar-scanner`, `DP-Check`, `docker`. Credentials : `Sonar-token`, `docker`, `nvd-api-key`.

## Étape 3 — Le pipeline EKS

Lis `EKS-TF/` : `vpc.tf` (VPC, subnets publics, IGW), `iam-role.tf` et `iam-policy.tf` (rôles cluster et nœuds), `eks-cluster.tf`, `eks-node-group.tf`, `backend.tf`, `variables.tfvars`. Adapte le **backend** (ton bucket, ta région), la **région** et le **type d'instance** des nœuds (`t3.medium`), et assure-toi que l'identité de Jenkins sera administratrice du cluster (bloc `access_config` avec `bootstrap_cluster_creator_admin_permissions = true`, voir projet 12).

Job **`eks-terraform`** (Pipeline from SCM, *Script Path* `JenkinsFile/EKS-Jenkinsfile`). Avec le rôle IAM, supprime les blocs `withAWS(credentials: 'aws-key', …)` ou remplace-les par `withAWS(region: 'eu-west-3')`. Corrige l'URL Git.

```groovy
properties([
    parameters([
        string(defaultValue: 'variables.tfvars', description: 'Fichier de variables', name: 'File-Name'),
        choice(choices: ['apply', 'destroy'], description: 'Action Terraform', name: 'Terraform-Action')
    ])
])
// ... stages : init → validate → plan → (apply | destroy) selon params.'Terraform-Action'
```

:::tip Ajoute une validation humaine
Le pipeline d'origine fait `terraform apply -auto-approve` ou `destroy -auto-approve` sans relecture. Ajoute un `input(message: "Confirmer ${params.'Terraform-Action'} ?")` après le plan, comme au projet 19. Un `destroy` lancé par erreur sur un cluster de production est une catastrophe classique.
:::

*Build with Parameters* → `apply`. 15 minutes plus tard :

```bash
aws eks update-kubeconfig --name <nom-du-cluster> --region eu-west-3
kubectl get nodes
```

## Étape 4 — La clé d'API OpenAI

Crée une clé sur la plateforme OpenAI (*API keys*), avec une **limite de dépense** basse (*Billing → Limits*). L'application Chatbot UI lit la variable d'environnement **`OPENAI_API_KEY`** côté serveur (sinon, chaque utilisateur doit saisir sa propre clé dans l'interface).

:::danger Une clé d'IA est un secret qui coûte de l'argent
Une clé OpenAI fuitée peut être utilisée par d'autres **à tes frais**, très vite. Ne la mets jamais dans le dépôt, dans le Dockerfile, ni dans un manifest Kubernetes en clair. Stocke-la dans un **Secret Kubernetes** créé à la main (ou mieux, via AWS Secrets Manager + External Secrets Operator), et référence-le dans le Deployment.
:::

```bash
kubectl create secret generic openai --from-literal=OPENAI_API_KEY='sk-...'
```

Dans `k8s/chatbot-ui.yaml`, ajoute au conteneur :

```yaml
        env:
        - name: OPENAI_API_KEY
          valueFrom:
            secretKeyRef: { name: openai, key: OPENAI_API_KEY }
```

## Étape 5 — Le pipeline de l'application

Job **`chatbot`** (*Script Path* `JenkinsFile/Chatbot-Jenkinsfile`). Corrections à apporter au fichier d'origine :

| Ligne d'origine | Problème | Correction |
|---|---|---|
| `git … url: '…/DevOps-Project-28/Chatbot-UI.git'` | URL inexistante | ton dépôt, branche `main` |
| `docker tag chatbot NotHarshhaa/chatbot:latest` | majuscules interdites dans un nom d'image | `<toi-dockerhub>/chatbot:${BUILD_NUMBER}` |
| `sh "docker stop chatbot \| true"` | `\|` est un **pipe**, pas un « ou » : le résultat dépend du hasard | `docker rm -f chatbot \|\| true` |
| `dependencyCheck … ` sans clé NVD | très lent / échec | `--nvdApiKey` (leçon 14) |
| `withAWS(credentials: 'aws-key', …)` | clés d'accès stockées | rôle IAM de l'instance |
| `kubectl apply -f k8s/chatbot-ui.yaml` avec `:latest` | pas de redéploiement | `kubectl set image deployment/chatbot chatbot=<image>:${BUILD_NUMBER}` après l'apply |

Pour le déploiement Kubernetes, avec le rôle IAM et `aws eks update-kubeconfig` exécuté une fois sur le serveur (dans le `HOME` de l'utilisateur `jenkins` : `sudo -u jenkins aws eks update-kubeconfig …`), le stage devient simplement :

```groovy
stage('Déployer sur EKS') {
    steps {
        sh '''
          kubectl apply -f k8s/chatbot-ui.yaml
          kubectl set image deployment/chatbot chatbot=<toi-dockerhub>/chatbot:$BUILD_NUMBER
          kubectl rollout status deployment/chatbot --timeout=180s
        '''
    }
}
```

:::check
- `http://<IP_JENKINS>:3000` : l'interface tourne en conteneur sur le serveur Jenkins.
- `kubectl get svc chatbot-service` → EXTERNAL-IP → `http://<EXTERNAL-IP>` : la même interface servie par EKS. Pose une question : la réponse vient de l'API OpenAI.
- SonarQube, Dependency-Check, rapports Trivy disponibles.
:::

## Dépannage

:::fix
- **`npm install` très long ou en échec mémoire** : Next.js est gourmand ; `t3.large` minimum, ou ajoute du swap.
- **L'interface s'affiche mais les réponses échouent** : clé OpenAI absente/invalide, quota épuisé, ou le pod n'a pas la variable (`kubectl exec deploy/chatbot -- printenv | grep OPENAI`).
- **`error: You must be logged in to the server`** : l'utilisateur `jenkins` n'a pas de kubeconfig, ou son identité n'est pas autorisée dans le cluster.
- **`terraform destroy` bloqué sur le VPC** : supprime d'abord le Service LoadBalancer (`kubectl delete -f k8s/chatbot-ui.yaml`).
:::

## Nettoyage

:::clean
1. `kubectl delete -f k8s/chatbot-ui.yaml` (supprime le load balancer) et `kubectl delete secret openai`.
2. Job `eks-terraform` avec `destroy`.
3. Destruction du serveur Jenkins (Terraform ou console).
4. **Révoque la clé OpenAI** sur la plateforme OpenAI.
:::
