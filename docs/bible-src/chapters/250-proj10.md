# Projet 10 — Pipeline CI/CD pour une application .NET sur Azure

:::card
| | |
|---|---|
| Niveau | ★★☆☆☆ Débutant+ |
| Durée | 3 à 5 heures |
| Coût | gratuit avec l'App Service plan **F1** (ou quelques centimes en **B1**) |
| Compétences | Azure App Service, pipeline YAML multi-stages (build, test, publish, deploy), artefacts de pipeline, environnements et approbations, Application Insights |
| Prérequis | Projet 07 (organisation Azure DevOps et service connection) |
| Dépôt d'origine | `DevOps-Project-10/README.md` (labs « DevOps Starter ») |
:::

:::info DevOps Starter n'existe plus
Le lab d'origine utilise **Azure DevOps Starter**, un assistant du portail Azure qui générait automatiquement un dépôt, un pipeline de build, un pipeline de release et une Web App. **Microsoft l'a retiré.** Nous allons construire exactement le même résultat à la main. C'est beaucoup plus formateur : tu sauras ce que faisait l'assistant, et tu sauras le refaire n'importe où.
:::

## Ce qu'on construit

```ascii
 Azure Repos (code ASP.NET Core) ──commit──► Azure Pipelines
                                               ├─ Stage BUILD : restore → build → test → publish → artefact "drop"
                                               └─ Stage DEPLOY (environnement "production", approbation optionnelle)
                                                      └─► Azure App Service (Web App Linux) ──► https://<app>.azurewebsites.net
                                                                     └── Application Insights (monitoring)
```

| Ce que faisait DevOps Starter | Ce que nous faisons |
|---|---|
| Crée un dépôt avec une appli exemple | `dotnet new webapp` + push dans Azure Repos |
| Crée un pipeline de build (*classic*) | stage `Build` dans `azure-pipelines.yml` |
| Crée un pipeline de release (*classic*) avec 5 tâches | stage `Deploy` dans le même YAML |
| Crée la Web App (et une base Azure SQL) | `az webapp create` (la base SQL est optionnelle ici) |
| Branche Application Insights | `az monitor app-insights component create` + paramètre d'application |

:::why YAML plutôt que les pipelines « classic »
Les pipelines *classic* (build et release configurés par clics dans l'interface) ne sont **pas versionnés avec le code** : impossible de relire un changement dans une pull request ou de revenir en arrière. Microsoft recommande désormais les pipelines **YAML multi-stages**, qui font build **et** release dans un seul fichier versionné.
:::

## Étape 1 — Créer l'application .NET

```bash
# SDK .NET sur Ubuntu/WSL (version LTS courante, par exemple 8.0 ou 10.0)
sudo apt update && sudo apt install -y dotnet-sdk-8.0
dotnet --version

mkdir io-dotnet && cd io-dotnet
dotnet new sln -n IoDotnet
dotnet new webapp -n IoDotnet.Web            # application ASP.NET Core Razor Pages
dotnet new xunit  -n IoDotnet.Tests          # projet de tests unitaires
dotnet sln add IoDotnet.Web IoDotnet.Tests
dotnet add IoDotnet.Tests reference IoDotnet.Web
dotnet new gitignore

dotnet build && dotnet test
dotnet run --project IoDotnet.Web            # http://localhost:5xxx
```

Dans Azure DevOps : *Repos → Files* → ton projet propose une URL de clonage. Ajoute-la comme remote et pousse :

```bash
git init && git add . && git commit -m "Application ASP.NET Core initiale"
git remote add origin https://dev.azure.com/<org>/<projet>/_git/io-dotnet
git push -u origin main          # authentification : bouton "Generate Git Credentials" dans Azure Repos
```

## Étape 2 — Créer la Web App et Application Insights

```bash
RG=io-dotnet-rg
APP=io-dotnet-$RANDOM                     # nom unique : il devient <APP>.azurewebsites.net
az group create -n $RG -l francecentral
az appservice plan create -n io-dotnet-plan -g $RG --is-linux --sku F1     # F1 = gratuit
az webapp create -n $APP -g $RG -p io-dotnet-plan --runtime "DOTNETCORE:8.0"

az extension add --name application-insights
az monitor app-insights component create --app $APP-ai -g $RG -l francecentral --kind web
CONN=$(az monitor app-insights component show --app $APP-ai -g $RG --query connectionString -o tsv)
az webapp config appsettings set -n $APP -g $RG --settings APPLICATIONINSIGHTS_CONNECTION_STRING="$CONN"
echo "https://$APP.azurewebsites.net"
```

:::why Un App Service, c'est du PaaS
Tu ne gères ni VM, ni système d'exploitation, ni serveur web : tu fournis ton application compilée, Azure s'occupe du reste (mises à jour, certificats HTTPS `*.azurewebsites.net`, mise à l'échelle). C'est l'opposé du projet 01, où tu gérais tout. Contrepartie : moins de contrôle.
:::

:::info La base Azure SQL du lab d'origine
DevOps Starter créait aussi une base Azure SQL. Notre application n'en a pas besoin ; si tu veux t'entraîner : `az sql server create` + `az sql db create --service-objective Basic`, puis une *connection string* dans les paramètres de la Web App. Pense à la supprimer ensuite (c'est elle qui coûte).
:::

## Étape 3 — Le pipeline multi-stages

À la racine du dépôt, `azure-pipelines.yml` :

```yaml
trigger:
  branches:
    include: [ main ]

pool:
  vmImage: ubuntu-latest

variables:
  buildConfiguration: Release
  azureSubscription: 'azure-devops-journey-service-connection'   # service connection du projet 07
  webAppName: '<APP>'

stages:
- stage: Build
  jobs:
  - job: Build
    steps:
    - task: UseDotNet@2
      inputs: { packageType: sdk, version: '8.0.x' }

    - script: dotnet restore
      displayName: Restaurer les dépendances

    - script: dotnet build --configuration $(buildConfiguration) --no-restore
      displayName: Compiler

    - task: DotNetCoreCLI@2
      displayName: Tests unitaires
      inputs:
        command: test
        projects: '**/*Tests.csproj'
        arguments: '--configuration $(buildConfiguration) --collect "XPlat Code Coverage"'
        publishTestResults: true          # résultats visibles dans l'onglet "Tests"

    - task: DotNetCoreCLI@2
      displayName: Publier l'application
      inputs:
        command: publish
        publishWebProjects: true
        arguments: '--configuration $(buildConfiguration) --output $(Build.ArtifactStagingDirectory)'
        zipAfterPublish: true

    - publish: $(Build.ArtifactStagingDirectory)
      artifact: drop                       # l'artefact que le stage Deploy récupérera

- stage: Deploy
  dependsOn: Build
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  jobs:
  - deployment: DeployWeb
    environment: production                # crée l'environnement "production" (historique, approbations)
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureWebApp@1
            inputs:
              azureSubscription: $(azureSubscription)
              appType: webAppLinux
              appName: $(webAppName)
              package: $(Pipeline.Workspace)/drop/**/*.zip
```

*Pipelines → New pipeline → Azure Repos Git → io-dotnet → Existing YAML file* → *Run*.

:::why `job` vs `deployment`
Un `deployment` est un job spécial lié à un **environnement**. Azure DevOps garde l'historique de ce qui a été déployé où (quel commit est en production ?), et on peut y attacher des **contrôles** : approbation humaine, plage horaire autorisée, vérification qu'une alerte n'est pas en cours… C'est l'équivalent du « release pipeline » classique, en mieux.
:::

## Étape 4 — Examiner ce que fait le pipeline

Reprends les questions du lab d'origine, mais sur ton pipeline :

1. **Le déclencheur** : `trigger` sur `main` = chaque commit lance le pipeline (intégration continue).
2. **Les tâches de build** : restaurer, compiler, tester, publier, puis produire l'artefact `drop` (onglet *Artifacts* d'un run → tu peux télécharger le zip).
3. **L'historique** : *Pipelines → ton pipeline → Runs*, et dans *Environments → production* la liste des déploiements avec leur commit.
4. **Les logs** : clique sur chaque étape d'un run.

**Ajouter une approbation** : *Pipelines → Environments → production → ⋮ → Approvals and checks → Approvals* → ajoute-toi. Le prochain run s'arrêtera avant le déploiement et attendra ton clic.

## Étape 5 — Commit et livraison continue

Dans Azure Repos, édite `IoDotnet.Web/Pages/Index.cshtml` (bouton *Edit*) : change le titre `<h1>` en « Get started right away with Azure DevOps ». *Commit* sur `main`.

:::check
- Le pipeline démarre seul ; les stages *Build* puis *Deploy* passent au vert (après ton approbation si tu l'as activée).
- `https://<APP>.azurewebsites.net` affiche le nouveau titre.
- Onglet *Tests* du run : tous les tests passent.
:::

**Bonus — un test qui casse le pipeline.** Dans le projet de tests, ajoute un test qui échoue (`Assert.True(false)`) et pousse : le stage *Build* échoue, et **rien n'est déployé**. C'est exactement le rôle de l'intégration continue.

## Étape 6 — Application Insights

Portail → Application Insights `<APP>-ai` :

- **Live metrics** : recharge ton site plusieurs fois, observe les requêtes en direct.
- **Performance** : temps de réponse par page.
- **Failures** : ajoute une page qui lève une exception, déploie, appelle-la : l'erreur apparaît avec sa pile d'appels.
- **Availability** : *Add Standard test* sur l'URL du site.

*(Pour une télémétrie riche côté code, ajoute le paquet `Microsoft.ApplicationInsights.AspNetCore` ou OpenTelemetry. Même sans, l'App Service remonte les métriques de base via la connection string.)*

## Dépannage

:::fix
- **Deploy : `Resource doesn't exist`** : `webAppName` ne correspond pas, ou la service connection n'a pas accès au groupe de ressources.
- **Le site affiche « Your web app is running and waiting for your content »** : le zip déployé ne contient pas le projet web (vérifie `publishWebProjects` et le contenu de l'artefact `drop`).
- **Erreur 500.30 / « HTTP Error 500.31 »** : version du runtime de la Web App différente de celle de l'application (`--runtime "DOTNETCORE:8.0"` vs `net8.0` dans le `.csproj`).
- **Le plan F1 refuse** : une seule Web App F1 Linux par région et par abonnement ; passe en B1 ou change de région.
:::
