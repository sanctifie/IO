# Projet 17 — Déployer une application sur AKS avec Azure DevOps et Cloud Shell

:::card
| | |
|---|---|
| Niveau | ★★☆☆☆ Débutant+ |
| Durée | 2 à 4 heures |
| Coût | ~0,10 $/h (AKS 1 nœud + ACR Basic + IP publique) |
| Compétences | Azure Cloud Shell, extension `azure-devops` de la CLI, AKS en ligne de commande, ACR, rôle AcrPull, pipeline Azure DevOps généré pour AKS (environnement Kubernetes, imagePullSecret), GitHub comme source |
| Prérequis | Projet 07 (ou au moins un compte Azure et une organisation Azure DevOps) |
| Dépôt d'origine | `DevOps-Project-17/README.md` ; application `github.com/ghostinthewires/k8s-application` (Node.js) |
:::

## Ce qu'on construit

```ascii
 GitHub (fork de k8s-application) ──push──► Azure Pipelines
                                              ├─ Build  : docker build/push ──► ACR (ksapplication:<BuildId>)
                                              └─ Deploy : environnement « k8s-application.default »
                                                          kubectl apply manifests/ ──► AKS « myakscluster »
                                                                                        Service LoadBalancer :8888
```

Ce projet montre la voie **rapide** : tout se fait depuis **Azure Cloud Shell** (un terminal dans le navigateur, déjà authentifié, avec `az`, `kubectl`, `git` et `helm`), et Azure DevOps **génère** le pipeline pour toi. Tu le liras ensuite ligne par ligne.

## Étape 1 — Cloud Shell et Azure DevOps CLI

Ouvre `https://shell.azure.com` → **Bash**. Puis :

```bash
az extension add --name azure-devops
az devops configure --defaults organization=https://dev.azure.com/<ton-organisation>/
az devops login            # colle un Personal Access Token Azure DevOps (User settings → Personal access tokens)
az devops project create --name k8s-project
az devops configure --defaults project=k8s-project
```

:::tip Le PAT Azure DevOps
Le tutoriel d'origine exporte le jeton dans `AZURE_DEVOPS_EXT_PAT`. `az devops login` fait la même chose en stockant le jeton de façon plus sûre. Donne au PAT une durée courte (7 à 30 jours) et seulement les droits nécessaires (*Build: Read & execute*, *Project and Team*, *Service Connections*, *Code*).
:::

## Étape 2 — L'infrastructure : AKS et ACR

```bash
RG=my-aks-rg
ACR=ioacr$RANDOM                         # unique au monde, minuscules et chiffres
az group create --location francecentral --resource-group $RG
az acr create -g $RG -n $ACR --sku Basic
az aks create -g $RG -n myakscluster \
  --node-count 1 --node-vm-size Standard_B2s \
  --generate-ssh-keys \
  --attach-acr $ACR                      # donne aux nœuds le rôle AcrPull sur ce registre
az aks get-credentials -g $RG -n myakscluster
kubectl get nodes
```

:::info Ce qui change par rapport au dépôt d'origine
Le tutoriel (2020) crée un **service principal** avec un mot de passe (`az ad sp create-for-rbac`), le donne au cluster, active le compte admin de l'ACR, puis attribue le rôle `acrpull` à la main. Aujourd'hui, AKS utilise par défaut une **identité managée** (aucun secret à gérer) et `--attach-acr` attribue le rôle `AcrPull` en une option. Résultat identique, sans mot de passe. L'erreur « 400 Client Error … localhost:50342 » citée par le tutoriel concernait cette ancienne méthode.
:::

## Étape 3 — Le code de l'application

1. **Fork** `github.com/ghostinthewires/k8s-application` sur ton GitHub.
2. Dans Cloud Shell :

```bash
git clone https://github.com/<toi>/k8s-application.git && cd k8s-application
ls                # Dockerfile  app.js  package.json  views/  manifests/  azure-pipelines.yml
cat Dockerfile manifests/*.yml
```

C'est une petite application Node.js (Express) qui écoute sur le port **8888**. Le dossier `manifests/` contient un `deployment.yml` et un `service.yml` (type `LoadBalancer`). Le fichier `azure-pipelines.yml` existant est celui de l'auteur : **supprime-le** pour que l'assistant en génère un pour **ton** ACR et **ton** cluster.

```bash
git rm azure-pipelines.yml && git commit -m "Retire le pipeline de l'auteur" && git push
```

## Étape 4 — Créer le pipeline

**Méthode recommandée (interface web)** : Azure DevOps → projet `k8s-project` → *Pipelines → New pipeline* → **GitHub** (autorise l'application *Azure Pipelines* sur ton compte GitHub, limite-la à ce dépôt) → choisis `k8s-application` → modèle **Deploy to Azure Kubernetes Service** → abonnement → cluster `myakscluster` → namespace **Existing : default** → registre `$ACR` → nom d'image `ksapplication` → port **8888** → *Validate and configure* → relis le YAML → *Save and run* (commit direct sur `master`/`main`).

**Méthode CLI (celle du tutoriel)** : `az pipelines create --name "k8s-application-pipeline"` lance le même assistant dans le terminal. *(GitHub n'accepte plus les mots de passe : l'assistant te demandera un **token GitHub**, pas ton mot de passe.)*

## Étape 5 — Lire le pipeline généré

```yaml
trigger:
- master                                   # chaque commit sur master lance le pipeline

variables:
  dockerRegistryServiceConnection: '<id>'   # connexion à ton ACR, créée par l'assistant
  imageRepository: 'ksapplication'
  containerRegistry: '<acr>.azurecr.io'
  dockerfilePath: '**/Dockerfile'
  tag: '$(Build.BuildId)'                  # chaque build produit un tag unique
  imagePullSecret: '<acr>-auth'            # secret créé dans le cluster pour tirer l'image
  vmImageName: 'ubuntu-latest'

stages:
- stage: Build
  jobs:
  - job: Build
    pool: { vmImage: $(vmImageName) }
    steps:
    - task: Docker@2                         # build + push vers ACR
      inputs:
        command: buildAndPush
        repository: $(imageRepository)
        dockerfile: $(dockerfilePath)
        containerRegistry: $(dockerRegistryServiceConnection)
        tags: $(tag)
    - upload: manifests                      # publie le dossier manifests comme artefact
      artifact: manifests

- stage: Deploy
  dependsOn: Build
  jobs:
  - deployment: Deploy
    environment: 'k8s-application.default'   # environnement Azure DevOps lié au namespace "default" du cluster
    strategy:
      runOnce:
        deploy:
          steps:
          - task: KubernetesManifest@1       # crée/maj le secret de pull de l'image
            inputs:
              action: createSecret
              secretName: $(imagePullSecret)
              dockerRegistryEndpoint: $(dockerRegistryServiceConnection)
          - task: KubernetesManifest@1       # applique les manifests en remplaçant l'image par <acr>/ksapplication:<tag>
            inputs:
              action: deploy
              manifests: |
                $(Pipeline.Workspace)/manifests/deployment.yml
                $(Pipeline.Workspace)/manifests/service.yml
              imagePullSecrets: $(imagePullSecret)
              containers: $(containerRegistry)/$(imageRepository):$(tag)
```

:::why Ce que fait la tâche `KubernetesManifest`
L'option `containers:` réécrit **à la volée** l'image du `deployment.yml` avec le tag du build : le fichier dans Git n'a pas besoin de connaître le tag. C'est une autre réponse au problème « comment déployer exactement l'image que je viens de construire », différente du `sed` + commit du GitOps (projet 16). L'environnement `k8s-application.default` garde l'historique des déploiements et affiche les ressources Kubernetes dans Azure DevOps (*Pipelines → Environments*).
:::

:::info L'`imagePullSecret` est-il nécessaire ?
Avec `--attach-acr`, les nœuds ont déjà le droit de tirer l'image : le secret est redondant (mais inoffensif). Le modèle le crée par défaut pour fonctionner aussi avec un cluster qui n'a pas ce rôle.
:::

## Étape 6 — Vérifier

```bash
kubectl get all
kubectl get svc                     # EXTERNAL-IP du service
```

Ouvre `http://<EXTERNAL-IP>:8888` : la page de l'application s'affiche.

:::check
- Le pipeline montre deux stages verts ; *Environments → k8s-application.default* liste le déploiement.
- ACR → *Repositories* → `ksapplication` avec un tag par build.
- Modifie `views/index.html` (ou le texte dans `app.js`) sur GitHub → commit → nouveau build → la page change.
:::

## Dépannage

:::fix
- **`No hosted parallelism has been purchased or granted`** : voir le projet 07 (demande de gratuité ou agent auto-hébergé).
- **Pod `ImagePullBackOff`** : nom d'ACR erroné ou rôle AcrPull absent (`az aks check-acr -g $RG -n myakscluster --acr $ACR.azurecr.io`).
- **`EXTERNAL-IP` en `<pending>` longtemps** : quota d'IP publiques de l'abonnement d'essai atteint ; `kubectl describe svc` donne l'erreur.
- **Quota de vCPU** : `Standard_B2s` (2 vCPU) suffit ; les abonnements d'essai sont limités à quelques vCPU par région.
:::

## Nettoyage

:::clean
```bash
az group delete -n my-aks-rg --yes --no-wait     # supprime AKS, ACR, IP, disques… (et le groupe MC_… des nœuds)
```
Dans Azure DevOps, tu peux supprimer le projet `k8s-project` (*Project settings → Overview → Delete*). Révoque le PAT et l'autorisation GitHub si tu ne t'en sers plus.
