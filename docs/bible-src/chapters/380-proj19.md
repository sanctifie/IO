## Ce qu'on construit

Deux couches d'infrastructure, toutes deux en Terraform, la seconde pilotée par un pipeline :

```ascii
 COUCHE 1 (depuis ton poste)                    COUCHE 2 (depuis Jenkins)
 terraform apply  jenkins_server/tf-aws-ec2     pipeline Jenkins (paramètre action = apply | destroy)
   VPC jenkins-vpc (module vpc)                   checkout → terraform init → validate → plan
   SG 8080/22/9000 (module security-group)        → [validation manuelle] → terraform $action
   EC2 Jenkins-Build-Server (module ec2-instance)   VPC my-eks-vpc (module vpc, subnets privés + NAT)
     user data : Jenkins, Docker, SonarQube,        EKS my-eks-cluster (module eks, managed node group)
     AWS CLI, Terraform, kubectl, Helm, Trivy     → aws eks update-kubeconfig → kubectl apply nginx
                                                     Service LoadBalancer ──► navigateur
 État : s3://<bucket>/jenkins/terraform.tfstate   État : s3://<bucket>/eks/terraform.tfstate
```

:::why Pourquoi séparer en deux couches avec deux états ?
Le serveur Jenkins vit longtemps ; le cluster EKS peut être créé et détruit souvent. Deux **états Terraform séparés** permettent de détruire l'un sans risquer l'autre, de limiter l'impact d'une erreur (*blast radius*) et d'accélérer les `plan`. En entreprise, on découpe ainsi l'infrastructure en couches : réseau, données, plateformes, applications.
:::

## Étape 1 — Lire et adapter le Terraform du serveur Jenkins

```bash
cd ~/IO/projects && mkdir 19-eks-terraform-jenkins && cd 19-eks-terraform-jenkins
cp -r /tmp/dp/DevOps-Project-19/* .
cd jenkins_server/tf-aws-ec2 && ls
# backend.tf data.tf main.tf outputs.tf provider.tf variables.tf variables/{dev,test,prod}.tfvars
```

`main.tf` utilise trois **modules du Terraform Registry** (`terraform-aws-modules/…`) : un module crée en quelques lignes ce qui demanderait des dizaines de ressources.

**À corriger avant de lancer :**

1. **`backend.tf`** : ton bucket (`io-tfstate-<prenom>`), clé `jenkins/terraform.tfstate`, région `eu-west-3`, `use_lockfile = true`.
2. **`variables/dev.tfvars`** : `aws_region = "eu-west-3"`, ton `aws_account_id`, `instance_type = "t3.large"`.
3. **L'AMI codée en dur** : `ami = "ami-0e8a34246278c21e4"` est un identifiant d'Amazon Linux 2 **dans `us-east-1`** uniquement. Un ID d'AMI est **propre à une région** : dans `eu-west-3`, il n'existe pas. Remplace-le par une recherche dynamique dans `data.tf` :

```hcl
data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-2023.*-x86_64"]
  }
}
```

   puis dans `main.tf` : `ami = data.aws_ami.al2023.id`. *(Le script `install_build_tools.sh` utilise `yum` : il fonctionne sur Amazon Linux 2023, où `yum` est un alias de `dnf`. Le paquet `docker` et `java-17-amazon-corretto-devel` existent sur AL2023.)*

4. **Security Group** : le module ouvre 22, 8080 et 9000 à `0.0.0.0/0`. Restreins au moins **22** à ton IP.
5. **Rôle IAM de l'instance** : le pipeline exécutera Terraform et kubectl **depuis Jenkins**. Plutôt que de stocker des clés AWS dans Jenkins (ce que fait le Jenkinsfile d'origine), donne un **rôle** à l'instance. Ajoute au module `ec2_instance` :

```hcl
  create_iam_instance_profile = true
  iam_role_policies = {
    admin = "arn:aws:iam::aws:policy/AdministratorAccess"   # lab uniquement ; restreindre en entreprise
  }
```

## Étape 2 — Créer le serveur Jenkins

```bash
terraform init
terraform plan  -var-file=variables/dev.tfvars
terraform apply -var-file=variables/dev.tfvars
terraform output                    # IP publique du serveur
```

Le user data (`../scripts/install_build_tools.sh`) installe Jenkins, Git, Docker, un conteneur SonarQube, AWS CLI, Terraform, kubectl, Helm et Trivy. Patiente 5 minutes, puis :

```bash
ssh -i ~/.ssh/io-key.pem ec2-user@<IP>
sudo cat /var/log/cloud-init-output.log | tail -30    # le script s'est-il bien terminé ?
jenkins --version; docker ps; terraform -version; kubectl version --client; aws sts get-caller-identity
sudo cat /var/lib/jenkins/secrets/initialAdminPassword
```

Configure Jenkins (`http://<IP>:8080`) : plugins suggérés + **Pipeline: Stage View**.

## Étape 3 — Le Terraform du cluster EKS

```bash
cd ../../tf-aws-eks && ls
# backend.tf data.tf eks.tf provider.tf variables.tf vpc.tf variables/{dev,test,prod}.tfvars
```

`vpc.tf` crée un VPC avec subnets **publics et privés**, une NAT Gateway unique, et surtout les **tags** dont EKS a besoin :

```hcl
public_subnet_tags  = { "kubernetes.io/role/elb" = 1 }            # où créer les load balancers publics
private_subnet_tags = { "kubernetes.io/role/internal-elb" = 1 }   # où créer les load balancers internes
```

`eks.tf` appelle le module `terraform-aws-modules/eks/aws` : cluster dans les subnets **privés** (les nœuds n'ont pas d'IP publique), endpoint d'API public, un *managed node group*.

**À corriger :**

1. **`backend.tf`** : ton bucket, clé `eks/terraform.tfstate`, `eu-west-3`.
2. **`variables/dev.tfvars`** : région et CIDR.
3. **`eks.tf`** :
   - `cluster_version` : supprime la ligne ou mets une version **actuellement supportée** par EKS (la 1.29 du dépôt est hors support standard, donc facturée en *extended support*, 6 fois plus cher !) ;
   - `instance_types = ["t3.medium"]` (le `t2.small` d'origine est trop petit) ; tu peux garder `capacity_type = "SPOT"` (instances jusqu'à 70 % moins chères, qu'AWS peut reprendre) ;
   - **ajoute** `enable_cluster_creator_admin_permissions = true`.

:::warn `enable_cluster_creator_admin_permissions`
Depuis la version 20 du module EKS, l'identité qui crée le cluster **n'est plus administratrice Kubernetes par défaut**. Sans cette option, Terraform crée le cluster, mais l'étape `kubectl apply` du pipeline échoue avec `Unauthorized`. C'est l'erreur la plus fréquente de ce projet.
:::

Pousse le tout dans **ton** dépôt GitHub (`terraform-eks-cicd`), avec `tf-aws-eks/`, `manifest/` et le `Jenkinsfile` à la racine.

## Étape 4 — Le pipeline Jenkins

Le Jenkinsfile d'origine lit `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` depuis les credentials Jenkins. Avec le rôle IAM de l'instance (étape 1), c'est **inutile** : supprime ce bloc. Version corrigée et rejouable :

```groovy
pipeline {
    agent any
    parameters {
        choice(name: 'action', choices: ['apply', 'destroy'], description: 'Créer ou détruire le cluster')
    }
    environment {
        AWS_DEFAULT_REGION = 'eu-west-3'
    }
    stages {
        stage('Checkout') {
            steps { git branch: 'main', url: 'https://github.com/<toi>/terraform-eks-cicd.git' }
        }
        stage('Terraform init') {
            steps { dir('tf-aws-eks') { sh 'terraform init -input=false' } }
        }
        stage('Terraform validate') {
            steps { dir('tf-aws-eks') { sh 'terraform validate' } }
        }
        stage('Terraform plan') {
            steps {
                dir('tf-aws-eks') {
                    script {
                        def destroyFlag = params.action == 'destroy' ? '-destroy' : ''
                        sh "terraform plan -input=false ${destroyFlag} -var-file=variables/dev.tfvars -out=tfplan"
                    }
                }
                input(message: "Appliquer ce plan (${params.action}) ?", ok: 'Confirmer')
            }
        }
        stage('Terraform apply/destroy') {
            steps { dir('tf-aws-eks') { sh 'terraform apply -input=false tfplan' } }
        }
        stage('Déployer Nginx') {
            when { expression { params.action == 'apply' } }        // pas de déploiement après un destroy
            steps {
                dir('manifest') {
                    sh '''
                      aws eks update-kubeconfig --name my-eks-cluster
                      kubectl create namespace eks-nginx-app --dry-run=client -o yaml | kubectl apply -f -
                      kubectl apply -f deployment.yaml -n eks-nginx-app
                      kubectl apply -f service.yaml -n eks-nginx-app
                      kubectl rollout status deploy/nginx -n eks-nginx-app --timeout=180s
                    '''
                }
            }
        }
    }
}
```

:::why Les améliorations par rapport à l'original
- **`input(...)`** : le pipeline **s'arrête** et attend qu'un humain lise le plan et clique *Confirmer*. C'est la validation manuelle avant de modifier l'infrastructure.
- **`plan -out=tfplan` puis `apply tfplan`** : on applique exactement le plan validé.
- **`plan -destroy`** : avec `action=destroy`, le plan affiché est celui de la destruction (dans l'original, on validait un plan de création avant de détruire !).
- **`when { … 'apply' }`** : on ne déploie pas l'application juste après avoir détruit le cluster (l'original le faisait, et échouait).
- **`create namespace … | kubectl apply`** : rejouable (l'original échouait au 2ᵉ lancement car le namespace existait déjà).
:::

Jenkins → *New Item* `eks-cicd` → **Pipeline** → *Pipeline script from SCM* → ton dépôt → `Jenkinsfile` → *Save*. Le premier lancement découvre le paramètre ; les suivants proposent **Build with Parameters**.

## Étape 5 — Lancer

*Build with Parameters* → `action = apply` → au stage *Terraform plan*, survole l'étape et clique **Confirmer** après avoir lu le plan dans la console. 15 à 20 minutes plus tard :

```bash
# sur le serveur Jenkins (ou ton poste avec les bons droits)
aws eks update-kubeconfig --name my-eks-cluster --region eu-west-3
kubectl get nodes
kubectl get all -n eks-nginx-app
kubectl get svc nginx -n eks-nginx-app        # EXTERNAL-IP → page "Welcome to nginx!"
```

:::check
- Les 6 stages sont verts ; la console montre le plan complet (VPC, subnets, NAT, EKS, node group, rôles IAM…).
- La page Nginx s'affiche par le nom DNS du load balancer.
- Deux fichiers d'état existent dans S3 : `jenkins/terraform.tfstate` et `eks/terraform.tfstate`.
:::

## Dépannage

:::fix
- **`InvalidAMIID.NotFound`** : l'AMI codée en dur (étape 1, point 3).
- **`Unauthorized` au `kubectl apply`** : `enable_cluster_creator_admin_permissions` manquant, ou Jenkins utilise une autre identité que celle qui a créé le cluster.
- **`terraform: command not found` dans Jenkins** : le user data n'a pas fini ou a échoué (`/var/log/cloud-init-output.log`).
- **`Error acquiring the state lock`** : un build interrompu. Après vérification : `terraform force-unlock <ID>` depuis le serveur.
- **Le destroy échoue sur le VPC (`DependencyViolation`)** : le load balancer créé par le Service Kubernetes existe encore. Supprime d'abord `kubectl delete svc nginx -n eks-nginx-app`. Ajoute idéalement cette commande en tête d'un stage « pré-destroy ».
- **Nœuds Spot non disponibles** : passe `capacity_type` à `ON_DEMAND`.
:::

## Nettoyage

:::clean
1. `kubectl delete svc nginx -n eks-nginx-app` (supprime le load balancer).
2. Pipeline avec `action = destroy` (ou `terraform destroy -var-file=variables/dev.tfvars` dans `tf-aws-eks/`).
3. Depuis ton poste : `terraform destroy -var-file=variables/dev.tfvars` dans `jenkins_server/tf-aws-ec2/`.
4. Vérifie NAT Gateways, Elastic IPs, load balancers, volumes EBS.
:::
