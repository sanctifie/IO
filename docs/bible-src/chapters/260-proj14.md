# Projet 14 — Pipeline CI/CD de bout en bout avec GitHub Actions pour une application Android

:::card

|---|---|
| Niveau | ★★☆☆☆ Débutant+ |
| Durée | 4 à 6 heures |

| Compétences | GitHub Actions (workflows, jobs, steps, triggers, secrets, cache, artefacts, outputs, conditions par branche), Gradle, lint, tests et couverture, SonarQube/SonarCloud, branches par environnement, OIDC vers AWS |

## Ce qu'on construit

Une usine logicielle pour une application mobile Android, intégralement dans GitHub :

```ascii
 push sur develop / qa / main  ou  pull request
          │
          ▼
 ┌───────────────────── job BUILD (runner ubuntu-latest) ─────────────────────┐
 │ checkout → JDK → cache Gradle → clean → lint → build (APK debug + release) │
 │ → tests + couverture Jacoco → analyse SonarCloud → APK renommés et datés   │
 │ → upload de l'artefact "apk-files"                                         │
 └──────────────────────────────────┬─────────────────────────────────────────┘
                                     │ needs: build   (seulement sur qa et main)
 ┌──────────────────── job DEPLOY ──▼──────────────────────────────────────────┐
 │ download de l'artefact → publication des APK (JFrog ou S3) dans qa/ ou main/│
 └─────────────────────────────────────────────────────────────────────────────┘
          │
          ▼  notification (Teams / Slack / e-mail)
```

## GitHub Actions : le vocabulaire

| Notion | Définition |
|---|---|
| **Workflow** | un fichier YAML dans `.github/workflows/`, déclenché par des événements |
| **Event** (`on:`) | ce qui déclenche : `push`, `pull_request`, `schedule`, `workflow_dispatch` (bouton manuel)… |
| **Job** | un ensemble d'étapes exécutées sur **une** machine (*runner*). Les jobs tournent **en parallèle**, sauf si `needs:` impose un ordre |
| **Step** | une commande (`run:`) ou une **action** réutilisable (`uses:`) |
| **Action** | un composant prêt à l'emploi, publié sur le Marketplace : `actions/checkout`, `actions/setup-java`… |
| **Runner** | la machine qui exécute le job : hébergée par GitHub (`ubuntu-latest`) ou auto-hébergée |
| **Secret** | une valeur chiffrée (*Settings → Secrets and variables → Actions*), lue avec `${{ secrets.NOM }}`, masquée dans les logs |
| **Artifact** | un fichier produit par un job, conservé et téléchargeable, transmis à un autre job |
| **Expression** | `${{ … }}` : accès aux contextes (`github.ref`, `secrets`, `steps.<id>.outputs`, `needs.<job>.outputs`) |

:::why Chaque job démarre sur une machine vierge
Le job `deploy` ne voit **pas** les fichiers du job `build` : ce sont deux machines différentes, effacées après usage. Pour transmettre les APK, on les **téléverse** comme artefact dans `build` et on les **télécharge** dans `deploy`. Pour transmettre une simple valeur (la date), on utilise les **outputs** du job.
:::

## Étape 1 — Préparer le dépôt

1. Crée un dépôt GitHub `android-demo-app` et copies-y le contenu de `DevOps-Project-14/android-demo-app`.
2. Crée les branches d'environnement : `git switch -c develop && git push -u origin develop`, puis `qa`. Sur GitHub, mets `main` comme branche par défaut.

:::warn Un projet Android de 2021
Le projet utilise l'Android Gradle Plugin 7.0 (bêta) et Gradle 7.0.2, qui exigent **Java 11** : on garde donc JDK 11 dans le workflow. Si le build échoue à cause d'un dépôt de dépendances disparu (`jcenter()` est fermé), remplace `jcenter()` par `mavenCentral()` dans `build.gradle`. Alternative : crée un projet neuf avec **Android Studio** (modèle *Empty Activity*), qui utilisera des versions actuelles (JDK 17), et applique-lui le même workflow.
:::

## Étape 2 — Le workflow, modernisé et commenté

Le workflow d'origine utilise des versions d'actions obsolètes (`checkout@v2/v3`, `cache@v1`, `upload-artifact@v3` qui ne fonctionne plus) et la commande `::set-output`, supprimée par GitHub. Voici la version à jour, `.github/workflows/android.yml` :

```yaml
name: Android CI/CD

on:
  push:
    branches: [ main, qa, develop ]
  pull_request:
    branches: [ main, qa ]
  workflow_dispatch:                 # bouton "Run workflow" dans l'onglet Actions

permissions:
  contents: read
  id-token: write                    # nécessaire pour l'authentification OIDC vers AWS (étape 5)

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      build_date: ${{ steps.date.outputs.build_date }}

    steps:
      - name: Récupérer le code
        uses: actions/checkout@v4
        with:
          fetch-depth: 0             # historique complet : utile à SonarCloud

      - name: Installer JDK 11 (avec cache Gradle intégré)
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '11'
          cache: gradle

      - name: Rendre gradlew exécutable
        run: chmod +x gradlew

      - name: Lint
        run: ./gradlew lint

      - name: Build (APK debug et release)
        run: ./gradlew build

      - name: Tests et couverture Jacoco
        run: ./gradlew jacocoTest      # tâche définie dans le projet (scripts/*.gradle)

      - name: Analyse SonarCloud
        if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: https://sonarcloud.io
        run: ./gradlew sonarqube -Dsonar.projectKey=${{ vars.SONAR_PROJECT_KEY }} -Dsonar.organization=${{ vars.SONAR_ORG }}

      - name: Date du build
        id: date
        run: echo "build_date=$(date +'%Y%m%d-%H%M%S')" >> "$GITHUB_OUTPUT"

      - name: Renommer les APK avec la date
        run: |
          mkdir -p apk-files/debug apk-files/release
          cp app/build/outputs/apk/debug/app-debug.apk \
             apk-files/debug/app-debug-${{ steps.date.outputs.build_date }}.apk
          cp app/build/outputs/apk/release/app-release-unsigned.apk \
             apk-files/release/app-release-unsigned-${{ steps.date.outputs.build_date }}.apk

      - name: Publier les APK comme artefact
        uses: actions/upload-artifact@v4
        with:
          name: apk-files
          path: apk-files/
          retention-days: 7

  deploy:
    needs: build
    if: github.ref == 'refs/heads/qa' || github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: ${{ github.ref_name }}      # environnements GitHub "qa" et "main" (règles de protection possibles)

    steps:
      - name: Récupérer les APK
        uses: actions/download-artifact@v4
        with:
          name: apk-files
          path: apk-files/

      - name: Afficher les fichiers
        run: ls -R apk-files

      - name: S'authentifier auprès d'AWS (OIDC, sans clé)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: eu-west-3

      - name: Publier dans S3, dans le dossier de l'environnement
        run: |
          aws s3 cp apk-files/ \
            s3://${{ vars.APK_BUCKET }}/${{ github.ref_name }}/${{ needs.build.outputs.build_date }}/ --recursive
```

:::why Les points clés à comprendre
- **`>> "$GITHUB_OUTPUT"`** : la façon actuelle de définir une sortie d'étape (remplace `::set-output`). Elle est lue ensuite avec `steps.date.outputs.build_date`, et exposée au job suivant via `outputs:` + `needs.build.outputs.build_date`.
- **`if:` sur le job deploy** : on ne publie que pour `qa` et `main`. Une branche `develop` ou une PR s'arrête après le build. C'est la stratégie « une branche = un environnement ».
- **`cache: gradle`** : Gradle télécharge des centaines de Mo de dépendances ; le cache fait passer le build de 8 à 3 minutes.
- **`vars.` vs `secrets.`** : les *variables* (non sensibles, visibles) et les *secrets* (chiffrés, masqués) se configurent au même endroit dans les paramètres du dépôt.
- **La condition sur SonarCloud** : les PR venant d'un *fork* n'ont pas accès aux secrets (sécurité) ; on saute l'analyse dans ce cas plutôt que de faire échouer le workflow.
:::

## Étape 3 — SonarCloud

1. `sonarcloud.io` → importe le dépôt GitHub → méthode d'analyse *GitHub Actions* (désactive l'*Automatic Analysis*, sinon conflit).
2. Dépôt GitHub → *Settings → Secrets and variables → Actions* :
   - secret **`SONAR_TOKEN`** ;
   - variables **`SONAR_ORG`** et **`SONAR_PROJECT_KEY`**.

## Étape 4 — Où publier les APK ?

Le dépôt d'origine publie dans **JFrog Artifactory** hébergé sur une EC2, et ouvre **temporairement** le Security Group à l'IP du runner GitHub avant l'envoi. C'est une technique intéressante (les runners GitHub changent d'IP à chaque exécution), mais elle impose des clés AWS à longue durée de vie dans les secrets. Deux options plus simples :

- **S3** (ci-dessus), avec authentification **OIDC** : aucun secret AWS permanent.
- **JFrog Cloud** : remplace les deux dernières étapes par l'action `jfrog/setup-jfrog-cli@v4` (secrets `JF_URL`, `JF_ACCESS_TOKEN`) puis `jf rt upload "apk-files/*" android-artifact/${{ github.ref_name }}/`.

## Étape 5 — L'authentification OIDC entre GitHub et AWS

:::why Pourquoi OIDC
Stocker `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` dans GitHub, c'est risquer une fuite de clés permanentes. Avec **OIDC**, GitHub fournit au workflow un jeton signé qui dit « je suis le workflow du dépôt X, branche Y ». AWS le vérifie et donne en échange des identifiants **temporaires** (1 heure) pour un rôle précis. Rien à stocker, rien à faire tourner.
:::

1. IAM → *Identity providers → Add provider* → **OpenID Connect** → URL `https://token.actions.githubusercontent.com`, audience `sts.amazonaws.com`.
2. IAM → *Roles → Create role* → *Web identity* → ce provider → audience `sts.amazonaws.com` → *GitHub organization* : ton pseudo, *repository* : `android-demo-app`. Attache une politique autorisant `s3:PutObject` sur `arn:aws:s3:::<bucket>/*`. Nom : `github-android-deploy`.
3. Crée le bucket (`aws s3 mb s3://io-14-apk-<prenom>`), puis dans GitHub : secret **`AWS_ROLE_ARN`** (ARN du rôle) et variable **`APK_BUCKET`**.

La politique de confiance générée ressemble à ceci (vérifie la condition `sub`, elle limite l'accès à **ton** dépôt) :

```json
"Condition": {
  "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
  "StringLike":   { "token.actions.githubusercontent.com:sub": "repo:<toi>/android-demo-app:*" }
}
```

## Étape 6 — Tester la stratégie de branches

```bash
git switch develop && echo "// test" >> app/build.gradle && git commit -am "test develop" && git push
# → onglet Actions : seul le job build tourne

git switch qa && git merge develop && git push
# → build puis deploy ; les APK arrivent dans s3://…/qa/<date>/
```

Ouvre aussi une **pull request** de `develop` vers `qa` : le workflow tourne sur la PR, et son résultat s'affiche dans la PR (coche verte ou croix rouge). Protège `main` et `qa` (*Settings → Branches*) en exigeant que le check `build` passe.

:::check
- Onglet *Actions* : runs verts, le job `deploy` apparaît uniquement pour `qa`/`main`.
- Dans un run : section *Artifacts* → `apk-files` téléchargeable.
- SonarCloud : analyse du projet visible.
- S3 : `aws s3 ls s3://io-14-apk-<prenom>/ --recursive`.
:::

## Étape 7 (optionnelle) — Notifications

Le workflow d'origine envoie une carte dans **Microsoft Teams**. Plus universel : un *Incoming Webhook* Slack ou Teams, appelé avec `curl` dans une étape `if: always()` :

```yaml
      - name: Notification
        if: always()
        run: |
          curl -s -X POST -H 'Content-Type: application/json' \
            -d "{\"text\":\"${{ github.workflow }} sur ${{ github.ref_name }} : ${{ job.status }}\"}" \
            "${{ secrets.CHAT_WEBHOOK_URL }}"
```

## Dépannage

:::fix
- **`Unsupported class file major version`** ou erreur de plugin Gradle : mauvaise version de JDK (ici, 11).
- **`Could not resolve … jcenter`** : remplace `jcenter()` par `mavenCentral()`.
- **`Not authorized to perform sts:AssumeRoleWithWebIdentity`** : condition `sub` de la politique de confiance qui ne correspond pas au dépôt/branche, ou `permissions: id-token: write` absent.
- **SonarCloud : `You are running CI analysis while Automatic Analysis is enabled`** : désactive l'analyse automatique dans SonarCloud.
- **Le job deploy ne se lance jamais** : la condition `if` compare `github.ref` à `refs/heads/qa` ; vérifie le nom exact de ta branche.
:::
