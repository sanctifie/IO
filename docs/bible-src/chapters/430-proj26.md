# Projet 26 — Automatiser l'infrastructure AWS avec Terraform et GitLab CI/CD

:::card
| | |
|---|---|
| Niveau | ★★★☆☆ Intermédiaire |

| Coût | ~0 € (une `t3.micro` quelques minutes ; minutes GitLab gratuites) |
| Compétences | modules Terraform locaux et sorties, backend S3 configuré à l'`init` (`-backend-config`), GitLab (projet, variables CI/CD masquées et protégées, runners), `.gitlab-ci.yml` (stages, artefacts, cache, jobs manuels), OIDC GitLab → AWS |
| Prérequis | Leçons 10 et 13 |

## Ce qu'on construit

```ascii
 Partie 1 (poste local)                       Partie 2 (GitLab CI)
 terraform init/plan/apply                    git push ──► pipeline GitLab (runner partagé, image Terraform)
   module vpc : VPC, subnet public, SG          validate ─► plan (artefact planfile) ─► apply (MANUEL) ─► destroy (MANUEL)
   module web : instance EC2                       │ identifiants AWS : variables CI/CD masquées (ou OIDC)
                      │                            │
                      └──────── état partagé : s3://<bucket>/terraform/staging/terraform.tfstate ────────┘
```

Le but : passer d'une infrastructure lancée **depuis ton poste** à une infrastructure lancée **par un pipeline**, avec le même code et le même état.

## Étape 1 — Le code et ses défauts

```text
.
├── main.tf          # appelle les modules vpc et web
├── provider.tf      # région
├── backend.tf       # backend S3
├── tfstate.config   # paramètres du backend passés à l'init
├── vpc/  (main.tf, variables.tf, outputs.tf)   # VPC 10.0.0.0/16, subnet 10.0.1.0/24, SG port 22
└── web/  (main.tf, variables.tf, outputs.tf)   # aws_instance
```

`main.tf` montre la bonne façon de relier des modules : les **sorties** du module `vpc` deviennent les **entrées** du module `web`.

```hcl
module "vpc" { source = "./vpc" }
module "ec2" {
  source = "./web"
  sn     = module.vpc.pb_sn       # sortie "pb_sn" du module vpc
  sg     = module.vpc.sg
}
```

**À corriger (le code d'origine ne fonctionne pas tel quel) :**

1. **`backend.tf`** : l'argument `aws_dynamodb_table` **n'existe pas** (c'est `dynamodb_table`). Modernise et ne garde que la structure, les valeurs viennent de `tfstate.config` :

```hcl
terraform {
  backend "s3" {}             # configuration partielle : complétée par -backend-config à l'init
}
```

```hcl
# tfstate.config
bucket       = "io-tfstate-<prenom>"
key          = "terraform/staging/terraform.tfstate"
region       = "eu-west-3"
encrypt      = true
use_lockfile = true
```

2. **`provider.tf`** : `region = "eu-west-3"` ; et dans `vpc/main.tf` : `availability_zone = "eu-west-3a"`.
3. **`web/main.tf`** : l'AMI `ami-04a81a99f5ec58529` est une Ubuntu de **`us-east-1`** (un ID d'AMI est propre à une région). Remplace par une recherche (voir le bloc `data "aws_ami" "ubuntu"` du projet 06). Et remplace `security_groups = [var.sg]` par **`vpc_security_group_ids = [var.sg]`** : dans un VPC personnalisé, `security_groups` attend des **noms** et provoque une recréation de l'instance à chaque `apply`.
4. **Le réseau** : le module `vpc` crée un subnet « public » (IP publique automatique) mais **ni Internet Gateway, ni route** : l'instance n'est pas joignable. Ajoute une `aws_internet_gateway`, une `aws_route_table` avec `0.0.0.0/0 → IGW` et l'association au subnet (comme au projet 06). Restreins le port 22 à ton IP.

:::why La configuration partielle du backend
Un bloc `backend` ne peut pas utiliser de variables Terraform. Pour garder le code identique entre environnements (staging, prod) tout en changeant de bucket ou de clé, on laisse le bloc vide et on fournit les valeurs à l'initialisation : `terraform init -backend-config=tfstate.config` (ou `-backend-config="key=prod/terraform.tfstate"`). C'est la technique utilisée par le pipeline GitLab.
:::

## Étape 2 — Partie 1 : en local

```bash
terraform init -backend-config=tfstate.config
terraform fmt -recursive && terraform validate
terraform plan -out=planfile
terraform apply planfile
terraform output
terraform destroy          # on détruit : la suite se fera par le pipeline, avec le même état S3
```

## Étape 3 — Le projet GitLab

1. Crée un compte sur `gitlab.com` → *New project → Create blank project* → `aws-terraform-gitlab` (privé).
2. Pousse le code :

```bash
git remote add gitlab git@gitlab.com:<toi>/aws-terraform-gitlab.git      # (ajoute ta clé SSH dans GitLab → Preferences → SSH Keys)
git push -u gitlab main
```

3. **Variables CI/CD** : *Settings → CI/CD → Variables → Add variable* :

| Clé | Valeur | Options |
|---|---|---|
| `MY_AWS_KEY` | access key ID d'un utilisateur IAM dédié (droits limités à EC2/VPC + bucket d'état) | *Masked*, *Protected* |
| `MY_AWS_ACCESS_KEY` | secret access key | *Masked*, *Protected* |

:::warn « Protected » et les branches
Une variable **protégée** n'est disponible que dans les pipelines des branches **protégées** (`main` par défaut). Si ton pipeline tourne sur une autre branche, les variables sont vides et Terraform échoue avec `No valid credential sources found`. C'est voulu : seules les branches relues peuvent toucher à la production.
:::

## Étape 4 — Le `.gitlab-ci.yml`, modernisé

Le fichier d'origine utilise une image interne de GitLab et `TF_LOG: DEBUG` (très verbeux, peut afficher des informations sensibles). Version propre :

```yaml
image:
  name: hashicorp/terraform:1.10        # image officielle, version épinglée
  entrypoint: [""]                       # l'image a terraform comme entrypoint : on le neutralise pour exécuter des scripts

variables:
  TF_IN_AUTOMATION: "true"
  AWS_ACCESS_KEY_ID: ${MY_AWS_KEY}
  AWS_SECRET_ACCESS_KEY: ${MY_AWS_ACCESS_KEY}
  AWS_DEFAULT_REGION: "eu-west-3"

cache:
  key: terraform
  paths: [.terraform]                    # garder les providers téléchargés entre les jobs

before_script:
  - terraform --version
  - terraform init -input=false -backend-config=tfstate.config

stages: [validate, plan, apply, destroy]

validate:
  stage: validate
  script:
    - terraform fmt -check -recursive
    - terraform validate

plan:
  stage: plan
  script:
    - terraform plan -input=false -out=planfile
  artifacts:
    paths: [planfile]
    expire_in: 1 day

apply:
  stage: apply
  script:
    - terraform apply -input=false planfile
  dependencies: [plan]                   # récupère l'artefact planfile
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual                       # bouton ▶ dans l'interface
  environment: staging

destroy:
  stage: destroy
  script:
    - terraform destroy -input=false -auto-approve
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual
  environment:
    name: staging
    action: stop
```

:::why Les mécanismes clés
- **`artifacts`** : le fichier `planfile` produit par le job `plan` est conservé et transmis au job `apply` (`dependencies`). On applique exactement le plan affiché.
- **`when: manual`** : `apply` et `destroy` attendent un clic humain, après lecture du plan dans les logs du job `plan`.
- **`cache`** : le dossier `.terraform` (les providers, plusieurs centaines de Mo) est réutilisé entre jobs et pipelines.
- **`before_script`** : exécuté avant chaque job (ici, l'`init` avec le backend partiel).
- **`environment`** : GitLab garde l'historique des déploiements de l'environnement *staging* (*Operate → Environments*).
:::

## Étape 5 — Exécuter

Pousse le fichier → *Build → Pipelines* : `validate` et `plan` s'exécutent seuls. Ouvre les logs de `plan`, lis-le, puis clique **▶** sur `apply`.

:::check
- L'instance `my_server` apparaît dans EC2 ; tu peux t'y connecter en SSH si tu as ajouté IGW, route et `key_name`.
- Le fichier d'état est dans `s3://io-tfstate-<prenom>/terraform/staging/terraform.tfstate`.
- Lance `terraform plan` en local (avec `init -backend-config=tfstate.config`) : « No changes » — ton poste et le pipeline partagent **le même état**.
- Clique ▶ sur `destroy` : tout disparaît.
:::

## Étape 6 (recommandée) — Sans clé d'accès : OIDC GitLab → AWS

Comme GitHub, GitLab peut fournir un jeton OIDC à chaque job :

1. IAM → *Identity providers → Add* → OpenID Connect → URL **`https://gitlab.com`**, audience `https://gitlab.com`.
2. Rôle IAM `gitlab-terraform` avec une politique de confiance limitée à ton projet et à `main` :

```json
"Condition": {
  "StringEquals": { "gitlab.com:aud": "https://gitlab.com" },
  "StringLike":   { "gitlab.com:sub": "project_path:<toi>/aws-terraform-gitlab:ref_type:branch:ref:main" }
}
```

3. Dans `.gitlab-ci.yml`, supprime `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` et ajoute :

```yaml
default:
  id_tokens:
    GITLAB_OIDC_TOKEN:
      aud: https://gitlab.com

variables:
  AWS_ROLE_ARN: arn:aws:iam::<compte>:role/gitlab-terraform
  AWS_WEB_IDENTITY_TOKEN_FILE: /tmp/web_identity_token

before_script:
  - echo "$GITLAB_OIDC_TOKEN" > /tmp/web_identity_token    # le SDK AWS (utilisé par Terraform) lit ce fichier et endosse le rôle
  - terraform init -input=false -backend-config=tfstate.config
```

Supprime ensuite les variables `MY_AWS_KEY`/`MY_AWS_ACCESS_KEY` et **désactive les clés** de l'utilisateur IAM.

## Dépannage

:::fix
- **`Unsupported argument "aws_dynamodb_table"`** : étape 1, point 1.
- **`No valid credential sources found`** : variables protégées sur une branche non protégée, ou noms de variables différents.
- **`terraform: not found`/le job se termine immédiatement** : `entrypoint: [""]` manquant avec l'image `hashicorp/terraform`.
- **`Saved plan is stale`** au job `apply` : un autre pipeline a modifié l'état entre-temps ; relance le pipeline.
- **L'instance est recréée à chaque `apply`** : `security_groups` au lieu de `vpc_security_group_ids`.
- **`Error acquiring the state lock`** : un job annulé a laissé le verrou ; `terraform force-unlock <ID>` en local après vérification.
:::

## Nettoyage

:::clean
Job `destroy` (ou `terraform destroy` en local). Supprime les variables CI/CD, l'utilisateur IAM et ses clés (ou le rôle OIDC), et éventuellement le projet GitLab.
:::
