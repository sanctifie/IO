## Ce qu'on construit

Le modèle « CI Jenkins + CD GitOps » qu'on retrouve dans énormément d'entreprises :

```ascii
          ┌────────── PIPELINE CI : register-app-ci (dépôt register-app) ──────────┐
 push ──► │ checkout → mvn package → mvn test → SonarQube + Quality Gate           │
          │ → docker build → push Docker Hub (1.0.0-<build>, latest) → scan Trivy  │
          │ → déclenche le job CD avec IMAGE_TAG=1.0.0-<build>                     │
          └────────────────────────────────┬───────────────────────────────────────┘
                                            │ HTTP (API Jenkins + jeton)
          ┌──── PIPELINE CD : gitops-register-app-cd (dépôt gitops-register-app) ──┐
          │ sed : deployment.yaml → image ...:1.0.0-<build>  → git commit + push   │
          └────────────────────────────────┬───────────────────────────────────────┘
                                            │ Git a changé
          ┌──────────────── ARGO CD (dans EKS) ─────────────▼──────────────────────┐
          │ détecte le commit → synchronise → rolling update du Deployment         │
          └────────────────────────────────────────────────────────────────────────┘
                     Service LoadBalancer :8080 ──► http://<lb>:8080/webapp/
```

**Serveurs** : `Jenkins-Master` (t3.small), `Jenkins-Agent` (t3.medium, Docker), `SonarQube` (t3.medium), `EKS-Bootstrap-Server` (t3.micro), plus le cluster EKS.

## Étape 1 — Jenkins master et agent

**1.1 — Deux instances Ubuntu 24.04**, 15 à 20 Go de disque : `Jenkins-Master` (`t3.small`, port 8080 ouvert depuis ton IP et GitHub) et `Jenkins-Agent` (`t3.medium`). Même Security Group ou SG qui autorise le SSH entre elles.

**1.2 — Sur les deux machines** :

```bash
sudo apt update && sudo apt upgrade -y
sudo hostnamectl set-hostname Jenkins-Master     # (Jenkins-Agent sur la seconde ! le tutoriel d'origine a une coquille)
exec bash
sudo apt install -y openjdk-21-jre
```

**1.3 — Sur le master** : installe Jenkins (annexe A.3). **Sur l'agent** : installe Docker et donne-le à ubuntu :

```bash
sudo apt install -y docker.io
sudo usermod -aG docker ubuntu
sudo reboot          # pour appliquer le groupe ; reconnecte-toi ensuite
```

**1.4 — Clé SSH master → agent.** Sur le **master** :

```bash
ssh-keygen -t ed25519 -N "" -f ~/.ssh/jenkins_agent
cat ~/.ssh/jenkins_agent.pub          # copie
```

Sur l'**agent** : colle la ligne dans `~/.ssh/authorized_keys` (le fichier s'appelle `authorized_keys`, avec un **s** : le tutoriel d'origine écrit `authorized_key`, ce qui ne fonctionne pas).

```bash
echo "<clé publique>" >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys
```

:::info Pas besoin de toucher à `sshd_config`
Le tutoriel d'origine modifie `/etc/ssh/sshd_config` (décommenter `PubkeyAuthentication` et `AuthorizedKeysFile`). Sur Ubuntu, ces options sont **déjà actives par défaut** : ce n'est pas nécessaire.
:::

**1.5 — Configurer Jenkins** (`http://<IP_MASTER>:8080`) :
- Débloque, installe les plugins suggérés, crée l'admin.
- *Manage Jenkins → Nodes → Built-In Node → Configure* : **0 exécuteur**.
- *Credentials* : *SSH Username with private key*, ID `Jenkins-Agent`, user `ubuntu`, clé = contenu de `~/.ssh/jenkins_agent` (la privée).
- *Nodes → New node* `Jenkins-Agent` (*Permanent*) : 2 exécuteurs, *Remote root* `/home/ubuntu`, **label `Jenkins-Agent`**, *Launch agents via SSH*, *Host* = IP **privée** de l'agent, credential `Jenkins-Agent`, *Non verifying*.
- Vérifie que l'agent est en ligne.

**1.6 — Outils et credentials pour le pipeline :**
- *Plugins* : **Maven Integration**, **Pipeline Maven Integration**, **Eclipse Temurin installer**, **SonarQube Scanner**, **Sonar Quality Gates**, **Docker**, **Docker Pipeline**, **Docker Commons**, **docker-build-step**, **CloudBees Docker Build and Publish**.
- *Tools* : Maven **`Maven3`** (auto-install) ; JDK **`Java17`** (auto-install depuis adoptium.net, version 17).
- *Credentials* : `github` (*Username with password* : ton pseudo + **token** GitHub ; GitHub refuse les mots de passe pour Git depuis 2021), `dockerhub` (*Username with password* : pseudo Docker Hub + **access token** Docker Hub).

## Étape 3 — SonarQube auto-hébergé

Instance Ubuntu 24.04 **`t3.medium`** (SonarQube embarque Elasticsearch : 4 Go de RAM minimum), 20 Go, port **9000** ouvert depuis ton IP et le SG de Jenkins.

Le tutoriel d'origine installe PostgreSQL et SonarQube « à la main » (zip + service systemd). La méthode la plus simple et la plus fiable aujourd'hui est **Docker Compose** (détails en annexe A.4) :

```bash
sudo apt update && sudo apt install -y docker.io docker-compose-v2
# Réglages noyau exigés par Elasticsearch (embarqué dans SonarQube)
echo "vm.max_map_count=524288" | sudo tee /etc/sysctl.d/99-sonarqube.conf
echo "fs.file-max=131072"      | sudo tee -a /etc/sysctl.d/99-sonarqube.conf
sudo sysctl --system

mkdir ~/sonarqube && cd ~/sonarqube
cat > compose.yaml <<'EOF'
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: sonar
      POSTGRES_PASSWORD: sonar_password_a_changer
      POSTGRES_DB: sonarqube
    volumes: [pgdata:/var/lib/postgresql/data]
    restart: unless-stopped
  sonarqube:
    image: sonarqube:community
    depends_on: [db]
    ports: ["9000:9000"]
    environment:
      SONAR_JDBC_URL: jdbc:postgresql://db:5432/sonarqube
      SONAR_JDBC_USERNAME: sonar
      SONAR_JDBC_PASSWORD: sonar_password_a_changer
    volumes:
      - sonar_data:/opt/sonarqube/data
      - sonar_extensions:/opt/sonarqube/extensions
      - sonar_logs:/opt/sonarqube/logs
    ulimits:
      nofile: { soft: 131072, hard: 131072 }
    restart: unless-stopped
volumes: { pgdata: {}, sonar_data: {}, sonar_extensions: {}, sonar_logs: {} }
EOF
sudo docker compose up -d
sudo docker compose logs -f sonarqube      # attends "SonarQube is operational"
```

:::why `vm.max_map_count`
Elasticsearch a besoin de nombreuses zones de mémoire mappée. Avec la valeur par défaut de Linux (65 530), SonarQube s'arrête au démarrage avec `max virtual memory areas vm.max_map_count [65530] is too low`. C'est l'équivalent des modifications de `/etc/sysctl.conf` et `/etc/security/limits.conf` du tutoriel d'origine.
:::

Ouvre `http://<IP_SONAR>:9000` → `admin` / `admin` → change le mot de passe.

**Relier SonarQube à Jenkins :**
1. SonarQube → *My Account → Security* → token **Global Analysis Token** `jenkins-sonarqube-token` → copie-le.
2. Jenkins → *Credentials* → *Secret text*, ID **`jenkins-sonarqube-token`**.
3. Jenkins → *System → SonarQube servers* : nom **`sonarqube-server`**, URL `http://<IP_PRIVEE_SONAR>:9000`, token `jenkins-sonarqube-token`.
4. Jenkins → *Tools → SonarQube Scanner installations* : `sonarqube-scanner` (auto-install).
5. SonarQube → *Administration → Configuration → Webhooks → Create* : `sonarqube-webhook`, URL `http://<IP_PRIVEE_JENKINS>:8080/sonarqube-webhook/`.

## Étape 4 — Le cluster EKS et le serveur bootstrap

1. Instance `EKS-Bootstrap-Server` (Ubuntu, `t3.micro`) avec un **rôle IAM** `eksctl_role` (*AdministratorAccess* pour ce lab).
2. Installe AWS CLI, kubectl et eksctl (partie 0, étape 5).
3. Crée le cluster :

```bash
eksctl create cluster --name io-register --region eu-west-3 \
  --node-type t3.medium --nodes 2 --nodes-min 2 --nodes-max 3 --managed
kubectl get nodes
```

*(Le tutoriel demande 3 nœuds `t2.small` ; 2 `t3.medium` offrent plus de capacité pour un coût proche.)*

## Étape 5 — Argo CD

```bash
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl get pods -n argocd -w

# CLI argocd (dernière version)
curl -sSL -o argocd https://github.com/argoproj/argo-cd/releases/latest/download/argocd-linux-amd64
sudo install -m 555 argocd /usr/local/bin/argocd && rm argocd

# Exposer l'interface (le tutoriel utilise un LoadBalancer ; port-forward est l'alternative gratuite)
kubectl patch svc argocd-server -n argocd -p '{"spec": {"type": "LoadBalancer"}}'
kubectl get svc argocd-server -n argocd           # EXTERNAL-IP au bout de 2 minutes

# Mot de passe initial de l'utilisateur admin
argocd admin initial-password -n argocd
```

Ouvre `https://<EXTERNAL-IP>` (accepte le certificat auto-signé), connecte-toi en `admin`, puis **change le mot de passe** (*User Info → Update password*).

```bash
argocd login <EXTERNAL-IP> --username admin --insecure
argocd cluster list
```

:::info Ajouter le cluster EKS à Argo CD : nécessaire ?
Le tutoriel ajoute le cluster EKS avec `argocd cluster add <contexte>`. **Argo CD tourne déjà dans ce cluster** et le connaît sous le nom `in-cluster` (`https://kubernetes.default.svc`) : on peut l'utiliser directement. `argocd cluster add` sert quand **un** Argo CD central pilote **plusieurs** clusters (dev, prod…). Fais-le pour t'entraîner :
```bash
kubectl config get-contexts
argocd cluster add <nom-du-contexte-eks> --name io-register-eks
argocd cluster list
```
:::

## Étape 6 — Le dépôt GitOps et le pipeline CD

1. **Fork** `github.com/MSFaizi/gitops-register-app`. Il contient `deployment.yaml`, `service.yaml` et un `Jenkinsfile`.
2. Dans ton fork : `deployment.yaml` → image `<toi>/register-app-pipeline:1.0.0-1` ; `Jenkinsfile` → URL de **ton** dépôt dans le `git` et le `git push`, ton nom et ton e-mail dans `git config`.

Le Jenkinsfile CD, expliqué :

```groovy
pipeline {
    agent { label "Jenkins-Agent" }
    environment { APP_NAME = "register-app-pipeline" }
    stages {
        stage("Cleanup Workspace") { steps { cleanWs() } }
        stage("Checkout from SCM") {
            steps { git branch: 'main', credentialsId: 'github', url: 'https://github.com/<toi>/gitops-register-app' }
        }
        stage("Update the Deployment Tags") {
            steps {
                // remplace "register-app-pipeline:<ancien tag>" par "register-app-pipeline:<IMAGE_TAG>"
                sh """
                   sed -i 's/${APP_NAME}.*/${APP_NAME}:${IMAGE_TAG}/g' deployment.yaml
                   cat deployment.yaml
                """
            }
        }
        stage("Push the changed deployment file to git") {
            steps {
                sh """
                   git config --global user.name "<ton nom>"
                   git config --global user.email "<ton e-mail>"
                   git add deployment.yaml
                   git commit -m "Updated Deployment manifest to ${IMAGE_TAG}"
                """
                withCredentials([gitUsernamePassword(credentialsId: 'github', gitToolName: 'Default')]) {
                    sh "git push https://github.com/<toi>/gitops-register-app main"
                }
            }
        }
    }
}
```

3. **Connecter le dépôt à Argo CD** : *Settings → Repositories → Connect repo* → HTTPS → URL de ton fork (dépôt public : pas d'identifiants ; privé : ton pseudo + un **token**, jamais ton mot de passe).
4. **Créer l'Application** : *New App* → nom `register-app`, projet `default`, *Sync policy* **Automatic** + **Prune resources** + **Self heal**, dépôt = ton fork, révision `HEAD`, chemin `./`, cluster `in-cluster` (ou celui ajouté), namespace `default` → *Create*.

```bash
kubectl get pods
kubectl get svc register-app-service      # EXTERNAL-IP
```

Ouvre `http://<EXTERNAL-IP>:8080/webapp/` : l'application d'inscription s'affiche.

5. **Le job CD dans Jenkins** : *New Item* `gitops-register-app-cd` → Pipeline → *Discard old builds* → **This project is parameterized** → *String Parameter* `IMAGE_TAG` → *Triggers* : **Trigger builds remotely** → token `gitops-token` → *Pipeline script from SCM* → ton fork gitops, branche `*/main` → *Save*.

6. **Le jeton d'API Jenkins** (pour que la CI puisse déclencher la CD) : ton profil Jenkins → *Security → API Token → Add new token* `JENKINS_API_TOKEN` → copie. Puis *Credentials* → *Secret text*, ID **`JENKINS_API_TOKEN`**.

7. **L'étape qui relie CI et CD**, dans le Jenkinsfile de `register-app` :

```groovy
stage("Trigger CD Pipeline") {
    steps {
        sh """
          curl -s -f --user <ton-user-jenkins>:${JENKINS_API_TOKEN} -X POST \
            --data 'IMAGE_TAG=${IMAGE_TAG}' \
            'http://<IP_PRIVEE_MASTER>:8080/job/gitops-register-app-cd/buildWithParameters?token=gitops-token'
        """
    }
}
```

:::why Pourquoi séparer CI et CD en deux dépôts et deux jobs
- Le dépôt **applicatif** contient le code ; le dépôt **GitOps** contient l'état désiré du cluster. Les droits peuvent différer (les développeurs poussent le code ; seule la CI modifie les manifests).
- Chaque déploiement est **un commit** dans le dépôt GitOps : historique complet, retour arrière par `git revert`.
- La CI **n'a aucun accès au cluster** : c'est Argo CD qui tire les changements. Moins de secrets à distribuer, moins de surface d'attaque.
:::

## Étape 7 — Le test de bout en bout

Modifie `webapp/src/main/webapp/index.jsp` dans ton fork `register-app`, commit, push. *(Pour un déclenchement automatique : webhook GitHub comme au projet 05, ou *Poll SCM* `H/2 * * * *` comme le propose le tutoriel. Le tutoriel indique `*`, c'est-à-dire chaque minute : trop agressif.)*

:::check
1. `register-app-ci` démarre : build, tests, analyse SonarQube (visible sur le tableau de bord SonarQube), image poussée sur Docker Hub avec le tag `1.0.0-<build>`, rapport Trivy dans la console.
2. `gitops-register-app-cd` démarre tout seul avec `IMAGE_TAG=1.0.0-<build>`.
3. Un nouveau commit « Updated Deployment manifest to 1.0.0-<build> » apparaît dans le dépôt GitOps.
4. Argo CD passe brièvement *OutOfSync* puis *Synced* ; les pods sont remplacés progressivement (`kubectl get pods -w`).
5. La page `http://<EXTERNAL-IP>:8080/webapp/` affiche ta modification.
6. **Self-heal** : `kubectl scale deploy register-app-deployment --replicas=5`. Quelques secondes plus tard, Argo CD remet 2 replicas (la valeur de Git).
:::

## Dépannage

:::fix
- **Le job CD ne démarre pas** : `curl` avec `-f` fait échouer l'étape en cas d'erreur HTTP. 401 → utilisateur ou jeton faux ; 403 → *Trigger builds remotely* non coché ou token `gitops-token` différent ; `Connection refused` → mauvaise IP/port.
- **`git push` refusé dans le job CD** : le credential `github` doit contenir un **token** avec le droit *Contents: Read and write* sur le dépôt GitOps.
- **`sed` ne remplace rien** : la ligne `image:` doit contenir exactement `register-app-pipeline` (variable `APP_NAME`).
- **Argo CD reste *OutOfSync*** : pas de synchro automatique (vérifie *Sync Policy*), ou erreur YAML : clique sur l'application pour lire le message.
- **SonarQube ne démarre pas** : `docker compose logs sonarqube` ; presque toujours `vm.max_map_count` ou manque de mémoire.
- **Trivy en Docker : `permission denied` sur docker.sock** : l'utilisateur de l'agent n'est pas dans le groupe docker (redémarre l'agent après l'ajout).
:::

## Nettoyage

:::clean
1. Supprime l'Application dans Argo CD (avec *cascade* : supprime aussi le Deployment et le Service, donc le load balancer de l'appli).
2. `kubectl delete svc argocd-server -n argocd` (ou repasse-le en ClusterIP) pour supprimer son load balancer.
3. `eksctl delete cluster --name io-register --region eu-west-3`.
4. *Terminate* les 4 instances EC2 ; supprime le rôle `eksctl_role`, les SG.
5. Supprime les webhooks GitHub ; garde tes forks et ton image Docker Hub.
:::
