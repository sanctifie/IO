## Ce qu'on construit

```ascii
 Navigateur ──► AWS Load Balancer (créé automatiquement par le Service) ──► Service "mygame-svc"
                                                                                 │ selector app=2048-ws
                                                ┌────────────────────────────────┴───────┐
 Cluster EKS "io-eks-1"                         │ Pod 2048   Pod 2048   Pod 2048         │
   plan de contrôle (géré par AWS)              │ (image blackicebird/2048, port 80)     │
   node group : 1 à 2 EC2 t3.medium             └────────────────────────────────────────┘
```

On va le faire **deux fois** : d'abord à la main dans la console (comme le dépôt d'origine), pour voir chaque brique ; puis en **une commande** avec `eksctl`, comme on le fait en vrai.

## Partie 1 — La méthode console (pour comprendre)

### Étape 1 — Les rôles IAM

Un cluster EKS a besoin de **deux** rôles :

**Rôle du cluster** (`eks-cluster-role`) : permet au plan de contrôle EKS de gérer des ressources AWS pour toi (interfaces réseau, load balancers). IAM → *Roles → Create role* → *AWS service* → **EKS** → cas d'usage **EKS - Cluster** → politique `AmazonEKSClusterPolicy`.

**Rôle des nœuds** (`eks-node-grp-role`) : permet aux EC2 des nœuds de rejoindre le cluster, de configurer le réseau des pods et de télécharger des images. *AWS service* → **EC2** → politiques :
- `AmazonEKSWorkerNodePolicy` (rejoindre le cluster),
- `AmazonEKS_CNI_Policy` (attribuer des IP du VPC aux pods),
- `AmazonEC2ContainerRegistryReadOnly` (télécharger depuis ECR).

### Étape 2 — Le cluster

EKS → *Clusters → Create cluster* → **Custom configuration** (désactive *EKS Auto Mode* pour ce premier essai, afin de voir les briques une à une) :

- Nom `io-eks-1`, rôle `eks-cluster-role`, version Kubernetes **par défaut proposée**.
- *Cluster access* : **EKS API** (access entries) ; coche *Allow cluster administrator access* pour ton identité.
- Réseau : VPC **par défaut**, 2 ou 3 subnets, Security Group par défaut ; *Endpoint access* : **Public**.
- Add-ons : garde les versions par défaut de **VPC CNI**, **CoreDNS**, **kube-proxy** (et *EKS Pod Identity Agent*).
- *Create*. Compte **10 à 15 minutes**, jusqu'à l'état **Active**.

### Étape 3 — Le node group

Cluster → onglet *Compute* → **Add node group** :
- Nom `io-eks-nodegrp-1`, rôle `eks-node-grp-role`.
- AMI : **Amazon Linux 2023** (par défaut), type **`t3.medium`**, disque 20 Go.
- Scaling : *desired* **1**, *min* **1**, *max* **2**.
- Subnets : ceux du cluster. *(L'accès SSH aux nœuds est optionnel ; inutile ici.)*
- *Create* : 2 à 3 minutes.

:::warn Pourquoi pas `t3.micro` ?
Chaque nœud EKS a un nombre maximal de pods, lié au nombre d'adresses IP que son type d'instance peut porter. Un `t3.micro` n'en accepte que 4, et les pods système (CoreDNS, kube-proxy, CNI…) en occupent déjà la plupart. Résultat : tes pods restent en `Pending`. `t3.medium` (17 pods) est le minimum confortable.
:::

### Étape 4 — S'authentifier auprès du cluster

Ouvre **CloudShell** (icône `>_` en haut de la console AWS : un terminal avec AWS CLI et kubectl déjà installés et authentifiés) ou ton terminal local :

```bash
aws sts get-caller-identity                              # qui suis-je pour AWS ?
aws eks update-kubeconfig --region eu-west-3 --name io-eks-1
# → écrit la configuration de connexion dans ~/.kube/config
kubectl get nodes
# NAME                                          STATUS   ROLES    AGE   VERSION
# ip-172-31-22-18.eu-west-3.compute.internal    Ready    <none>   3m    v1.3x.x
```

:::why Ce que fait `update-kubeconfig`
Il ajoute à `~/.kube/config` l'adresse de l'API du cluster, son certificat, et une commande (`aws eks get-token`) que kubectl appellera pour obtenir un jeton d'authentification à partir de ton identité IAM. EKS vérifie ensuite que cette identité a une **access entry** dans le cluster. Si tu as créé le cluster avec un autre utilisateur/rôle que celui de ton terminal, tu obtiendras `Unauthorized` : il faut alors ajouter une access entry pour ton identité (cluster → onglet *Access*).
:::

### Étape 5 — Un premier Pod

```yaml
# 2048-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: game-2048-pod          # (le nom "2048-pod" du dépôt d'origine est accepté, mais un nom commençant par une lettre est plus sûr)
  labels:
    app: 2048-ws
spec:
  containers:
  - name: game-2048
    image: blackicebird/2048
    ports:
    - containerPort: 80
```

```bash
kubectl apply -f 2048-pod.yaml
kubectl get pods -o wide
kubectl describe pod game-2048-pod      # lis la section Events : Scheduled → Pulling → Pulled → Created → Started
```

### Étape 6 — L'exposer avec un Service LoadBalancer

```yaml
# mygame-svc.yaml
apiVersion: v1
kind: Service
metadata:
  name: mygame-svc
spec:
  selector:
    app: 2048-ws               # doit correspondre EXACTEMENT au label du pod
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
  type: LoadBalancer
```

```bash
kubectl apply -f mygame-svc.yaml
kubectl get svc mygame-svc -w           # attends qu'EXTERNAL-IP passe de <pending> à un nom DNS (Ctrl+C pour arrêter)
kubectl describe svc mygame-svc         # "LoadBalancer Ingress: a06aa…elb.eu-west-3.amazonaws.com"
```

Ouvre `http://<nom-DNS>` dans ton navigateur (2 à 3 minutes de propagation) : **le jeu 2048 s'affiche.**

:::why Qui a créé ce load balancer ?
Tu n'as rien créé dans EC2. C'est le **contrôleur de service intégré** à EKS qui, voyant un Service de type `LoadBalancer`, a appelé l'API AWS pour créer un load balancer (Classic ou NLB) et y enregistrer les nœuds. Kubernetes pilote le cloud : c'est sa force… et la raison pour laquelle il faut **supprimer le Service avant le cluster**, sinon le load balancer reste orphelin et facturé.
:::

### Étape 7 — Passer du Pod au Deployment (et monter en charge)

Un Pod seul n'est **jamais** recréé s'il meurt. En vrai, on utilise un Deployment :

```bash
kubectl delete pod game-2048-pod
```

```yaml
# 2048-deploy.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: game-2048
spec:
  replicas: 3
  selector:
    matchLabels: { app: 2048-ws }
  template:
    metadata:
      labels: { app: 2048-ws }
    spec:
      containers:
      - name: game-2048
        image: blackicebird/2048
        ports: [{ containerPort: 80 }]
        resources:
          requests: { cpu: 50m, memory: 64Mi }
          limits:   { cpu: 200m, memory: 128Mi }
```

```bash
kubectl apply -f 2048-deploy.yaml
kubectl get pods -l app=2048-ws          # 3 pods ; le Service les a trouvés tout seul grâce au label
kubectl get endpoints mygame-svc         # les 3 IP de pods derrière le Service

# Expérience 1 : auto-réparation
kubectl delete pod <un-des-pods>
kubectl get pods -l app=2048-ws -w       # un nouveau pod apparaît aussitôt

# Expérience 2 : mise à l'échelle
kubectl scale deployment game-2048 --replicas=6
kubectl get pods -o wide                 # si un nœud ne suffit pas : des pods en Pending → augmente le node group à 2
```

:::check
- `kubectl get nodes` montre tes nœuds `Ready`.
- Le jeu est accessible par le nom DNS du load balancer.
- Supprimer un pod ne coupe pas le jeu, et un nouveau pod le remplace.
:::

## Partie 2 — La même chose en une commande avec eksctl

Supprime d'abord tout ce qui précède (voir *Nettoyage*), puis :

```bash
eksctl create cluster \
  --name io-eks-2 --region eu-west-3 \
  --nodegroup-name workers --node-type t3.medium \
  --nodes 1 --nodes-min 1 --nodes-max 2 --managed
# 15 à 20 minutes : eksctl crée un VPC dédié, les rôles, le cluster, le node group, et configure kubectl

kubectl get nodes
kubectl apply -f 2048-deploy.yaml -f mygame-svc.yaml
```

:::why Ce qu'eksctl fait pour toi
Il génère et déploie des piles **CloudFormation** (visibles dans la console CloudFormation : `eksctl-io-eks-2-cluster`, `eksctl-io-eks-2-nodegroup-workers`) : un VPC propre avec subnets publics et privés, une NAT Gateway, les rôles IAM, le cluster et les nœuds. Et `eksctl delete cluster` supprime tout dans le bon ordre. Pour un cluster d'apprentissage, c'est la méthode recommandée.
:::

*(En production, on décrit plutôt le cluster en **Terraform** (projet 19), ou avec un fichier de configuration eksctl versionné : `eksctl create cluster -f cluster.yaml`.)*

## Dépannage

:::fix
- **`error: You must be logged in to the server (Unauthorized)`** : ton identité IAM n'a pas d'access entry. Cluster → *Access* → *Create access entry* → ton utilisateur/rôle → politique `AmazonEKSClusterAdminPolicy`.
- **Nœuds absents de `kubectl get nodes`** : le node group est en échec (onglet *Compute* → *Health issues*) ; souvent un rôle de nœud sans les 3 politiques, ou des subnets sans accès Internet (ni IP publique, ni NAT) qui empêchent les nœuds de joindre l'API.
- **Pods en `Pending`** : `kubectl describe pod` → `Too many pods` ou `Insufficient cpu` : augmente le node group ou le type d'instance.
- **`EXTERNAL-IP` reste `<pending>`** : les subnets publics doivent porter le tag `kubernetes.io/role/elb=1` pour que Kubernetes sache où créer le load balancer (eksctl les tague automatiquement ; le VPC par défaut parfois non). `kubectl describe svc` donne l'erreur exacte.
- **`exec format error`** : image construite pour ARM sur des nœuds x86 (ou l'inverse).
:::

## Nettoyage

:::clean
**L'ordre est important.**
1. **Supprime le Service** d'abord : `kubectl delete svc mygame-svc` (supprime le load balancer AWS). Vérifie dans EC2 → *Load Balancers* qu'il a disparu.
2. `kubectl delete deployment game-2048`.
3. **Cluster console** : supprime le node group (*Compute → Delete*), attends, puis supprime le cluster. **Cluster eksctl** : `eksctl delete cluster --name io-eks-2 --region eu-west-3`.
4. Vérifie CloudFormation (aucune pile `eksctl-…` restante), EC2 (instances, volumes), VPC (NAT Gateway, Elastic IP).
5. Les rôles IAM peuvent rester (gratuits) pour les projets suivants.
:::

## Pour aller plus loin

- Remplace le Service `LoadBalancer` par un **Ingress** avec l'AWS Load Balancer Controller (projet 15).
- Ajoute un **HorizontalPodAutoscaler** (`kubectl autoscale deployment game-2048 --cpu-percent=50 --min=2 --max=10`) : il nécessite le *metrics-server* (`kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml`).
- Essaie **EKS Auto Mode** : AWS gère aussi les nœuds, le stockage et les load balancers.
- Construis ta propre image du jeu (le code est open source) et pousse-la dans ECR.
