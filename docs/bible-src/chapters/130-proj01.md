## Ce qu'on construit

Une application web Java de connexion/inscription d'employés, déployée selon l'architecture la plus classique du web : **3 tiers** (3 couches), chacune isolée, redondante et capable de grandir.

```ascii
 Utilisateur ── HTTP 80 ──► [ NLB public ]                         (subnets publics)
                                  │
                       ┌──────────┴──────────┐
 TIER 1 : présentation │  Nginx    Nginx     │ ASG Nginx           (subnets privés app)
 (reverse proxy)       └──────────┬──────────┘
                                  │ 8080
                           [ NLB interne ]
                       ┌──────────┴──────────┐
 TIER 2 : application  │ Tomcat    Tomcat    │ ASG Tomcat          (subnets privés app)
 (Java .war)           └──────────┬──────────┘    ▲ au démarrage : télécharge le .war depuis JFrog
                                  │ 3306           │
 TIER 3 : données          [ RDS MySQL ]           │                (subnets privés DB)
                                                   │
 CHAÎNE DE BUILD :  GitHub ──► serveur Maven ──► SonarCloud (qualité)
                                      └────────► JFrog Artifactory (stockage du .war)

 ADMIN : bastion (VPC 192.168.0.0/16) ── Transit Gateway ──► VPC app 172.32.0.0/16 ;  SSM Session Manager
 EXPLOITATION : cron → logs Tomcat vers S3 ;  alarme CloudWatch « connexions DB > 100 » → e-mail (SNS)
```

## Les concepts du projet

:::why Pourquoi 3 tiers ?
Chaque couche a un rôle et des besoins différents :
- **Présentation** (Nginx) : reçoit le trafic Internet, sert les fichiers statiques, termine le HTTPS, protège l'application.
- **Application** (Tomcat + Java) : exécute la logique métier. C'est souvent la couche la plus gourmande, qu'on veut faire grandir indépendamment.
- **Données** (MySQL) : stocke l'information. C'est la couche la plus précieuse et la plus protégée.

Séparer les couches permet de les **faire grandir indépendamment**, de les **sécuriser séparément** (la base n'accepte que les connexions des serveurs Tomcat) et de **les mettre à jour séparément**.
:::

:::why Pourquoi un dépôt d'artefacts (JFrog) ?
Le serveur qui **compile** le code (Maven) n'est pas celui qui l'**exécute** (Tomcat). Entre les deux, il faut un endroit fiable où stocker les livrables versionnés (`dptweb-1.0.war`, `dptweb-1.1.war`…) : c'est le **dépôt d'artefacts** (*artifact repository*). Avantages : on déploie exactement le binaire qui a été testé, on peut revenir à une version précédente, et les nouveaux serveurs de l'ASG téléchargent tout seuls la bonne version au démarrage. Les alternatives sont **Nexus** (projet 30), **AWS CodeArtifact**, ou un simple bucket S3.
:::

:::why Pourquoi une analyse SonarCloud ?
SonarCloud (version en ligne de SonarQube) lit le code source et détecte les **bugs**, les **failles de sécurité**, le **code dupliqué** et les mauvaises pratiques. Une **Quality Gate** (porte de qualité) définit des seuils : si le nouveau code ne les respecte pas, la porte est « rouge » et on peut bloquer la livraison. Tu vas voir que cette application contient une vraie faille, une **injection SQL**, et que SonarCloud la trouve.
:::

## Étape 1 — Les AMI : Global, puis trois Golden

**1.1 — La Global AMI** : Amazon Linux 2023 avec AWS CLI (préinstallée), agent SSM (préinstallé) et agent CloudWatch configuré pour la mémoire. C'est exactement l'étape 1 du projet 02, **sans Apache**. Nomme l'AMI `io-global-v1`.

**1.2 — Golden AMI Nginx.** Lance une instance depuis `io-global-v1`, puis :

```bash
sudo dnf install -y nginx
sudo systemctl enable nginx
```

Crée l'AMI `io-golden-nginx-v1`, termine l'instance.

**1.3 — Golden AMI Tomcat.** Lance une instance depuis `io-global-v1`, puis :

```bash
# Java 11 (Amazon Corretto, la distribution OpenJDK d'Amazon)
sudo dnf install -y java-11-amazon-corretto-headless
java -version

# Tomcat 9 — dernière version 9.0.x sur https://dlcdn.apache.org/tomcat/tomcat-9/
TOMCAT_VERSION=9.0.<xx>
cd /tmp
curl -fLO "https://dlcdn.apache.org/tomcat/tomcat-9/v${TOMCAT_VERSION}/bin/apache-tomcat-${TOMCAT_VERSION}.tar.gz"
sudo mkdir -p /opt/tomcat
sudo tar -xzf apache-tomcat-${TOMCAT_VERSION}.tar.gz -C /opt/tomcat --strip-components=1

# Un utilisateur système dédié : Tomcat ne doit pas tourner en root
sudo useradd -r -M -d /opt/tomcat -s /sbin/nologin tomcat
sudo chown -R tomcat:tomcat /opt/tomcat
sudo rm -rf /opt/tomcat/webapps/*          # retirer les applications d'exemple (surface d'attaque)
```

:::warn Tomcat 9, pas Tomcat 10 ou 11
Tomcat 10 et suivants utilisent les nouveaux noms de paquets Java `jakarta.*` au lieu de `javax.*`. Cette application (Spring Boot 2.2) utilise `javax.*` : sur Tomcat 10, le `.war` se déploie mais renvoie des erreurs 404/500 incompréhensibles. **La version de la plateforme doit correspondre à celle de l'application** : leçon valable bien au-delà de Tomcat.
:::

Crée le service systemd :

```bash
sudo tee /etc/systemd/system/tomcat.service > /dev/null <<'EOF'
[Unit]
Description=Apache Tomcat 9
After=network.target

[Service]
Type=forking
User=tomcat
Group=tomcat
Environment=JAVA_HOME=/usr/lib/jvm/java-11-amazon-corretto
Environment=CATALINA_HOME=/opt/tomcat
Environment=CATALINA_PID=/opt/tomcat/temp/tomcat.pid
Environment="CATALINA_OPTS=-Xms256m -Xmx512m"
# Fichier optionnel (le "-" devant) qui contiendra les variables de l'application
EnvironmentFile=-/etc/default/dptweb
ExecStart=/opt/tomcat/bin/startup.sh
ExecStop=/opt/tomcat/bin/shutdown.sh
Restart=on-failure

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now tomcat
curl -I http://localhost:8080        # réponse HTTP (404 normal : webapps est vide)
```

Ajoute la collecte des logs Tomcat dans la configuration de l'agent CloudWatch si tu le souhaites, puis crée l'AMI `io-golden-tomcat-v1`.

**1.4 — Golden AMI Maven** (le serveur de build).

```bash
sudo dnf install -y git java-17-amazon-corretto-devel
MAVEN_VERSION=3.9.<x>          # dernière version sur https://maven.apache.org/download.cgi
cd /tmp
curl -fLO "https://dlcdn.apache.org/maven/maven-3/${MAVEN_VERSION}/binaries/apache-maven-${MAVEN_VERSION}-bin.tar.gz"
sudo tar -xzf apache-maven-${MAVEN_VERSION}-bin.tar.gz -C /opt
sudo ln -s /opt/apache-maven-${MAVEN_VERSION} /opt/maven

# Mettre Maven dans le PATH de tous les utilisateurs
sudo tee /etc/profile.d/maven.sh > /dev/null <<'EOF'
export JAVA_HOME=/usr/lib/jvm/java-17-amazon-corretto
export M2_HOME=/opt/maven
export PATH=$M2_HOME/bin:$PATH
EOF
source /etc/profile.d/maven.sh
mvn -version
```

:::why Java 17 pour builder, Java 11 pour exécuter ?
Le scanner SonarCloud exige **Java 17 ou plus** pour s'exécuter. Le code, lui, est compilé pour Java 8 (`<java.version>1.8</java.version>` dans le `pom.xml`), donc le `.war` produit tourne sans problème sur le Java 11 de Tomcat. Un JDK récent sait produire du code pour une version plus ancienne : c'est le rôle de l'option `release` du compilateur.
:::

Crée l'AMI `io-golden-maven-v1`.

:::tip Le lien symbolique `/opt/maven`
`/opt/maven` pointe vers `/opt/apache-maven-3.9.x`. Pour mettre Maven à jour, on installe la nouvelle version à côté et on déplace le lien : rien d'autre à modifier. C'est une astuce d'administration très courante.
:::

## Étape 2 — Préparer JFrog et SonarCloud

**2.1 — JFrog.** Crée un compte sur `jfrog.com` (essai gratuit / plateforme cloud). Dans ton instance (`https://<nom>.jfrog.io`) :

1. *Administration → Repositories → Create repository → Local → Maven* : clé **`libs-release-local`**.
2. *Create → Remote → Maven* : clé **`maven-remote`** (URL par défaut : Maven Central). Il servira de cache pour les dépendances.
3. *Create → Virtual → Maven* : clé **`libs-release`**, qui regroupe `libs-release-local` et `maven-remote`.
4. Ton profil → *Edit profile* → **Generate an Identity Token** (ou *Access token*). Note ton nom d'utilisateur et ce jeton.

:::why Local, Remote, Virtual
- **Local** : tes propres artefacts (ton `.war`).
- **Remote** : un cache d'un dépôt externe (Maven Central). Si Maven Central est indisponible, ou si une dépendance disparaît d'Internet, ton build continue de fonctionner.
- **Virtual** : une seule URL qui agrège les deux. Maven n'a qu'une adresse à connaître.
:::

**2.2 — SonarCloud.** Connecte-toi sur `sonarcloud.io` avec ton compte GitHub → *+ → Create new organization* (gratuite pour les projets publics) → *Analyze new project* → choisis le dépôt de l'application → méthode d'analyse **« With other CI tools » / Manually**, build **Maven**. Note la **clé d'organisation** et la **clé de projet**. *My Account → Security* → génère un **token**.

## Étape 3 — Préparer le code de l'application

**3.1** — Crée un dépôt GitHub `java-login-app` (public, pour SonarCloud gratuit) et copie-y le contenu de `DevOps-Project-01/Java-Login-App` du dépôt d'origine. Ouvre-le dans VS Code.

**3.2 — Modifier le `pom.xml`.** Remplace le bloc `<distributionManagement>` et ajoute les propriétés Sonar :

```xml
<properties>
    <java.version>1.8</java.version>
    <!-- versions de plugins récentes, compatibles avec un JDK 17 -->
    <maven-war-plugin.version>3.4.0</maven-war-plugin.version>
    <!-- SonarCloud -->
    <sonar.organization>TON-ORGANISATION</sonar.organization>
    <sonar.projectKey>TON-ORGANISATION_java-login-app</sonar.projectKey>
    <sonar.host.url>https://sonarcloud.io</sonar.host.url>
</properties>

<distributionManagement>
    <repository>
        <id>central</id>
        <name>libs-release-local</name>
        <url>https://TON-NOM.jfrog.io/artifactory/libs-release-local</url>
    </repository>
</distributionManagement>
```

:::warn Pourquoi surcharger `maven-war-plugin` ?
Spring Boot 2.2 impose par défaut la version 3.2.3 du plugin WAR, qui plante sous Java 16+ avec une erreur du type `Unable to make field … TreeMap.comparator accessible`. Surcharger la propriété `maven-war-plugin.version` règle le problème sans toucher au reste. **Quand une vieille application refuse de se construire sur un JDK récent, c'est presque toujours un plugin trop ancien.**
:::

**3.3 — Le `settings.xml`, sans mot de passe en clair.** Le fichier du dépôt d'origine contient un e-mail et un mot de passe **en clair**. Ne reproduis jamais ça. Utilise des variables d'environnement :

```xml
<?xml version="1.0" encoding="UTF-8"?>
<settings xmlns="http://maven.apache.org/SETTINGS/1.2.0">
  <servers>
    <server>
      <id>central</id>
      <username>${env.JFROG_USER}</username>
      <password>${env.JFROG_TOKEN}</password>
    </server>
  </servers>
  <mirrors>
    <mirror>
      <id>central</id>
      <mirrorOf>*</mirrorOf>
      <url>https://TON-NOM.jfrog.io/artifactory/libs-release</url>
    </mirror>
  </mirrors>
</settings>
```

- `<servers>` : les identifiants associés à l'`id` `central` (le même `id` que dans `distributionManagement` et dans le miroir).
- `<mirrors>` : « pour télécharger **toutes** les dépendances (`mirrorOf *`), passe par mon dépôt virtuel JFrog ».

**3.4 — La configuration de la base de données** n'est **pas** écrite dans `application.properties` (le dépôt d'origine y mettait le mot de passe). Spring Boot lit automatiquement les **variables d'environnement** : `SPRING_DATASOURCE_URL` remplace `spring.datasource.url`, etc. On les fournira à Tomcat au démarrage (étape 6). Laisse donc `application.properties` sans identifiants.

:::why Les « 12 facteurs »
La méthodologie *Twelve-Factor App* (une référence du développement cloud) dit : **la configuration doit être séparée du code et fournie par l'environnement**. Le même `.war` doit pouvoir tourner en test et en production ; seules les variables changent. Et un mot de passe ne doit jamais se retrouver dans Git.
:::

**3.5 — Le flux Git demandé par l'énoncé.**

```bash
git checkout -b feature/jfrog-sonar
git add pom.xml settings.xml
git commit -m "Configure JFrog et SonarCloud"
git push -u origin feature/jfrog-sonar
```

Sur GitHub : **Compare & pull request** → relis les changements → **Merge pull request** → supprime la branche. Tu viens d'appliquer le flux de travail standard de toutes les équipes : **branche de fonctionnalité → pull request → relecture → fusion dans `main`**.

## Étape 4 — Construire et analyser

Lance une instance depuis `io-golden-maven-v1` (dans un subnet privé de `io-app-vpc`, rôle avec SSM), connecte-toi par Session Manager ou par le bastion :

```bash
git clone https://github.com/<toi>/java-login-app.git && cd java-login-app

export JFROG_USER='ton-user-jfrog'
read -s JFROG_TOKEN && export JFROG_TOKEN     # saisie masquée : rien dans l'historique
read -s SONAR_TOKEN && export SONAR_TOKEN

# Compiler, tester, analyser, puis publier le .war dans JFrog
mvn -s settings.xml clean verify sonar:sonar -Dsonar.token=$SONAR_TOKEN
mvn -s settings.xml deploy -DskipTests
```

:::why Le cycle de vie Maven
Maven enchaîne des **phases** dans un ordre fixe : `validate → compile → test → package → verify → install → deploy`. Demander une phase exécute toutes les précédentes. `package` produit le `.war` dans `target/` ; `deploy` l'envoie vers le dépôt déclaré dans `distributionManagement`. `clean` vide d'abord le dossier `target/`. `-s settings.xml` dit à Maven d'utiliser *ce* fichier de configuration.
:::

:::check
- `target/dptweb-1.0.war` existe.
- Dans JFrog : *Artifactory → Artifacts → libs-release-local → com/devopsrealtime/dptweb/1.0/dptweb-1.0.war*.
- Dans SonarCloud : le tableau de bord du projet affiche bugs, vulnérabilités, *security hotspots* et l'état de la Quality Gate. Ouvre les problèmes de sécurité : SonarCloud signale la **requête SQL construite par concaténation** dans `login.java` et `register.java`.
:::

:::danger L'injection SQL de cette application
```java
String query = "select * from Employee where username='" + userName + "' and password='" + password + "'";
```
Si quelqu'un tape `' OR '1'='1` comme mot de passe, la requête devient `... and password='' OR '1'='1'`, toujours vraie : **connexion sans mot de passe**. De plus, les mots de passe sont stockés en clair. C'est une application d'exercice ; ne la laisse pas en ligne plus longtemps que nécessaire. La correction (exercice bonus) : utiliser un `PreparedStatement` avec des paramètres `?`, et hacher les mots de passe (BCrypt).
:::

**Bonus** : renomme l'artefact pour que l'application soit servie à la racine du site. Ajoute dans le `pom.xml`, section `<build>` : `<finalName>ROOT</finalName>`. Tomcat sert `ROOT.war` sur `/` au lieu de `/dptweb-1.0/`. *(Le nom dans JFrog reste versionné ; c'est le nom local qui change. Dans la suite, on renomme simplement le fichier au téléchargement.)*

## Étape 5 — La base de données RDS

**5.1 — Security Groups** (dans `io-app-vpc`) :

| SG | Entrée | Source |
|---|---|---|
| `io-db-sg` | MySQL 3306 | `io-tomcat-sg` **et** `192.168.1.0/24` (bastion) |
| `io-tomcat-sg` | 8080 | `172.32.0.0/16` (le NLB interne, dont les IP sont dans le VPC) ; 22 depuis `192.168.1.0/24` |
| `io-nginx-sg` | 80 | `io-public-nlb-sg` ; 22 depuis `192.168.1.0/24` |
| `io-public-nlb-sg` | 80 | `0.0.0.0/0` |

**5.2 — DB subnet group** : RDS → *Subnet groups* → *Create* → `io-db-subnets`, VPC `io-app-vpc`, subnets `db-private-a` et `db-private-b`.

**5.3 — Créer la base** : RDS → *Create database* :

- *Standard create*, moteur **MySQL**, version **8.4** (la 8.0 est en fin de support standard).
- Modèle : **Free tier** si proposé, sinon *Dev/Test*.
- Identifiant `io-db`, utilisateur `admin`, mot de passe : **Manage master credentials in AWS Secrets Manager** *(recommandé)* ou un mot de passe fort que tu notes.
- Classe `db.t4g.micro`, stockage 20 Go gp3, **pas d'autoscaling du stockage**.
- **Multi-AZ** : l'énoncé le demande. Coche *Create a standby instance* pour voir le fonctionnement, **mais sache que ça double le coût** ; pour l'apprentissage, Single-AZ suffit.
- Connectivité : VPC `io-app-vpc`, subnet group `io-db-subnets`, *Public access* **No**, SG `io-db-sg`.
- *Additional configuration* : sauvegardes 1 jour, désactive la protection contre la suppression.

Note le **endpoint** (ex. `io-db.xxxxxx.eu-west-3.rds.amazonaws.com`).

**5.4 — Stocker la configuration dans SSM Parameter Store** :

```bash
aws ssm put-parameter --name /io/01/db/url --type String \
  --value "jdbc:mysql://io-db.xxxxxx.eu-west-3.rds.amazonaws.com:3306/UserDB?sslMode=REQUIRED"
aws ssm put-parameter --name /io/01/db/user --type String --value admin
aws ssm put-parameter --name /io/01/db/password --type SecureString --value '<mot-de-passe>'
aws ssm put-parameter --name /io/01/jfrog/token --type SecureString --value '<token-jfrog>'
```

Ajoute au rôle des instances Tomcat une politique autorisant `ssm:GetParameter` et `ssm:GetParameters` sur `arn:aws:ssm:eu-west-3:<compte>:parameter/io/01/*` (et `kms:Decrypt` si tu utilises une clé KMS personnalisée ; la clé par défaut `aws/ssm` est autorisée automatiquement).

:::why `sslMode=REQUIRED`
Sur RDS MySQL 8.4, le paramètre `require_secure_transport` est activé par défaut : la base **refuse** les connexions non chiffrées. `sslMode=REQUIRED` demande au pilote JDBC de chiffrer la connexion en TLS. Bonus : c'est aussi une bonne pratique de sécurité.
:::

**5.5 — Créer le schéma** depuis le bastion (ou une instance Tomcat) :

```bash
sudo dnf install -y mariadb105        # fournit le client "mysql"
mysql -h io-db.xxxxxx.eu-west-3.rds.amazonaws.com -u admin -p
```

## Étape 6 — Le tier application (Tomcat)

**6.1 — NLB interne.** Target Group `io-tomcat-tg` : instances, TCP **8080**, VPC `io-app-vpc`, health check HTTP sur `/` *(ou sur `/login` si `/` renvoie une redirection)*. Load balancer **Network**, schéma **Internal**, subnets `app-private-a/b`, listener TCP 8080 → `io-tomcat-tg`. Note son nom DNS (`internal-…` ou `io-tomcat-nlb-….elb.eu-west-3.amazonaws.com`).

**6.2 — Launch Template `io-tomcat-lt`** : AMI `io-golden-tomcat-v1`, `t3.small` (Java aime la mémoire), SG `io-tomcat-sg`, rôle IAM avec SSM et lecture des paramètres, IMDSv2, et ce user data :

```bash
#!/bin/bash
set -euxo pipefail
exec > /var/log/user-data.log 2>&1
REGION=eu-west-3
JFROG_URL=https://TON-NOM.jfrog.io/artifactory/libs-release-local
JFROG_USER=ton-user-jfrog
APP_VERSION=1.0

p() { aws ssm get-parameter --region $REGION --name "$1" --with-decryption --query Parameter.Value --output text; }

# 1. Variables de l'application, lues dans Parameter Store
cat > /etc/default/dptweb <<EOF
SPRING_DATASOURCE_URL=$(p /io/01/db/url)
SPRING_DATASOURCE_USERNAME=$(p /io/01/db/user)
SPRING_DATASOURCE_PASSWORD=$(p /io/01/db/password)
EOF
chmod 600 /etc/default/dptweb

# 2. Télécharger le .war depuis JFrog et le déployer à la racine
curl -fsSL -u "$JFROG_USER:$(p /io/01/jfrog/token)" \
  -o /opt/tomcat/webapps/ROOT.war \
  "$JFROG_URL/com/devopsrealtime/dptweb/$APP_VERSION/dptweb-$APP_VERSION.war"
chown tomcat:tomcat /opt/tomcat/webapps/ROOT.war

systemctl restart tomcat
```

**6.3 — ASG `io-tomcat-asg`** : Launch Template `io-tomcat-lt`, subnets `app-private-a/b`, Target Group `io-tomcat-tg`, health checks ELB activés, capacité 2/2/4.

:::check
Depuis le bastion : `curl -I http://<DNS-NLB-interne>:8080/` répond (200 ou 302). Si ce n'est pas le cas, regarde `/var/log/user-data.log` et `/opt/tomcat/logs/catalina.out` sur une instance.
:::

## Étape 7 — Le tier présentation (Nginx)

**7.1 — NLB public** : Target Group `io-nginx-tg` (TCP 80), NLB *Internet-facing* dans `app-public-a/b`, SG `io-public-nlb-sg`, listener TCP 80 → `io-nginx-tg`.

**7.2 — Launch Template `io-nginx-lt`** : AMI `io-golden-nginx-v1`, `t3.micro`, SG `io-nginx-sg`, rôle SSM, user data :

```bash
#!/bin/bash
set -euxo pipefail
BACKEND=<DNS-du-NLB-interne>
cat > /etc/nginx/conf.d/dptweb.conf <<EOF
server {
    listen 80 default_server;
    server_name _;
    location / {
        proxy_pass http://$BACKEND:8080;
        proxy_set_header Host \$host;
        proxy_set_header X-Real-IP \$remote_addr;
        proxy_set_header X-Forwarded-For \$proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto \$scheme;
    }
}
EOF
# Désactiver le "server" par défaut du nginx.conf d'Amazon Linux pour éviter le conflit
sed -i 's/listen       80;/listen 8081;/; s/listen       \[::\]:80;/listen [::]:8081;/' /etc/nginx/nginx.conf
nginx -t && systemctl reload nginx
```

:::why `\$host` avec un antislash ?
Dans un heredoc **sans** guillemets (`<<EOF`), Bash remplace les variables : `$BACKEND` devient le nom DNS, c'est voulu. Mais `$host` et `$remote_addr` sont des variables **de Nginx**, qui doivent arriver telles quelles dans le fichier : on les protège avec `\`. Mélanger variables du shell et variables de l'application dans un même fichier est une source d'erreurs classique.
:::

:::why Ce que font les `proxy_set_header`
Sans eux, Tomcat croit que toutes les requêtes viennent de Nginx. `X-Real-IP` et `X-Forwarded-For` transmettent l'IP du vrai visiteur ; `Host` et `X-Forwarded-Proto` permettent à l'application de générer des liens corrects.
:::

## Étape 9 — Post-déploiement : logs vers S3 et alarme

**9.1 — Envoyer les logs Tomcat vers S3 avec cron.** Crée un bucket `io-01-logs-<prenom>`, autorise le rôle Tomcat à y écrire (`s3:PutObject` sur `arn:aws:s3:::io-01-logs-<prenom>/*`). Ajoute dans le user data Tomcat (ou dans l'AMI) :

```bash
cat > /usr/local/bin/ship-tomcat-logs.sh <<'EOF'
#!/bin/bash
# Envoie vers S3 les logs Tomcat des jours précédents, puis les supprime localement
set -euo pipefail
BUCKET=io-01-logs-<prenom>
IID=$(cat /var/lib/cloud/data/instance-id)
cd /opt/tomcat/logs
# fichiers datés (catalina.2026-10-03.log, localhost_access_log.2026-10-03.txt...) de plus d'un jour
find . -maxdepth 1 -type f -name '*.20*' -mtime +0 | while read -r f; do
  aws s3 cp "$f" "s3://$BUCKET/$IID/${f#./}" && rm -f "$f"
done
EOF
chmod +x /usr/local/bin/ship-tomcat-logs.sh
dnf install -y cronie && systemctl enable --now crond
echo "15 0 * * * root /usr/local/bin/ship-tomcat-logs.sh >> /var/log/ship-logs.log 2>&1" > /etc/cron.d/ship-tomcat-logs
```

:::why Pourquoi c'est indispensable avec l'auto-scaling
Une instance peut être détruite à tout moment par l'ASG : ses logs disparaissent avec elle. Il faut les **sortir** de la machine. Ce script le fait une fois par jour ; en production, on préfère une collecte en continu (agent CloudWatch Logs, Fluent Bit…), qu'on verra plus tard. Ajoute aussi une **règle de cycle de vie** sur le bucket (S3 → *Management → Lifecycle rule*) pour passer les logs en stockage froid après 30 jours et les supprimer après 365 jours.
:::

## Dépannage

:::fix
- **502 Bad Gateway sur le NLB public** : c'est Nginx qui répond, mais il n'arrive pas à joindre Tomcat. Vérifie le nom du NLB interne dans `/etc/nginx/conf.d/dptweb.conf`, l'état des cibles de `io-tomcat-tg`, et que `io-tomcat-sg` autorise 8080 depuis le VPC.
- **404 Tomcat** : le `.war` n'a pas été téléchargé (regarde `/var/log/user-data.log` : un 401 signifie un jeton JFrog incorrect, un 404 un mauvais chemin), ou tu es sur Tomcat 10.
- **Page d'erreur après connexion / `Communications link failure`** : Tomcat n'arrive pas à joindre RDS. Vérifie `io-db-sg` (source `io-tomcat-sg`), l'URL JDBC, et `cat /etc/default/dptweb`. Un `Access denied` vient de l'utilisateur ou du mot de passe ; `Unknown database` signifie que `CREATE DATABASE` n'a pas été fait.
- **Maven : `401 Unauthorized` au `deploy`** : l'`id` du `<server>` ne correspond pas à l'`id` du `<repository>`, ou les variables `JFROG_USER`/`JFROG_TOKEN` ne sont pas exportées dans **ce** terminal.
- **Maven : `Could not resolve dependencies`** : le miroir JFrog est mal configuré (URL du dépôt *virtual*) ou le dépôt remote n'a pas accès à Maven Central.
- **SonarCloud : `Project not found`** : vérifie `sonar.organization` et `sonar.projectKey` (sensibles à la casse) et le token.
:::

## Nettoyage

:::clean
1. ASG Nginx et ASG Tomcat (supprime les instances), puis les deux NLB et leurs Target Groups.
2. Instance Maven, bastion, Elastic IPs.
3. **RDS** : *Delete* → décoche *Create final snapshot* (sauf si tu veux le garder) → confirme. Supprime ensuite le secret Secrets Manager s'il a été créé.
4. NAT Gateway, Transit Gateway (attachements d'abord), VPC.
5. Buckets S3, paramètres SSM (`aws ssm delete-parameters --names ...`), topic SNS, alarme.
6. Désenregistre les AMI que tu ne garderas pas et supprime leurs snapshots.
7. Garde le compte SonarCloud et JFrog pour les projets suivants (désactive JFrog s'il s'agit d'un essai payant à la fin).
:::
