## Ce qu'on construit

Le même type de résultat que le projet 08 (un jeu dans EKS), mais le cluster est cette fois **créé par Terraform**, depuis une machine d'administration dédiée.

```ascii
 Toi ──SSH──► EC2 "bootstrap" (Ubuntu) ── rôle IAM ──► API AWS
               │ script.sh : Terraform + kubectl + AWS CLI
               │ terraform apply  (état dans S3)
               ▼
         EKS "EKS_CLOUD" (VPC par défaut)
           node group 1 × t3.medium
           Deployment mario (2 replicas, image sevenajay/mario) ── Service LoadBalancer ──► navigateur
```

:::why Pourquoi une machine « bootstrap » ?
On centralise les outils et les droits sur une machine d'administration, avec un **rôle IAM** plutôt que des clés sur ton portable. C'est une pratique courante (on parle aussi de *jump box* ou de *bastion d'administration*). En entreprise, on remplace souvent cette machine par un pipeline CI.
:::

## Étape 1 — La machine bootstrap

1. **Rôle IAM** : IAM → *Create role* → *AWS service* → *EC2* → politique `AdministratorAccess` → nom `io-bootstrap-role`. *(Acceptable pour un lab jetable ; en entreprise, on limiterait aux droits EKS/EC2/IAM nécessaires.)*
2. **Instance** : Ubuntu 24.04, `t3.micro`, SG SSH depuis My IP, rôle `io-bootstrap-role`, nom `mario-bootstrap`.
3. Connecte-toi et installe les outils :

```bash
ssh -i ~/.ssh/io-key.pem ubuntu@<IP>
git clone https://github.com/Aj7Ay/k8s-mario.git && cd k8s-mario
cat script.sh                   # lis TOUJOURS un script avant de l'exécuter
sudo chmod +x script.sh && ./script.sh
terraform -version && kubectl version --client && aws --version
aws sts get-caller-identity     # doit afficher le rôle io-bootstrap-role (assumed-role/...)
```

:::check
`aws sts get-caller-identity` répond **sans** que tu aies tapé `aws configure` : la CLI a trouvé seule les identifiants temporaires du rôle via le service de métadonnées de l'instance.
:::

## Étape 2 — Lire le code Terraform

```bash
cd EKS-TF && ls
# backend.tf  main.tf  provider.tf
```

Ce que fait `main.tf`, bloc par bloc :

| Bloc | Rôle |
|---|---|
| `data "aws_iam_policy_document" "assume_role"` | la politique de confiance : « le service `eks.amazonaws.com` peut endosser ce rôle » |
| `aws_iam_role.example` + attachement `AmazonEKSClusterPolicy` | le **rôle du cluster** (comme au projet 08, mais en code) |
| `data "aws_vpc" "default"` / `data "aws_subnets" "public"` | lit le VPC par défaut et ses subnets (rien n'est créé) |
| `aws_eks_cluster.example` | le cluster `EKS_CLOUD` dans ces subnets |
| `aws_iam_role.example1` + 3 attachements | le **rôle des nœuds** (WorkerNode, CNI, ECR ReadOnly) |
| `aws_eks_node_group.example` | le node group : 1 nœud (min 1, max 2) |

Les `depends_on` garantissent que les politiques IAM sont attachées **avant** la création du cluster et des nœuds, et détachées **après** leur destruction (sinon EKS ne pourrait plus nettoyer ses propres ressources).

## Étape 3 — Adapter le code

1. **`backend.tf`** : mets ton bucket et ta région :

```hcl
terraform {
  backend "s3" {
    bucket       = "io-tfstate-<prenom>"
    key          = "EKS/terraform.tfstate"
    region       = "eu-west-3"
    use_lockfile = true
  }
}
```

2. **`provider.tf`** : `region = "eu-west-3"`.
3. **`main.tf`** : remplace `instance_types = ["t2.medium"]` par `["t3.medium"]` (génération plus récente et moins chère).

:::warn Les subnets du VPC par défaut
Le code prend **tous** les subnets du VPC par défaut. Dans certaines régions (notamment `us-east-1`), une AZ n'est pas supportée par EKS (`us-east-1e`), et la création échoue avec `UnsupportedAvailabilityZoneException`. Si ça t'arrive, filtre les subnets par AZ :
```hcl
data "aws_subnets" "public" {
  filter { name = "vpc-id",            values = [data.aws_vpc.default.id] }
  filter { name = "availability-zone", values = ["eu-west-3a", "eu-west-3b", "eu-west-3c"] }
}
```
:::

## Étape 4 — Créer le cluster

```bash
terraform init
terraform validate
terraform plan
terraform apply --auto-approve          # 10 à 15 minutes
```

Puis configure kubectl :

```bash
aws eks update-kubeconfig --name EKS_CLOUD --region eu-west-3
kubectl get nodes
```

:::warn `Unauthorized` avec kubectl ?
Avec l'API des access entries (mode par défaut des clusters récents créés par Terraform), **l'identité qui crée le cluster** n'a pas toujours automatiquement les droits d'administration Kubernetes. Ajoute dans `aws_eks_cluster` :
```hcl
access_config {
  authentication_mode                         = "API_AND_CONFIG_MAP"
  bootstrap_cluster_creator_admin_permissions = true
}
```
Ici, c'est le rôle `io-bootstrap-role` qui crée le cluster et qui utilise kubectl : il sera administrateur.
:::

## Étape 5 — Déployer Mario

```bash
cd ..                                   # retour à la racine du dépôt
cat deployment.yaml service.yaml        # 2 replicas de sevenajay/mario, Service LoadBalancer port 80
kubectl apply -f deployment.yaml
kubectl get deploy,pods
kubectl apply -f service.yaml
kubectl get svc mario-service -w        # attends l'EXTERNAL-IP
kubectl describe svc mario-service | grep "LoadBalancer Ingress"
```

Ouvre `http://<LoadBalancer Ingress>` : **Super Mario se lance dans ton navigateur.** 🍄

## Dépannage

:::fix
- **`Error: creating EKS Cluster … AccessDeniedException`** : le rôle de l'instance n'a pas les droits (vérifie qu'il est bien attaché à l'instance).
- **`Error acquiring the state lock` / `NoSuchBucket`** : bucket du backend inexistant ou dans une autre région.
- **Node group en `CREATE_FAILED` (« Instances failed to join the kubernetes cluster »)** : subnets sans IP publique automatique et sans NAT. Les subnets du VPC par défaut ont l'IP publique automatique activée ; si tu as modifié ce réglage, réactive-le.
- **Pods `Pending`** : un seul `t3.medium` peut manquer de place ; passe `desired_size` à 2.
:::

## Nettoyage

:::clean
```bash
kubectl delete -f service.yaml           # D'ABORD le Service (supprime le load balancer)
kubectl delete -f deployment.yaml
cd EKS-TF && terraform destroy --auto-approve   # 10 minutes
```
Puis *terminate* l'instance `mario-bootstrap` et supprime le rôle `io-bootstrap-role` (ou garde-le pour le projet 19). Vérifie EC2 → *Load Balancers* : rien ne doit rester.
:::

:::tip Pourquoi supprimer le Service avant `terraform destroy` ?
Le load balancer a été créé par **Kubernetes**, pas par Terraform : Terraform ne le connaît pas et ne le supprimera pas. Pire, ce load balancer et son Security Group occupent le VPC et peuvent bloquer la suppression d'autres ressources. Règle générale : **ce qu'un outil a créé, c'est à cet outil de le supprimer.**
:::

## Pour aller plus loin

- Ajoute des `output` (nom du cluster, endpoint) et une `variable` pour la région et le type d'instance.
- Remplace le VPC par défaut par le module `terraform-aws-modules/vpc` avec subnets privés (c'est ce que fait le projet 19).
- Déploie Mario **avec Terraform aussi**, grâce au provider `kubernetes` (ressources `kubernetes_deployment` et `kubernetes_service`). Discute : est-ce une bonne idée de gérer les applications avec le même outil que l'infrastructure ? *(Souvent non : on préfère Helm/Argo CD pour les applications.)*
