## Ce qu'on construit

Une API REST (utilisateurs, produits, images de produits) **sans aucun serveur à gérer** :

```ascii
 Client ──HTTPS──► API Gateway (REST, ressources /healthz, /v1/user, /v1/product…, intégration proxy)
                        │ invoque
                        ▼
 VPC ┌──────────────────────── subnets PRIVÉS (aucun accès Internet) ────────────────────────────┐
     │  Lambda "serverless_api" (Node.js : Express + serverless-http, Sequelize)                 │
     │      │ 3306                         │ HTTPS (endpoint Interface)    │ (endpoint Gateway)  │
     │      ▼                              ▼                               ▼                     │
     │  Aurora Serverless v2 MySQL    Secrets Manager                    S3 (images produits)    │
     │  (0,5 à 1 ACU, chiffrée KMS)   (mot de passe de la base, rotation)                        │
     └───────────────────────────────────────────────────────────────────────────────────────────┘
 CloudWatch Logs + métriques        ACM + Route 53 : domaine personnalisé de l'API (optionnel)
 CI/CD : GitHub Actions ── OIDC ──► terraform apply (+ zip de la Lambda)
```

## Les points d'architecture à comprendre

:::why Une Lambda dans un VPC
Pour joindre Aurora (qui est dans des subnets privés), la Lambda doit être **dans le VPC** : AWS lui crée des interfaces réseau (ENI) dans les subnets indiqués. Conséquence : elle n'a **plus accès à Internet**, ni aux services AWS publics (S3, Secrets Manager…), sauf si on lui en donne le moyen.
:::

:::why Les VPC endpoints au lieu d'une NAT Gateway
Plutôt qu'une NAT Gateway (~35 $/mois), le projet crée :
- un **endpoint de type Gateway pour S3** (gratuit) : une route dans la table de routage privée envoie le trafic S3 directement au service, sans passer par Internet ;
- un **endpoint de type Interface pour Secrets Manager** (une ENI privée dans le VPC, ~7 $/mois par AZ) : la Lambda appelle Secrets Manager via une IP privée.

Bonus sécurité : le trafic ne quitte jamais le réseau AWS.
:::

:::why `manage_master_user_password = true`
Aurora **génère lui-même** le mot de passe administrateur et le range dans **Secrets Manager**, chiffré par une clé **KMS** dédiée, avec **rotation automatique** (tous les 7 jours par défaut). Le mot de passe n'apparaît **nulle part** : ni dans le code, ni dans Terraform, ni dans les variables de la Lambda. La Lambda reçoit seulement l'**ARN du secret** (`SECRET_ID`) et le lit à l'exécution grâce à son rôle IAM.
:::

## Étape 1 — Lire et moderniser le code Terraform

```bash
cd ~/IO/projects && mkdir 22-serverless && cd 22-serverless
cp -r /tmp/dp/DevOps-Project-22/* .
grep -n 'resource "' main.tf | wc -l        # environ 80 ressources
```

**Corrections indispensables :**

1. **Runtime Lambda** : `runtime = "nodejs16.x"` n'est plus accepté par AWS (runtime retiré : on ne peut plus créer de fonction avec). Mets **`nodejs20.x`** ou **`nodejs22.x`**, et vérifie que les dépendances de `serverless-api/package.json` s'installent avec cette version.
2. **Version d'Aurora** : `engine_version = "8.0.mysql_aurora.3.02.0"` est trop ancienne. Supprime la ligne (Aurora choisira la version par défaut) dans `aws_rds_cluster` **et** `aws_rds_cluster_instance` (où elle référence celle du cluster), ou mets une version 3.x actuelle (`aws rds describe-db-engine-versions --engine aurora-mysql --query "DBEngineVersions[].EngineVersion"`).
3. **Domaine personnalisé** : les ressources `aws_api_gateway_domain_name`, `aws_route53_record` et `aws_api_gateway_base_path_mapping` exigent un domaine et un certificat ACM. Sans domaine, **commente-les** : tu utiliseras l'URL fournie par API Gateway.
4. **Variables** : renseigne un fichier `terraform.tfvars` (région, profil, CIDR, nombre de subnets privés, `artifact_location`, `api_stage`…) selon `variables.tf`. Ajoute un **backend S3** (leçon 10).

## Étape 2 — Empaqueter la Lambda

```bash
cd serverless-api
npm ci --omit=dev                    # dépendances de production uniquement
zip -r ../serverless-api.zip . -x "*.git*" "test/*"
cd ..
ls -lh serverless-api.zip            # artifact_location = "serverless-api.zip"
```

Lis `index.js` : en mode `ENVIRONMENT=lambda`, l'application Express est enveloppée par `serverless-http` et exportée comme `handler` (d'où `handler = "index.handler"` dans Terraform). En local (`node index.js`), la même application écoute sur le port 3000. **Une seule base de code pour les deux modes** : pratique pour tester.

:::tip Le zip, Terraform et `source_code_hash`
`source_code_hash = filebase64sha256(var.artifact_location)` : Terraform calcule une empreinte du zip. Si le code change, l'empreinte change, et Terraform met à jour la fonction. Sans cet attribut, Terraform ne verrait pas qu'il faut redéployer le code.
:::

## Étape 3 — Déployer à la main une première fois

```bash
terraform init
terraform plan -out=tfplan
terraform apply tfplan              # 10 à 15 minutes (Aurora est le plus long)
```

Récupère l'URL de l'API : *API Gateway → serverless API → Stages → <stage>* → **Invoke URL** (ou ajoute un `output`).

```bash
API=https://xxxxxxxx.execute-api.eu-west-3.amazonaws.com/<stage>
curl $API/healthz
curl -X POST $API/v1/user -H 'Content-Type: application/json' \
  -d '{"first_name":"Ada","last_name":"Lovelace","username":"ada@exemple.com","password":"Motdepasse123!"}'
curl $API/v1/user/<id renvoyé>       # voir le README de serverless-api pour les champs et l'authentification
```

:::check
- `/healthz` répond 200.
- CloudWatch → *Log groups* → `/aws/lambda/serverless_api` : les logs de chaque invocation, dont « Tables are created successfully! » (Sequelize crée les tables au premier appel).
- Secrets Manager : un secret `rds!cluster-…` géré par RDS, avec la rotation activée.
- Le premier appel est plus lent (*cold start* : création de l'environnement Lambda, connexion à Aurora qui peut se « réveiller »), les suivants sont rapides.
:::

## Étape 4 — La CI/CD avec GitHub Actions

Le dépôt d'origine décrit la CI/CD mais ne fournit pas le workflow. Voici une version complète, avec **OIDC** (rôle IAM `github-serverless-deploy` créé comme au projet 14, avec des droits suffisants pour Terraform sur ces services, et la condition `sub` limitée à ton dépôt) :

```yaml
# .github/workflows/deploy.yml
name: Serverless API

on:
  pull_request:
    branches: [ main ]
  push:
    branches: [ main ]

permissions:
  contents: read
  id-token: write
  pull-requests: write

jobs:
  terraform:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: npm, cache-dependency-path: serverless-api/package-lock.json }

      - name: Tests et paquet Lambda
        working-directory: serverless-api
        run: |
          npm ci
          npm test --if-present
          npm ci --omit=dev
          zip -qr ../serverless-api.zip . -x "*.git*"

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: eu-west-3

      - uses: hashicorp/setup-terraform@v3

      - run: terraform fmt -check -recursive
      - run: terraform init -input=false
      - run: terraform validate
      - run: terraform plan -input=false -out=tfplan

      - name: Apply (uniquement sur main)
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        run: terraform apply -input=false tfplan
```

:::why Plan sur la PR, apply sur main
Sur une **pull request**, le workflow construit, teste et affiche le **plan** : le relecteur voit exactement ce qui changera dans l'infrastructure. Après **fusion** dans `main`, le même workflow **applique**. Pour aller plus loin, publie le plan en commentaire de la PR (actions comme `terraform-plan-comment`) et protège `main` avec un *environment* GitHub exigeant une approbation.
:::

## Dépannage

:::fix
- **`InvalidParameterValueException: The runtime parameter of nodejs16.x is no longer supported`** : étape 1, point 1.
- **La Lambda dépasse le timeout (30 s) à la première requête** : Aurora Serverless se réveille, ou la Lambda n'arrive pas à joindre Secrets Manager (endpoint Interface absent, ou son Security Group n'autorise pas le SG de la Lambda en 443, ou `private_dns_enabled` désactivé).
- **`AccessDeniedException` sur `secretsmanager:GetSecretValue`** ou **`kms:Decrypt`** : politique `lambda_rds_secret_policy` ; le rôle doit aussi pouvoir déchiffrer avec la clé KMS du secret.
- **`Missing Authentication Token`** d'API Gateway : mauvais chemin ou stage non déployé (`aws_api_gateway_deployment` doit être recréé quand les routes changent).
- **`ENI` / suppression lente** : au `destroy`, AWS met parfois 20 à 40 minutes à libérer les interfaces réseau des Lambda dans le VPC ; c'est normal, laisse Terraform attendre.
:::

## Nettoyage

:::clean
```bash
terraform destroy
```
Vérifie : cluster Aurora supprimé (et pas de snapshot final si `skip_final_snapshot = true`), endpoints VPC, bucket S3 (vide-le s'il contient des images : `aws s3 rm s3://<bucket> --recursive`), clé KMS (elle passe en *pending deletion* pendant 7 à 30 jours, sans coût), secret Secrets Manager (supprimé avec le cluster), log groups CloudWatch.
:::
