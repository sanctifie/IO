## Ce qu'on construit

**Robot Shop**, une boutique en ligne de démonstration composée d'une dizaine de **microservices** écrits dans des langages différents, déployée en une commande avec **Helm**, exposée par un **ALB** créé automatiquement à partir d'un objet **Ingress**, et dont les bases de données stockent leurs données sur des **volumes EBS**.

```ascii
 Navigateur ──► ALB (créé par l'AWS Load Balancer Controller à partir de l'Ingress)
                   │
                   ▼  namespace robot-shop
   ┌───────────────── PRÉSENTATION ─────────────────┐
   │  web (Nginx + AngularJS)                       │
   └──────────────┬─────────────────────────────────┘
   ┌───────────── LOGIQUE MÉTIER (microservices) ───┐
   │ catalogue (Node.js)  user (Node.js)  cart (Node.js)
   │ shipping (Java)  payment (Python)  ratings (PHP)  dispatch (Go)
   └──────────────┬─────────────────────────────────┘
   ┌───────────── DONNÉES ──────────────────────────┐
   │ MongoDB   MySQL   Redis (PVC → volume EBS via le pilote EBS CSI)   RabbitMQ
   └────────────────────────────────────────────────┘
```

## Les concepts nouveaux

:::why IRSA : donner des droits AWS à un pod
L'**AWS Load Balancer Controller** est un pod qui doit appeler l'API AWS pour créer des ALB. Le **pilote EBS CSI** est un pod qui doit créer et attacher des volumes EBS. Comment leur donner des droits sans clés d'accès ?
1. Le cluster expose un **fournisseur d'identité OIDC**, qu'on enregistre dans IAM.
2. On crée un **rôle IAM** dont la politique de confiance dit : « le ServiceAccount Kubernetes `kube-system/aws-load-balancer-controller` de ce cluster peut m'endosser ».
3. Le ServiceAccount porte une annotation avec l'ARN du rôle ; le pod obtient automatiquement des identifiants temporaires.

C'est l'équivalent, pour un pod, du rôle IAM d'une instance EC2. (EKS propose aussi **Pod Identity**, plus récent et plus simple ; IRSA reste très répandu et c'est ce que montre le projet.)
:::

:::why Ingress + AWS Load Balancer Controller
Au projet 08, chaque Service `LoadBalancer` créait **son** load balancer. Ici, un seul objet **Ingress** décrit les règles HTTP, et le **contrôleur** traduit cet Ingress en un **ALB** configuré (listeners, règles, target groups). Un ALB pour toute l'application, routage par chemin ou par nom de domaine, HTTPS avec ACM : c'est la méthode standard sur EKS.
:::

:::why Le pilote EBS CSI
Les bases de données (MongoDB, MySQL, Redis) demandent du stockage persistant via des **PersistentVolumeClaims**. Sur EKS, c'est le **pilote EBS CSI** (un add-on) qui crée les volumes EBS correspondants et les attache au bon nœud. Sans lui, les PVC restent en `Pending` et les pods de bases de données ne démarrent jamais.
:::

## Étape 1 — Le cluster

```bash
export CLUSTER=io-robotshop
export REGION=eu-west-3
eksctl create cluster --name $CLUSTER --region $REGION \
  --nodegroup-name workers --node-type t3.medium \
  --nodes 2 --nodes-min 1 --nodes-max 3 --managed
kubectl get nodes
```

*(Le dépôt d'origine utilise des `t3.small` : avec une dizaine de microservices plus les contrôleurs, c'est trop juste. `t3.medium` × 2 est un minimum confortable.)*

## Étape 2 — Le fournisseur OIDC

```bash
oidc_id=$(aws eks describe-cluster --name $CLUSTER --query "cluster.identity.oidc.issuer" --output text | cut -d '/' -f 5)
aws iam list-open-id-connect-providers | grep $oidc_id    # déjà là ? (eksctl l'a peut-être créé)
eksctl utils associate-iam-oidc-provider --cluster $CLUSTER --region $REGION --approve
```

## Étape 3 — Les droits IAM de l'AWS Load Balancer Controller

```bash
# La politique officielle, à jour (le dépôt d'origine épingle la v2.5.4, ancienne)
curl -o iam_policy.json https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/main/docs/install/iam_policy.json
aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy --policy-document file://iam_policy.json

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
eksctl create iamserviceaccount \
  --cluster=$CLUSTER --region $REGION \
  --namespace=kube-system \
  --name=aws-load-balancer-controller \
  --role-name AmazonEKSLoadBalancerControllerRole \
  --attach-policy-arn=arn:aws:iam::$ACCOUNT_ID:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve
kubectl get sa aws-load-balancer-controller -n kube-system -o yaml | grep role-arn   # l'annotation IRSA
```

## Étape 4 — Installer le contrôleur avec Helm

```bash
VPC_ID=$(aws eks describe-cluster --name $CLUSTER --query "cluster.resourcesVpcConfig.vpcId" --output text)
helm repo add eks https://aws.github.io/eks-charts && helm repo update eks
helm install aws-load-balancer-controller eks/aws-load-balancer-controller -n kube-system \
  --set clusterName=$CLUSTER \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=$REGION \
  --set vpcId=$VPC_ID
kubectl get deployment -n kube-system aws-load-balancer-controller    # READY 2/2
```

`serviceAccount.create=false` : on réutilise le ServiceAccount créé à l'étape 3 (celui qui porte le rôle IAM).

## Étape 5 — Le pilote EBS CSI

```bash
eksctl create iamserviceaccount \
  --name ebs-csi-controller-sa --namespace kube-system \
  --cluster $CLUSTER --region $REGION \
  --role-name AmazonEKS_EBS_CSI_DriverRole --role-only \
  --attach-policy-arn arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy \
  --approve

eksctl create addon --name aws-ebs-csi-driver --cluster $CLUSTER --region $REGION \
  --service-account-role-arn arn:aws:iam::$ACCOUNT_ID:role/AmazonEKS_EBS_CSI_DriverRole --force

kubectl get pods -n kube-system | grep ebs-csi
kubectl get storageclass          # une StorageClass gp2 (ou gp3) doit exister
```

:::info `--role-only`
Ici, eksctl crée seulement le **rôle** IAM (pas le ServiceAccount), parce que c'est l'**add-on** EKS qui crée et gère son propre ServiceAccount ; on lui passe l'ARN du rôle à utiliser.
:::

## Étape 6 — Installer Robot Shop avec Helm

```bash
git clone https://github.com/uniquesreedhar/RobotShop-Project.git
cd RobotShop-Project/EKS/helm
ls                               # Chart.yaml  values.yaml  templates/  ingress.yaml
cat values.yaml                  # options : StorageClass, images, ressources…
kubectl create ns robot-shop
helm install robot-shop --namespace robot-shop .
kubectl get pods -n robot-shop -w            # attends que tout soit Running (2 à 5 minutes)
kubectl get pvc -n robot-shop                # les PVC doivent être Bound
```

:::warn PVC en `Pending` ?
`kubectl describe pvc <nom> -n robot-shop`. Si l'événement dit *waiting for first consumer*, c'est normal : le volume est créé quand le pod est placé. Si la StorageClass demandée n'existe pas (par exemple `gp2` absente sur un cluster récent qui n'a que `gp3`), adapte la StorageClass dans `values.yaml` ou crée-la.
:::

## Étape 7 — L'Ingress

```bash
cat ingress.yaml
```

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: robot-shop
  namespace: robot-shop
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing     # ALB public
    alb.ingress.kubernetes.io/target-type: ip             # l'ALB envoie directement aux IP des pods
spec:
  ingressClassName: alb
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service: { name: web, port: { number: 8080 } }
```

```bash
kubectl apply -f ingress.yaml
kubectl get ingress -n robot-shop -w         # ADDRESS : le nom DNS de l'ALB (2 à 3 minutes)
```

:::check
- Ouvre `http://<ADDRESS>` : la boutique Robot Shop s'affiche. Crée un compte, connecte-toi, ajoute des robots au panier, note un robot (*Rate the Artificial Intelligence*), passe commande.
- EC2 → *Load Balancers* : un ALB `k8s-robotsho-…` ; ses *target groups* contiennent des **IP de pods**.
- EC2 → *Volumes* : des volumes EBS créés pour les bases de données.
- Supprime le pod MySQL (`kubectl delete pod -n robot-shop -l service=mysql`) : il revient avec **les mêmes données** (le volume persiste).
:::

## Dépannage

:::fix
- **L'Ingress n'a jamais d'ADDRESS** : `kubectl logs -n kube-system deploy/aws-load-balancer-controller`. Causes classiques : `AccessDenied` (rôle IRSA mal configuré ou politique ancienne), subnets publics non tagués `kubernetes.io/role/elb=1` (eksctl les tague), `ingressClassName` absent.
- **`helm install` du contrôleur : webhook errors** à l'installation de l'Ingress → le contrôleur n'est pas encore prêt ; attends qu'il soit `2/2`.
- **Pods `Pending` (Insufficient cpu/memory)** : ajoute un nœud (`eksctl scale nodegroup --cluster $CLUSTER --name workers --nodes 3`).
- **Pods `CrashLoopBackOff` sur un microservice** : souvent sa base n'est pas encore prête ; patiente ou supprime le pod pour le relancer.
:::

## Nettoyage

:::clean
```bash
kubectl delete -f ingress.yaml                 # D'ABORD : supprime l'ALB
helm uninstall robot-shop -n robot-shop        # supprime les pods (les PVC peuvent rester :)
kubectl delete pvc --all -n robot-shop         # supprime les volumes EBS associés
helm uninstall aws-load-balancer-controller -n kube-system
eksctl delete cluster --name $CLUSTER --region $REGION
```
Vérifie EC2 → *Load Balancers* et *Volumes* (aucun volume `available` orphelin), CloudFormation (piles `eksctl-…`). Les politiques/rôles IAM peuvent être supprimés ou gardés.
:::
