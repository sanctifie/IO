## Ce qu'on construit

L'**Example Voting App** de Docker est l'application microservices de référence : 5 composants dans 3 langages.

```ascii
          ┌────────── vote (Python/Flask) :5000 ──┐                ┌── result (Node.js) :5001 ──┐
 votant ──►  « Chats ou chiens ? »                 │                │  résultats en temps réel   │◄── visiteur
          └──────────────────┬────────────────────┘                └─────────────▲──────────────┘
                             │ écrit le vote                                      │ lit
                             ▼                                                     │
                       [ Redis ] ──► worker (.NET) lit la file ──► [ PostgreSQL ] ─┘
```

Et la chaîne CI/CD :

```ascii
 commit dans vote/ ──► pipeline « vote » (agent auto-hébergé sur une VM Azure)
                         Build : docker build vote/   →  Push : ACR votingapp/vote:<BuildId>
                         Update : script → k8s-specifications/vote-deployment.yaml → image …:<BuildId> → git push (Azure Repos)
                                                       │
 Argo CD (dans AKS) surveille k8s-specifications/ ◄────┘ → synchronise → nouveau pod vote
 (même chose pour result/ et worker/, chacun avec son pipeline)
```

## Étape 1 — Tester l'application en local avec Docker Compose

Sur une VM Ubuntu Azure (`Standard_B2s`, port 22, et 5000/5001 depuis ton IP), qui servira aussi d'agent à l'étape 4 :

```bash
sudo apt update && sudo apt install -y docker.io docker-compose-v2 git
sudo usermod -aG docker $USER && newgrp docker
git clone https://github.com/dockersamples/example-voting-app.git && cd example-voting-app
docker compose up -d          # (le tutoriel installe l'ancien binaire "docker-compose" : le plugin "docker compose" le remplace)
docker compose ps
```

Ouvre `http://<IP_VM>:5000` (vote) et `http://<IP_VM>:5001` (résultats). Vote : le résultat change en temps réel. Lis `docker-compose.yml` : il décrit les 5 services, leurs réseaux, leurs volumes et leurs `healthcheck`. `docker compose down` quand tu as fini.

## Étape 4 — L'agent auto-hébergé

:::why Pourquoi un agent auto-hébergé ?
1. Les nouvelles organisations n'ont pas de parallélisme gratuit sur les agents Microsoft (voir projet 07) : un agent à toi fonctionne tout de suite.
2. Les builds Docker profitent du **cache** local de l'agent (les couches déjà construites) : beaucoup plus rapides.
3. En entreprise, un agent dans ton réseau peut joindre des ressources privées.

Contrepartie : tu dois maintenir la machine (mises à jour, espace disque, sécurité).
:::

1. *Project settings → Agent pools → Add pool* → *Self-hosted* → nom `votingApp-Agent` → *Grant access permission to all pipelines*.
2. Le pool → *New agent* → *Linux* → copie l'URL de téléchargement affichée.
3. Sur la VM :

```bash
mkdir ~/myagent && cd ~/myagent
wget <URL-copiée-depuis-Azure-DevOps>          # vsts-agent-linux-x64-<version>.tar.gz
tar zxvf vsts-agent-linux-x64-*.tar.gz
./config.sh       # URL : https://dev.azure.com/<org> ; authentification : PAT (droits Agent Pools: Read & manage) ; pool : votingApp-Agent
sudo ./svc.sh install && sudo ./svc.sh start   # en service : l'agent survit à la déconnexion SSH et au redémarrage
```

*(Le tutoriel lance `./run.sh` : l'agent s'arrête dès que tu fermes le terminal. `svc.sh` l'installe comme service systemd.)*

L'agent apparaît **Online** dans le pool. L'utilisateur qui exécute l'agent doit être dans le groupe `docker`.

## Étape 5 — Un pipeline par microservice

Crée `vote/azure-pipelines-vote.yml` (dans Azure Repos) :

```yaml
trigger:
  branches:
    include: [ main ]
  paths:
    include: [ vote/* ]            # ne se déclenche QUE si quelque chose change dans vote/

resources:
- repo: self

variables:
  dockerRegistryServiceConnection: 'votingACR'
  imageRepository: 'votingapp/vote'
  containerRegistry: '<ton-acr>.azurecr.io'
  dockerfilePath: '$(Build.SourcesDirectory)/vote/Dockerfile'
  tag: '$(Build.BuildId)'

pool:
  name: 'votingApp-Agent'          # l'agent auto-hébergé

stages:
- stage: Build
  jobs:
  - job: Build
    steps:
    - task: Docker@2
      inputs:
        containerRegistry: $(dockerRegistryServiceConnection)
        repository: $(imageRepository)
        command: build
        Dockerfile: vote/Dockerfile
        tags: $(tag)

- stage: Push
  jobs:
  - job: Push
    steps:
    - task: Docker@2
      inputs:
        containerRegistry: $(dockerRegistryServiceConnection)
        repository: $(imageRepository)
        command: push
        tags: $(tag)

- stage: Update_K8s
  jobs:
  - job: Update
    steps:
    - task: ShellScript@2
      inputs:
        scriptPath: 'scripts/updateK8sManifests.sh'
        args: 'vote $(imageRepository) $(tag)'
      env:
        AZDO_PAT: $(AZDO_PAT)       # variable secrète du pipeline
```

*Pipelines → New pipeline → Azure Repos Git → Existing YAML* → `vote/azure-pipelines-vote.yml`. Duplique pour `result` et `worker` (chemins, Dockerfile, `imageRepository`).

:::why Séparer Build et Push en deux stages… sur un agent auto-hébergé
Les stages peuvent s'exécuter sur des machines différentes : l'image construite dans *Build* n'existerait pas pour *Push*. Ça fonctionne ici **parce que** le même agent auto-hébergé exécute les deux stages et garde l'image en local. Sur des agents hébergés par Microsoft, on ferait `buildAndPush` dans une seule étape.
:::

## Étape 6 — Le script de mise à jour des manifests

Crée `scripts/updateK8sManifests.sh` :

```bash
#!/bin/bash
# Usage : updateK8sManifests.sh <service> <imageRepository> <tag>
set -euo pipefail

SERVICE=$1          # vote | result | worker
IMAGE_REPO=$2       # votingapp/vote
TAG=$3              # numéro de build
ACR="<ton-acr>.azurecr.io"
REPO_URL="https://${AZDO_PAT}@dev.azure.com/<org>/votingApp/_git/votingApp"

rm -rf /tmp/temp_repo
git clone "$REPO_URL" /tmp/temp_repo
cd /tmp/temp_repo

sed -i "s|image:.*|image: ${ACR}/${IMAGE_REPO}:${TAG}|g" "k8s-specifications/${SERVICE}-deployment.yaml"

git config user.email "pipeline@exemple.com"
git config user.name  "Azure Pipeline"
git add "k8s-specifications/${SERVICE}-deployment.yaml"
git commit -m "ci: ${SERVICE} -> ${TAG} [skip ci]"
git push

rm -rf /tmp/temp_repo
```

:::danger Le jeton dans le script
Le tutoriel écrit le **PAT directement dans le script** (`https://<ACCESS-TOKEN>@dev.azure.com/…`), donc dans le dépôt. Utilise une **variable secrète** de pipeline (`AZDO_PAT`, cadenas coché) passée en `env:` (les secrets ne sont pas exposés automatiquement aux scripts, voir projet 20). Donne au PAT uniquement *Code: Read & write*. `[skip ci]` dans le message empêche Azure Pipelines de se redéclencher sur ce commit (en plus, le filtre `paths` exclut déjà `k8s-specifications/`).
:::

## Étape 7 — AKS et Argo CD

```bash
az aks create -g voting-rg -n voting-aks --node-count 1 --node-vm-size Standard_B2s --generate-ssh-keys
az aks get-credentials -g voting-rg -n voting-aks
kubectl get nodes
```

Installe Argo CD (le script du tutoriel est correct ; version courte) :

```bash
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl wait --for=condition=Ready pods --all -n argocd --timeout=600s
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d; echo
kubectl -n argocd patch svc argocd-server -p '{"spec": {"type": "NodePort"}}'
kubectl -n argocd get svc argocd-server        # port NodePort (ex. 31xxx)
kubectl get nodes -o wide                      # EXTERNAL-IP d'un nœud
```

:::warn NodePort sur AKS
Pour joindre un NodePort depuis Internet, le nœud doit avoir une IP publique (option `--enable-node-public-ip` à la création) et le groupe de sécurité réseau (NSG) des nœuds doit autoriser le port. Plus simple : `kubectl -n argocd port-forward svc/argocd-server 8443:443` depuis ton poste.
:::

**Configurer Argo CD** : *Settings → Repositories → Connect repo* (HTTPS) → URL du dépôt Azure Repos, utilisateur quelconque, mot de passe = un PAT *Code: Read*. Puis *New App* : nom `voting-app`, chemin **`k8s-specifications`**, cluster `in-cluster`, namespace `default`, synchro automatique.

## Étape 8 — Autoriser AKS à tirer les images

Deux options :

- **Recommandée** : `az aks update -g voting-rg -n voting-aks --attach-acr <ton-acr>` (rôle AcrPull pour les nœuds, aucun secret).
- **Celle du tutoriel** : un `imagePullSecret` :

```bash
kubectl create secret docker-registry acr-secret \
  --docker-server=<ton-acr>.azurecr.io \
  --docker-username=<nom-acr> --docker-password=<mot-de-passe-acr>   # nécessite l'utilisateur admin de l'ACR activé
```

  puis ajouter dans chaque `*-deployment.yaml` : `imagePullSecrets: [{ name: acr-secret }]` (sous `spec.template.spec`).

## Étape 9 — Vérifier le CI/CD

Modifie `vote/app.py` : remplace les options `Cats`/`Dogs` (variables `option_a`/`option_b`) par `Summer`/`Winter`. Commit sur `main`.

:::check
1. Seul le pipeline **vote** démarre (filtre de chemins) : Build → Push → Update_K8s.
2. ACR : `votingapp/vote:<BuildId>`.
3. Azure Repos : un commit « ci: vote -> <BuildId> » dans `k8s-specifications/vote-deployment.yaml`.
4. Argo CD : *OutOfSync* → *Synced* (synchro toutes les 3 minutes, ou *Refresh*).
5. `kubectl get pods` : un nouveau pod `vote` ; la page de vote propose « Summer / Winter ».
:::

Pour accéder aux pages : `kubectl get svc vote result` (NodePort 31000/31001 dans les manifests d'exemple), ou `kubectl port-forward svc/vote 5000:5000`.

## Dépannage

:::fix
- **Le pipeline reste en file d'attente** : l'agent est *Offline* (service arrêté), ou le pool n'est pas autorisé pour ce pipeline.
- **`permission denied … docker.sock` sur l'agent** : l'utilisateur de l'agent n'est pas dans le groupe docker (redémarre le service de l'agent après l'ajout).
- **Push : `unauthorized`** : service connection ACR incorrecte.
- **Le script échoue au `git push`** : PAT absent (secret non passé en `env:`) ou sans droit d'écriture.
- **Pods `ImagePullBackOff`** : rôle AcrPull ou `imagePullSecret` manquant (étape 8).
- **Les trois pipelines se déclenchent à chaque commit** : filtre `paths` absent ou incorrect.
:::

## Nettoyage

:::clean
```bash
az group delete -n voting-rg --yes --no-wait      # AKS, ACR, VM (si elle est dans ce groupe)
```
Désinstalle l'agent de la VM si tu la gardes (`./config.sh remove`), supprime le pool, révoque les PAT.
:::
