# Leçon 3 — Les services AWS de base

Les trois premiers projets utilisent une douzaine de services AWS. Voici ce que chacun fait, avec les notions qu'il faut avoir en tête.

## IAM — qui a le droit de faire quoi

**IAM** (*Identity and Access Management*) gère les identités et les permissions.

| Notion | Ce que c'est |
|---|---|
| **User** | une personne (ou un programme) avec des identifiants permanents |
| **Group** | un ensemble d'utilisateurs qui partagent des permissions |
| **Role** | une identité **sans mot de passe** qu'on « endosse » temporairement : une instance EC2, une fonction Lambda, un pipeline, un pod Kubernetes |
| **Policy** | un document JSON qui liste ce qui est autorisé ou interdit |

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::mon-bucket-config/*"
  }]
}
```

Lecture : « autoriser (`Allow`) l'action *lire un objet S3* (`s3:GetObject`) sur tous les objets du bucket `mon-bucket-config` ». Chaque ressource AWS a un identifiant unique, son **ARN** (*Amazon Resource Name*), de la forme `arn:aws:service:région:compte:ressource`.

:::why Le principe du moindre privilège
On donne **exactement** les droits nécessaires, rien de plus. Le projet 02 te demande explicitement de ne **pas** donner `AmazonS3FullAccess` à tes instances, mais seulement la lecture d'**un** bucket. Si une instance est piratée, l'attaquant n'aura accès qu'à ce bucket, pas à tout ton compte.
:::

Un **instance profile** est l'enveloppe qui permet d'attacher un rôle IAM à une instance EC2. Les programmes sur l'instance (AWS CLI, SDK) obtiennent alors automatiquement des identifiants temporaires : **aucune clé à stocker**.

## EC2 — les machines virtuelles

| Notion | Explication |
|---|---|
| **Instance** | une machine virtuelle |
| **AMI** (*Amazon Machine Image*) | le modèle de disque à partir duquel on crée l'instance : Ubuntu 24.04, Amazon Linux 2023… ou ta propre image |
| **Type d'instance** | la taille : `t3.micro` (2 vCPU, 1 Go), `t3.medium` (2 vCPU, 4 Go), `t3.large` (2 vCPU, 8 Go)… |
| **Key pair** | la paire de clés SSH : AWS garde la publique, tu télécharges la privée (`.pem`) **une seule fois** |
| **EBS** | les disques réseau attachés à l'instance |
| **Security Group** | le pare-feu de l'instance |
| **User data** | un script exécuté **une fois**, au premier démarrage de l'instance (installation automatique) |
| **Elastic IP** | une IP publique fixe, qui ne change pas quand on arrête/redémarre l'instance |

:::info Les noms d'utilisateur par défaut selon l'AMI
`ubuntu` pour Ubuntu, `ec2-user` pour Amazon Linux et RHEL, `admin` pour Debian. Se tromper donne l'erreur `Permission denied (publickey)`.
:::

**Lancer une instance (console), le geste de base que tu referas cent fois :**

1. **EC2 → Instances → Launch instances**.
2. *Name* : `labo-linux`. Ajoute un tag `Project=io-03`.
3. *AMI* : **Ubuntu Server 24.04 LTS** (ou Amazon Linux 2023).
4. *Instance type* : `t3.micro` (éligible à l'offre gratuite).
5. *Key pair* : **Create new key pair** → nom `io-key`, type ED25519 ou RSA, format `.pem` → le fichier se télécharge.
6. *Network settings* : VPC par défaut, *Auto-assign public IP* : **Enable**. *Create security group* : autorise **SSH depuis My IP** (et pas *Anywhere*).
7. *Storage* : 8 à 20 Go gp3.
8. **Launch instance**.

```bash
# Sur ton poste (WSL/macOS) : range la clé et protège-la
mkdir -p ~/.ssh && mv ~/Downloads/io-key.pem ~/.ssh/     # sous WSL : /mnt/c/Users/<toi>/Downloads/io-key.pem
chmod 400 ~/.ssh/io-key.pem
ssh -i ~/.ssh/io-key.pem ubuntu@<IP_PUBLIQUE>
```

:::warn « UNPROTECTED PRIVATE KEY FILE! »
SSH refuse une clé lisible par d'autres utilisateurs. C'est pour ça qu'on fait `chmod 400`. Sous WSL, si la clé est restée sur le disque Windows (`/mnt/c/...`), `chmod` ne fonctionne pas : copie-la d'abord dans `~/.ssh/`.
:::

## Security Groups et NACL — les pare-feux

Un **Security Group** (SG) est un pare-feu attaché à une ressource (instance, base de données, load balancer).

- On écrit uniquement des règles **Allow** (tout ce qui n'est pas autorisé est bloqué).
- Il est **stateful** : si une requête entrante est autorisée, la réponse sortante l'est automatiquement.
- La **source** d'une règle peut être une plage d'IP (`82.64.10.5/32`) **ou un autre Security Group**. C'est extrêmement puissant : « autoriser le port 3306 depuis le SG des serveurs d'application » reste vrai même quand les serveurs changent d'IP avec l'auto-scaling.

```ascii
 Internet ──80──► [ SG-alb ] Load balancer
                        │ 8080 (source = SG-alb)
                        ▼
                  [ SG-app ] Serveurs d'application
                        │ 3306 (source = SG-app)
                        ▼
                  [ SG-db  ] Base de données RDS
```

Les **NACL** (*Network ACL*) sont des pare-feux au niveau du **sous-réseau**, **stateless** (il faut autoriser l'aller ET le retour) et acceptent des règles Deny. On les laisse généralement à leur valeur par défaut (tout autorisé) et on travaille avec les Security Groups.

## VPC — ton réseau privé dans le cloud

| Composant | Rôle |
|---|---|
| **VPC** | ton réseau isolé, défini par une plage CIDR (`172.32.0.0/16`) dans une région |
| **Subnet** | une sous-plage du VPC (`172.32.1.0/24`), située dans **une seule AZ** |
| **Route table** | les règles de routage d'un ou plusieurs sous-réseaux |
| **Internet Gateway (IGW)** | la porte entre le VPC et Internet (une par VPC, gratuite) |
| **Subnet public** | un sous-réseau dont la table de routage envoie `0.0.0.0/0` vers l'**IGW** |
| **Subnet privé** | un sous-réseau **sans** route vers l'IGW |
| **NAT Gateway** | placée dans un subnet public, elle permet aux subnets privés de **sortir** sur Internet (mises à jour, téléchargements) sans être joignables. **Payante à l'heure.** |
| **Transit Gateway** | un routeur central qui relie plusieurs VPC (et des réseaux d'entreprise) entre eux |
| **VPC Peering** | une liaison directe entre deux VPC (alternative plus simple et gratuite à l'heure au Transit Gateway) |
| **VPC Flow Logs** | l'enregistrement des connexions réseau (acceptées/rejetées), envoyé vers CloudWatch Logs ou S3 |
| **VPC Endpoint** | accès privé à un service AWS (S3, Secrets Manager…) sans passer par Internet |

```ascii
VPC 172.32.0.0/16
├── Subnet public  172.32.1.0/24 (AZ a) ── route 0.0.0.0/0 → IGW     ← NAT GW, bastion, load balancer
├── Subnet public  172.32.2.0/24 (AZ b) ── route 0.0.0.0/0 → IGW
├── Subnet privé   172.32.3.0/24 (AZ a) ── route 0.0.0.0/0 → NAT GW  ← serveurs d'application
└── Subnet privé   172.32.4.0/24 (AZ b) ── route 0.0.0.0/0 → NAT GW  ← base de données
```

:::why Pourquoi mettre les serveurs dans des subnets privés ?
Un serveur sans IP publique et sans route entrante depuis Internet **ne peut pas être attaqué directement** depuis Internet. Seul le load balancer (public) le contacte, sur un seul port. Les administrateurs passent par le bastion ou par **SSM Session Manager**. C'est la base de toute architecture sérieuse.
:::

## Les load balancers (ELB)

| Type | Couche | Usage |
|---|---|---|
| **ALB** (*Application Load Balancer*) | 7 (HTTP/HTTPS) | Routage par chemin (`/api` → service A) ou par nom de domaine, terminaison HTTPS, WAF. Le choix par défaut pour le web. |
| **NLB** (*Network Load Balancer*) | 4 (TCP/UDP) | Très hautes performances, IP fixes, tout protocole TCP. Utilisé dans les projets 01 et 02. |

Un load balancer envoie le trafic vers un **Target Group** (un groupe de cibles : instances, IP ou fonctions Lambda) et effectue des **health checks** : il interroge régulièrement chaque cible (par exemple `GET /` sur le port 80) et cesse d'envoyer du trafic aux cibles en mauvaise santé.

## Auto Scaling — s'adapter à la charge

Un **Auto Scaling Group** (ASG) maintient un nombre d'instances entre un **minimum**, un **désiré** et un **maximum**. Si une instance tombe en panne, il la remplace. Si la charge augmente (par exemple CPU > 70 %), il en ajoute.

Pour savoir quoi lancer, il utilise un **Launch Template** : AMI, type d'instance, key pair, Security Group, rôle IAM, user data. *(Les anciennes « Launch Configurations » mentionnées dans le dépôt d'origine sont dépréciées ; on utilise les Launch Templates.)*

:::why La conséquence fondamentale de l'auto-scaling
Les instances deviennent **jetables** : elles peuvent être détruites et recréées à tout moment. **Tu ne dois jamais configurer une instance à la main**. Tout doit être dans l'AMI ou dans le user data. C'est le passage de l'informatique « animal de compagnie » (un serveur chouchouté avec un nom) à l'informatique « bétail » (des instances identiques et interchangeables).
:::

## AMI personnalisées : Global AMI et Golden AMI

Les projets 01 et 02 parlent de *Global AMI* et de *Golden AMI*. C'est une stratégie en couches :

```ascii
 AMI officielle (Amazon Linux 2023)
        │  + AWS CLI, agent CloudWatch, agent SSM, durcissement sécurité
        ▼
   « Global AMI »  ── base commune de l'entreprise
        │
        ├── + Nginx      ──► « Golden AMI Nginx »
        ├── + Tomcat+JDK ──► « Golden AMI Tomcat »
        └── + Maven+Git  ──► « Golden AMI Maven »
```

Créer une AMI : configure une instance, puis **Actions → Image and templates → Create image**. L'instance redémarre, et quelques minutes plus tard l'AMI apparaît dans **EC2 → AMIs**. On peut ensuite lancer autant d'instances identiques qu'on veut. *(En entreprise, on automatise cette fabrication avec **Packer** ou **EC2 Image Builder**.)*

:::why Pourquoi préinstaller dans l'AMI plutôt que tout faire en user data ?
Une instance lancée depuis une Golden AMI est prête en 1 minute ; avec un user data qui installe tout, il faut 5 à 10 minutes, et le script peut échouer si un dépôt Internet est indisponible. Pour l'auto-scaling, la vitesse de démarrage compte. Le user data ne sert alors qu'à la configuration finale (déployer la dernière version de l'appli, renseigner une adresse).
:::

## S3 — le stockage d'objets

**S3** stocke des fichiers (« objets ») dans des **buckets**. Le nom d'un bucket est **unique au monde** (`io-config-<ton-prenom>-2026`). Usages : fichiers de configuration, artefacts de build, sauvegardes, logs, sites statiques, état Terraform.

```bash
aws s3 mb s3://io-config-alex-2026            # créer un bucket (make bucket)
aws s3 cp app.conf s3://io-config-alex-2026/  # envoyer un fichier
aws s3 ls s3://io-config-alex-2026/           # lister
aws s3 sync ./logs s3://io-logs-alex-2026/    # synchroniser un dossier
aws s3 rb s3://io-config-alex-2026 --force    # supprimer le bucket et son contenu
```

Par défaut, un bucket est **privé** et l'option *Block Public Access* est activée. Laisse-la.

## RDS — les bases de données managées

**RDS** fournit MySQL, PostgreSQL, MariaDB, etc. sans gérer le serveur : sauvegardes automatiques, mises à jour, réplication. En mode **Multi-AZ**, une copie de secours synchrone tourne dans une autre AZ et prend le relais automatiquement en cas de panne. On la place dans un **DB subnet group** (des subnets privés sur au moins 2 AZ) et on ne l'expose **jamais** sur Internet.

## CloudWatch — métriques, logs et alarmes

- **Metrics** : CPU, réseau, disque des instances (par défaut toutes les 5 minutes). **La mémoire et l'espace disque ne sont pas mesurés par défaut** : il faut installer l'**agent CloudWatch** sur l'instance. C'est le « push custom memory metrics » des projets 01 et 02.
- **Logs** : centralisation des logs (applications, VPC Flow Logs, Lambda) dans des *log groups* composés de *log streams*.
- **Alarms** : « si la métrique X dépasse le seuil Y pendant Z minutes, alors notifie (via **SNS**, par e-mail) ou déclenche une action (auto-scaling) ».

## SSM Session Manager — SSH sans SSH

**Systems Manager Session Manager** ouvre un terminal sur une instance **depuis la console AWS ou la CLI, sans port 22 ouvert, sans clé, sans bastion**. Conditions : l'agent SSM est installé (préinstallé sur Amazon Linux et Ubuntu officiels), l'instance a un rôle IAM avec la politique `AmazonSSMManagedInstanceCore`, et elle peut joindre les points d'accès SSM (via NAT ou via des VPC endpoints).

```bash
aws ssm start-session --target i-0123456789abcdef0
# nécessite le "Session Manager plugin" installé sur ton poste
```

## Route 53 — le DNS d'AWS

Route 53 héberge des **zones DNS** (*hosted zones*) et peut aussi vendre des noms de domaine (environ 15 $/an pour un `.com`). Une zone hébergée coûte 0,50 $/mois. Pour les projets, un domaine est **optionnel** : tu peux utiliser directement le nom DNS fourni par le load balancer (`xxx.elb.eu-west-3.amazonaws.com`).

:::interview
- Différence entre Security Group et NACL ? *SG : au niveau de l'instance, stateful, règles Allow uniquement. NACL : au niveau du subnet, stateless, Allow et Deny.*
- Comment une instance dans un subnet privé télécharge-t-elle des mises à jour ? *Via une NAT Gateway placée dans un subnet public (ou via des VPC endpoints pour les services AWS).*
- Pourquoi utiliser un rôle IAM plutôt que des access keys sur une instance ? *Identifiants temporaires renouvelés automatiquement, rien à stocker ni à faire tourner, aucun risque de fuite dans le code.*
- ALB ou NLB ? *ALB pour HTTP/HTTPS avec routage applicatif ; NLB pour du TCP/UDP brut, des performances extrêmes ou des IP fixes.*
:::
