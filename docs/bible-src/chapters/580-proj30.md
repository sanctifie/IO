## Ce qu'on construit

Le scénario d'une vraie mission : *« Mets en place la CI/CD et le monitoring de notre application de blog. »*

```ascii
 GitHub (token) ──► JENKINS
                     checkout → mvn compile → mvn test → Trivy fs → SonarQube → mvn package
                     → mvn deploy ──────────────────────────────► NEXUS (maven-releases / maven-snapshots)
                     → docker build → Trivy image → docker push ──► Docker Hub (dépôt PRIVÉ)
                     → kubectl apply (ServiceAccount jenkins, RBAC limité au namespace webapps)
                                                    │
                                                    ▼
                      EKS (Terraform) ── namespace webapps ── Deployment (imagePullSecret regcred) ── Service LoadBalancer
                                                                                      │
                     e-mail de résultat (HTML)                         blog.<ton-domaine> (CNAME)
                                                                                      ▲
 MONITORING : Blackbox Exporter sonde l'URL ──► Prometheus ──► Grafana (disponibilité, temps de réponse, certificat)
```

C'est le **projet de démonstration** à mettre en avant sur ton CV : fais-le proprement, documente-le dans `projects/30-blog-app/NOTES.md` avec des captures, et prépare un schéma d'architecture.

## Étape 2 — Les serveurs

## Étape 3 — Jenkins, SonarQube et Nexus

**Jenkins** : annexe A.3 + Docker (groupe `docker` pour `jenkins`) + Trivy (annexe A.5) + kubectl.

**SonarQube** : `docker run -d --name sonar -p 9000:9000 --restart unless-stopped sonarqube:community` (après le réglage `vm.max_map_count`, annexe A.4).

**Nexus** (annexe A.9) :

```bash
sudo apt install -y docker.io
sudo docker run -d --name nexus -p 8081:8081 --restart unless-stopped -v nexus-data:/nexus-data sonatype/nexus3
sudo docker exec nexus cat /nexus-data/admin.password ; echo     # mot de passe initial (attendre 2 à 3 minutes)
```

Ouvre `http://<IP_NEXUS>:8081` → *Sign in* `admin` + mot de passe initial → assistant : nouveau mot de passe, **désactive l'accès anonyme**.

:::why Nexus, c'est quoi ?
**Sonatype Nexus Repository** est un dépôt d'artefacts, comme JFrog Artifactory (projets 01 et 06), très répandu et utilisable gratuitement en auto-hébergé. Il héberge par défaut `maven-releases` (versions finales, immuables), `maven-snapshots` (versions de développement, suffixe `-SNAPSHOT`, remplaçables) et `maven-central` (cache de Maven Central). Il peut aussi servir de registre Docker, npm, PyPI…
:::

## Étape 4 — Plugins, outils et configurations

**Plugins** : *SonarQube Scanner*, *Eclipse Temurin installer*, *Config File Provider*, *Maven Integration*, *Pipeline Maven Integration*, *Kubernetes*, *Kubernetes Credentials*, *Kubernetes CLI*, *Kubernetes Client API*, *Docker*, *Docker Pipeline*, *Email Extension Template*, *Pipeline: Stage View*.

**Tools** : JDK **`jdk17`** (adoptium, 17), Maven **`maven3`**, SonarQube Scanner **`sonar-scanner`**, Docker **`docker`**.

**SonarQube** : token (*Administration → Security → Users → Tokens*) → credential *Secret text* `sonar-token` → *System → SonarQube servers* : `sonar-server`, `http://<IP_PRIVEE_SONAR>:9000`. Webhook SonarQube → `http://<IP_PRIVEE_JENKINS>:8080/sonarqube-webhook/`.

**Nexus** :

1. Dans le `pom.xml` de l'application, la section `distributionManagement` doit pointer vers **ton** Nexus :

```xml
<distributionManagement>
  <repository>
    <id>maven-releases</id>
    <url>http://<IP_PRIVEE_NEXUS>:8081/repository/maven-releases/</url>
  </repository>
  <snapshotRepository>
    <id>maven-snapshots</id>
    <url>http://<IP_PRIVEE_NEXUS>:8081/repository/maven-snapshots/</url>
  </snapshotRepository>
</distributionManagement>
```

2. *Manage Jenkins → Managed files → Add a new Config → Global Maven settings.xml*, ID **`maven-settings`**. Dans le contenu, la section `<servers>` — **sans mot de passe en clair** : le plugin *Config File Provider* permet d'associer un credential Jenkins à chaque `serverId` (*Server Credentials* → *Add* → ServerId `maven-releases` → credential `nexus-cred`, idem pour `maven-snapshots`). Le tutoriel écrit `admin`/`admin` en clair dans le fichier : évite-le.

3. Dans Nexus : `maven-releases` → *Deployment policy* : **Allow redeploy** (sinon le second `mvn deploy` d'une même version échoue avec une erreur 400). *(En production, on garde « Disable redeploy » et on incrémente la version : une release est immuable.)*

**Docker Hub** : crée un dépôt **privé** `blogging-app` ; credential *Username with password* `dockerhub-cred`.

## Étape 5 — Le pipeline CI

```groovy
pipeline {
    agent any
    tools {
        jdk 'jdk17'
        maven 'maven3'
    }
    environment {
        SCANNER_HOME = tool 'sonar-scanner'
        IMAGE = '<toi-dockerhub>/blogging-app'
    }
    stages {
        stage('Checkout') {
            steps { git branch: 'main', credentialsId: 'git-cred', url: 'https://github.com/<toi>/blogging-app.git' }
        }
        stage('Compilation') { steps { sh 'mvn -B compile' } }
        stage('Tests')       { steps { sh 'mvn -B test' } }
        stage('Trivy FS')    { steps { sh 'trivy fs --format table -o fs.html .' } }
        stage('Analyse SonarQube') {
            steps {
                withSonarQubeEnv('sonar-server') {
                    sh '$SCANNER_HOME/bin/sonar-scanner -Dsonar.projectName=Blogging-app -Dsonar.projectKey=Blogging-app -Dsonar.java.binaries=target'
                }
            }
        }
        stage('Quality Gate') {
            steps { timeout(time: 5, unit: 'MINUTES') { waitForQualityGate abortPipeline: true, credentialsId: 'sonar-token' } }
        }
        stage('Build') { steps { sh 'mvn -B package -DskipTests' } }
        stage('Publication Nexus') {
            steps {
                withMaven(globalMavenSettingsConfig: 'maven-settings', jdk: 'jdk17', maven: 'maven3', traceability: true) {
                    sh 'mvn -B deploy -DskipTests'
                }
            }
        }
        stage('Build image') {
            steps {
                script {
                    withDockerRegistry(credentialsId: 'dockerhub-cred', url: 'https://index.docker.io/v1/') {
                        sh 'docker build -t $IMAGE:$BUILD_NUMBER .'
                    }
                }
            }
        }
        stage('Trivy image') { steps { sh 'trivy image --format table -o image.html $IMAGE:$BUILD_NUMBER' } }
        stage('Push image') {
            steps {
                script {
                    withDockerRegistry(credentialsId: 'dockerhub-cred', url: 'https://index.docker.io/v1/') {
                        sh 'docker push $IMAGE:$BUILD_NUMBER'
                    }
                }
            }
        }
        // stage('Déploiement EKS') : ajouté à l'étape 6
    }
}
```

:::check
Pipeline vert jusqu'au push ; Nexus → *Browse* → `maven-releases` contient le `.jar` (la version du `pom.xml`, `0.0.3`, n'a pas le suffixe `-SNAPSHOT` : c'est une release) ; Docker Hub contient l'image (privée) ; SonarQube affiche le projet.
:::

## Étape 6 — EKS, RBAC et déploiement

**6.1 — Le cluster.** Depuis une machine d'administration (ou ton poste) avec AWS CLI, Terraform et kubectl : crée le cluster avec le Terraform du dépôt (`main.tf`, `variables.tf`, `output.tf`, adapte région et AZ) **ou** avec le module EKS du projet 19. Puis :

```bash
aws eks update-kubeconfig --region eu-west-3 --name <cluster>
kubectl get nodes
kubectl create namespace webapps
```

**6.2 — Une identité dédiée à Jenkins, limitée au namespace.** Au lieu de donner à Jenkins le kubeconfig administrateur, on crée un **ServiceAccount** avec des droits **seulement** sur `webapps` :

```yaml
# rbac-jenkins.yaml
apiVersion: v1
kind: ServiceAccount
metadata: { name: jenkins, namespace: webapps }
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: app-role, namespace: webapps }
rules:
- apiGroups: ["", "apps", "autoscaling", "networking.k8s.io"]
  resources: ["pods", "services", "configmaps", "secrets", "deployments", "replicasets",
              "horizontalpodautoscalers", "ingresses", "persistentvolumeclaims"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: app-rolebinding, namespace: webapps }
roleRef: { apiGroup: rbac.authorization.k8s.io, kind: Role, name: app-role }
subjects:
- kind: ServiceAccount
  name: jenkins
  namespace: webapps
---
apiVersion: v1
kind: Secret
metadata:
  name: jenkins-token
  namespace: webapps
  annotations: { kubernetes.io/service-account.name: jenkins }
type: kubernetes.io/service-account-token
```

```bash
kubectl apply -f rbac-jenkins.yaml
kubectl -n webapps get secret jenkins-token -o jsonpath='{.data.token}' | base64 -d; echo    # le jeton
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}'; echo               # l'URL de l'API
```

:::why RBAC : Role, RoleBinding, ServiceAccount
- Un **ServiceAccount** est une identité pour un programme (ici Jenkins).
- Un **Role** liste des permissions (*verbes* sur des *ressources*) **dans un namespace**. (Un **ClusterRole** vaut pour tout le cluster.)
- Un **RoleBinding** attribue le Role au ServiceAccount.

Si le jeton de Jenkins fuit, l'attaquant ne peut agir que dans `webapps`, pas sur tout le cluster : c'est encore le **moindre privilège**. Vérifie : `kubectl auth can-i delete nodes --as=system:serviceaccount:webapps:jenkins` → `no`.
:::

Jenkins → *Credentials* → *Secret text*, ID **`k8-cred`**, valeur = le jeton.

**6.3 — Le secret pour tirer l'image privée :**

```bash
kubectl -n webapps create secret docker-registry regcred \
  --docker-server=https://index.docker.io/v1/ \
  --docker-username=<toi-dockerhub> --docker-password=<token-dockerhub>
```

Dans `deployment-service.yml`, l'image doit être `<toi-dockerhub>/blogging-app:IMAGE_TAG` et le pod doit référencer `imagePullSecrets: [{ name: regcred }]`.

**6.4 — Le stage de déploiement :**

```groovy
stage('Déploiement EKS') {
    steps {
        withKubeConfig(credentialsId: 'k8-cred', serverUrl: '<URL-API-EKS>', namespace: 'webapps',
                       clusterName: '<cluster>', caCertificate: '', restrictKubeConfigAccess: false) {
            sh '''
              sed -i "s#IMAGE_TAG#${BUILD_NUMBER}#" deployment-service.yml
              kubectl apply -f deployment-service.yml
              kubectl rollout status deployment/bloggingapp-deployment --timeout=180s
            '''
        }
    }
}
stage('Vérification') {
    steps {
        withKubeConfig(credentialsId: 'k8-cred', serverUrl: '<URL-API-EKS>', namespace: 'webapps', clusterName: '<cluster>') {
            sh 'kubectl get pods,svc -n webapps'
        }
    }
}
```

*(`bloggingapp-deployment` est le nom du Deployment dans `deployment-service.yml`. `caCertificate: ''` désactive la vérification du certificat du serveur : acceptable pour un lab ; en production, fournis le certificat du cluster.)*

**6.5 — L'e-mail** : configure *Extended E-mail Notification* (projet 09, étape 6) et ajoute un bloc `post { always { emailext … } }` avec un corps HTML (statut coloré, numéro de build, lien), et en pièces jointes `fs.html` et `image.html`.

## Étape 8 — Le monitoring de l'application

Sur `monitoring` : installe **Prometheus**, **Grafana** et **Blackbox Exporter** (annexe A.7).

:::why Le Blackbox Exporter
node_exporter mesure **la machine de l'intérieur**. Le **Blackbox Exporter** teste l'application **de l'extérieur**, comme un utilisateur : il envoie une requête HTTP à l'URL et mesure si elle répond (`probe_success`), en combien de temps (`probe_duration_seconds`), avec quel code HTTP, et quand expire le certificat TLS. C'est la base du **monitoring de disponibilité** (*uptime*).
:::

Ajoute dans `prometheus.yml` (configuration standard du Blackbox Exporter, avec réécriture des labels) :

```yaml
  - job_name: blackbox
    metrics_path: /probe
    params:
      module: [http_2xx]                 # module défini dans blackbox.yml : attend un code 2xx
    static_configs:
      - targets:
        - http://blog.<ton-domaine>      # ou http://<DNS-du-load-balancer>
        - https://www.google.com         # une cible témoin
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target     # l'URL à sonder devient le paramètre ?target=
      - source_labels: [__param_target]
        target_label: instance           # et le label "instance" affiché dans Grafana
      - target_label: __address__
        replacement: localhost:9115      # Prometheus interroge en réalité le Blackbox Exporter
```

```bash
promtool check config /etc/prometheus/prometheus.yml && curl -X POST http://localhost:9090/-/reload
```

Grafana → source Prometheus → import du tableau **7587** (*Prometheus Blackbox Exporter*). Tu vois : statut UP/DOWN, temps de réponse, phases de la requête (DNS, connexion, TLS, traitement), code HTTP, expiration du certificat.

:::exo Le test de panne
1. `kubectl scale deploy -n webapps --all --replicas=0` : en moins d'une minute, Grafana passe au rouge.
2. Ajoute une **règle d'alerte** `probe_success == 0` pendant 1 minute (leçon 15) et branche Alertmanager ou une alerte Grafana sur ton e-mail.
3. Remets les replicas : retour au vert. Note le temps de détection dans tes notes : c'est ton **MTTD** (*Mean Time To Detect*).
:::

## Dépannage

:::fix
- **`mvn deploy` : 401** : credentials Nexus non associés aux `serverId` du `settings.xml`, ou `id` du `pom.xml` différent (`maven-releases`/`maven-snapshots`).
- **`mvn deploy` : 400 Repository does not allow updating assets** : *Allow redeploy* non activé, ou tu déploies une version release vers `maven-snapshots` (ou l'inverse).
- **`kubectl` dans Jenkins : `Forbidden`** : le Role ne couvre pas la ressource demandée (lis le message : il nomme la ressource et le verbe), ou mauvais namespace.
- **Pods `ImagePullBackOff`** : `regcred` absent du namespace `webapps` ou non référencé dans le manifest ; image privée.
- **`probe_success` à 0 alors que le site marche** : le monitoring n'atteint pas l'URL (SG, DNS), ou le module attend du 2xx et le site redirige (301) : utilise un module qui suit les redirections.
:::

## Nettoyage

:::clean
1. `kubectl delete -f deployment-service.yml -n webapps` (supprime le load balancer), puis destruction du cluster (Terraform ou eksctl).
2. *Terminate* les 4 instances, supprime le SG et les volumes.
3. Supprime l'enregistrement DNS, révoque les tokens (GitHub, Docker Hub), supprime le dépôt Docker Hub privé si besoin.
:::
