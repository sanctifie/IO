## Ce qu'on construit

Une chaîne complète **entièrement dans l'écosystème Microsoft** : un pipeline Azure DevOps qui crée l'infrastructure avec Terraform (réseau, registre ACR, cluster AKS, Log Analytics), construit l'image d'une application ASP.NET Core, la pousse dans ACR et la déploie dans AKS, puis teste l'infrastructure et la surveille.

```ascii
 Azure Repos ──commit──► Azure Pipelines (azure-pipelines.yml)
                           │ stage validate ─► plan ─► apply   (Terraform, état dans Azure Storage)
                           │                              └─► crée : VNet, ACR, AKS, Log Analytics, App Insights, Key Vault
                           │ stage build   ─► docker build/push ──► ACR (aspnet:<BuildId>)
                           │ stage deploy  ─► kubectl apply ──► AKS ──pull (rôle AcrPull)──► ACR
                           │ stage test    ─► InSpec vérifie que l'infra est conforme
                           ▼
              Application Insights + Container Insights (monitoring)
```

## Azure en 2 minutes (pour qui connaît AWS)

| Azure | AWS | Remarque |
|---|---|---|
| **Abonnement** (*subscription*) | compte AWS | l'unité de facturation |
| **Groupe de ressources** (*resource group*) | — (tags, CloudFormation stack) | **toute** ressource Azure appartient à un groupe ; supprimer le groupe supprime tout ce qu'il contient. Très pratique pour le nettoyage ! |
| **Entra ID** (ex-Azure AD) | IAM Identity Center | annuaire des utilisateurs et groupes |
| **Service principal** / **managed identity** | utilisateur technique / rôle IAM | identité d'une application ou d'un pipeline |
| **RBAC** (rôles *Owner*, *Contributor*, *Reader*, *AcrPull*…) | politiques IAM | attribués sur un **scope** : abonnement, groupe ou ressource |
| VNet, Storage Account, ACR, AKS, Key Vault | VPC, S3, ECR, EKS, Secrets Manager | |

```bash
# Azure CLI (sur ton poste)
curl -sL https://aka.ms/InstallAzureCLIDeb | sudo bash
az login                                  # ouvre le navigateur

az account set --subscription "<nom ou id>"
```

:::warn Les agents hébergés d'Azure DevOps ne sont pas activés d'office
Une nouvelle organisation Azure DevOps n'a **pas** de « parallel job » gratuit sur les agents hébergés par Microsoft : le premier pipeline échoue avec *No hosted parallelism has been purchased or granted*. Deux solutions :
1. Demander la gratuité via le formulaire officiel (`https://aka.ms/azpipelines-parallelism-request`) : réponse en 2 à 3 jours ouvrés. **Fais-le dès le début du projet.**
2. En attendant, utiliser un **agent auto-hébergé** (*self-hosted*) sur ton poste ou une petite VM (le projet 29 le détaille) : *Project settings → Agent pools → Default → New agent*, puis suivre les 3 commandes affichées.
:::

## Lab 1 — Mise en place initiale

**1.1 — Organisation et projet Azure DevOps.** Va sur `https://dev.azure.com` → *New organization* (choisis la région Europe) → *New project* : `devops-journey`, visibilité privée.

**1.2 — Service connection vers Azure.** *Project settings → Service connections → New → Azure Resource Manager* → **Workload Identity federation (automatic)** → abonnement → laisse le groupe de ressources vide (accès à l'abonnement) → nom **`azure-devops-journey-service-connection`** → coche *Grant access permission to all pipelines*.

:::why Workload Identity Federation
Le dépôt d'origine crée un *service principal* avec un **secret** (un mot de passe qui expire et qu'il faut renouveler). La fédération d'identité (OIDC) permet au pipeline d'obtenir un jeton temporaire **sans aucun secret stocké** : c'est aujourd'hui la méthode recommandée, et c'est l'équivalent des rôles IAM pour GitHub Actions sur AWS.
:::

L'identité créée a le rôle *Contributor* sur l'abonnement. Pour que Terraform puisse aussi **attribuer des rôles** (étape AcrPull), elle a besoin du rôle *User Access Administrator* (ou *Role Based Access Control Administrator*) : Portail Azure → *Subscriptions → Access control (IAM) → Add role assignment*.

**1.3 — Stockage de l'état Terraform.** Terraform garde la mémoire de ce qu'il a créé dans un fichier d'**état** (*state*). En équipe ou dans un pipeline, cet état doit être **distant et partagé** : ici, un conteneur Azure Blob Storage.

```bash
RG=devops-journey-rg
SA=devopsjourney$RANDOM          # nom unique, minuscules et chiffres uniquement
az group create -l francecentral -n $RG
az storage account create -n $SA -g $RG -l francecentral --sku Standard_LRS --min-tls-version TLS1_2
az storage container create --name tfstate --account-name $SA --auth-mode login
echo $SA                          # note-le
```

**1.4 — Groupe Entra ID des administrateurs AKS.** Les membres de ce groupe pourront administrer le cluster avec `kubectl`.

```bash
az ad group create --display-name devopsthehardway-aks-group --mail-nickname devopsthehardway-aks-group
az ad group member add --group devopsthehardway-aks-group --member-id $(az ad signed-in-user show --query id -o tsv)
az ad group show --group devopsthehardway-aks-group --query id -o tsv     # note cet ID
```

## Lab 2 — Déployer l'infrastructure avec Terraform via Azure DevOps

**2.1 — Récupérer le code.** Le code des labs du dépôt d'origine date de 2021 (provider `azurerm` v2, syntaxe `addon_profile` supprimée depuis). **Utilise la version maintenue** du même parcours, sur le GitHub de l'auteur : `https://github.com/thomast1906/DevOps-Journey-Using-Azure-DevOps` (dossier `labs/2-AzureDevOps-Terraform-Pipeline/`). Importe-le dans Azure Repos : *Repos → Import repository* → URL du dépôt.

La structure Terraform est **modulaire** :

```text
terraform/
├── providers.tf        # provider azurerm + backend "azurerm" (l'état distant)
├── main.tf             # appelle les modules
├── variables.tf
└── modules/
    ├── vnet/           # réseau + sous-réseaux
    ├── acr/            # Azure Container Registry
    ├── log-analytics/  # espace de travail pour les logs et métriques
    └── aks/            # le cluster Kubernetes
vars/production.tfvars  # les valeurs : noms, région, taille des nœuds, ID du groupe AKS admins…
```

Adapte `vars/production.tfvars` : noms uniques (l'ACR doit avoir un nom unique au monde), région (`francecentral`), **1 nœud** `Standard_B2s` ou `Standard_D2s_v5` pour limiter le coût, ID du groupe Entra (lab 1.4), et **désactive l'Application Gateway** (AGIC) si l'option est présente.

**2.2 — Installer l'extension Terraform** dans l'organisation : *Organization settings → Extensions → Browse marketplace* → **Terraform** (Microsoft DevLabs).

**2.3 — Le pipeline.** Voici la structure (variables à adapter) :

```yaml
trigger: none          # lancement manuel pour l'instant (le lab 5 activera le déclenchement auto)
pr: none

pool:
  vmImage: ubuntu-latest        # agent hébergé ; ou "name: Default" pour un agent auto-hébergé

variables:
  backendServiceArm: 'azure-devops-journey-service-connection'
  backendAzureRmResourceGroupName: 'devops-journey-rg'
  backendAzureRmStorageAccountName: '<ton-storage-account>'
  backendAzureRmContainerName: 'tfstate'
  backendAzureRmKey: 'terraform.tfstate'
  environment: 'production'

stages:
- stage: validate
  jobs:
  - job: validate
    steps:
    - task: TerraformInstaller@1
      inputs: { terraformVersion: 'latest' }
    - task: TerraformTaskV4@4
      displayName: init
      inputs:
        provider: azurerm
        command: init
        workingDirectory: '$(System.DefaultWorkingDirectory)/terraform'
        backendServiceArm: $(backendServiceArm)
        backendAzureRmResourceGroupName: $(backendAzureRmResourceGroupName)
        backendAzureRmStorageAccountName: $(backendAzureRmStorageAccountName)
        backendAzureRmContainerName: $(backendAzureRmContainerName)
        backendAzureRmKey: $(backendAzureRmKey)
    - task: TerraformTaskV4@4
      displayName: validate
      inputs: { provider: azurerm, command: validate, workingDirectory: '$(System.DefaultWorkingDirectory)/terraform' }

- stage: plan
  dependsOn: validate
  jobs:
  - job: plan
    steps:
    - task: TerraformInstaller@1
      inputs: { terraformVersion: 'latest' }
    - task: TerraformTaskV4@4
      displayName: init
      inputs: { provider: azurerm, command: init, workingDirectory: '$(System.DefaultWorkingDirectory)/terraform',
                backendServiceArm: $(backendServiceArm), backendAzureRmResourceGroupName: $(backendAzureRmResourceGroupName),
                backendAzureRmStorageAccountName: $(backendAzureRmStorageAccountName),
                backendAzureRmContainerName: $(backendAzureRmContainerName), backendAzureRmKey: $(backendAzureRmKey) }
    - task: TerraformTaskV4@4
      displayName: plan
      inputs:
        provider: azurerm
        command: plan
        commandOptions: '-input=false -var-file="../vars/$(environment).tfvars"'
        environmentServiceNameAzureRM: $(backendServiceArm)
        workingDirectory: '$(System.DefaultWorkingDirectory)/terraform'

- stage: apply
  dependsOn: plan
  jobs:
  - job: apply
    steps:
    # (mêmes étapes installer + init, puis :)
    - task: TerraformTaskV4@4
      displayName: apply
      inputs:
        provider: azurerm
        command: apply
        commandOptions: '-input=false -auto-approve -var-file="../vars/$(environment).tfvars"'
        environmentServiceNameAzureRM: $(backendServiceArm)
        workingDirectory: '$(System.DefaultWorkingDirectory)/terraform'
```

*Pipelines → New pipeline → Azure Repos Git → ton dépôt → Existing Azure Pipelines YAML file* → choisis le fichier → *Run*.

:::why Trois stages : validate, plan, apply
**validate** vérifie la syntaxe (rapide, échoue tôt). **plan** calcule et affiche ce qui va changer, sans rien toucher. **apply** applique. En production, on insère une **approbation manuelle** entre plan et apply (via un *Environment* Azure DevOps avec un *check* d'approbation) : un humain relit le plan avant que l'infrastructure soit modifiée.
:::

:::check
Dans le portail Azure, tu trouves les groupes de ressources créés, avec le VNet, l'ACR, le cluster AKS et l'espace Log Analytics. Dans le conteneur `tfstate`, le fichier `terraform.tfstate` est apparu.
:::

## Lab 3 — Construire l'application et la pousser dans ACR

1. *Project settings → Service connections → New → Docker Registry → Azure Container Registry* → choisis ton ACR → nom : le nom DNS de l'ACR (ex. `devopsjourneyacr.azurecr.io`).
2. Copie le dossier de l'application `aspnet-core-dotnet-core` (lab 3) dans ton dépôt.
3. Teste-la en local si tu as Docker : `docker build -t devopsjourneyapp . && docker run -p 8080:80 devopsjourneyapp` → `http://localhost:8080`.
4. Ajoute le stage de build au pipeline :

```yaml
variables:
  # ... (variables précédentes)
  repository: 'aspnet'
  dockerfile: '$(Build.SourcesDirectory)/aspnet-core-dotnet-core/Dockerfile'
  containerRegistry: 'devopsjourneyacr.azurecr.io'     # nom de la service connection Docker

- stage: build
  dependsOn: apply
  jobs:
  - job: build
    steps:
    - task: Docker@2
      displayName: Build et push vers ACR
      inputs:
        command: buildAndPush
        repository: $(repository)
        dockerfile: $(dockerfile)
        containerRegistry: $(containerRegistry)
        tags: $(Build.BuildId)
```

Après exécution : portail → ACR → *Repositories* → `aspnet` → un tag par build.

## Lab 4 — Déployer dans AKS

**4.1 — Autoriser AKS à télécharger depuis ACR.** Ajoute au `main.tf` (le nom exact des sorties dépend du module) :

```hcl
resource "azurerm_role_assignment" "aks_acr_pull" {
  scope                = module.acr.acr_id                 # le registre
  role_definition_name = "AcrPull"
  principal_id         = module.aks.kubelet_object_id      # l'identité des nœuds
}
```

:::why Pourquoi l'identité « kubelet »
Ce sont les **nœuds** du cluster (via le *kubelet*, l'agent Kubernetes de chaque nœud) qui téléchargent les images. On donne donc le rôle *AcrPull* (lecture seule) à **leur** identité managée, sur **le** registre : moindre privilège, et aucun mot de passe de registre à gérer (contrairement au `imagePullSecret` JFrog du projet 06).
:::

**4.2 — Application Insights et Key Vault.** Ajoute les modules `appinsights` et `keyvault` (dossier `labs/4-Deploy-App-AKS/terraform/modules` du dépôt maintenu), relance le pipeline, puis range la clé d'Application Insights dans le Key Vault :

```bash
az extension add --name application-insights
AIKEY=$(az monitor app-insights component show --app devopsjourney -g devopsjourney-rg --query instrumentationKey -o tsv)
az keyvault secret set --vault-name "<ton-keyvault>" --name "AIKEY" --value "$AIKEY"
```

Puis dans Azure DevOps : *Pipelines → Library → + Variable group* → `devopsjourney` → **Link secrets from an Azure key vault** → choisis le coffre → ajoute `AIKEY`. Référence le groupe dans le pipeline (`variables: - group: devopsjourney`).

:::why Le variable group lié à Key Vault
Le secret ne vit **que** dans Key Vault. Le pipeline le lit au moment de l'exécution ; il est masqué dans les logs (`***`). Si on change la valeur dans Key Vault, tous les pipelines utilisent la nouvelle automatiquement. C'est le même principe que les Credentials Jenkins ou les Secrets GitHub, mais centralisé.
:::

**4.3 — Le manifest de l'application** (`pipelines/scripts/aspnet.yaml`), corrigé pour les versions actuelles de Kubernetes :

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: aspnetcore
spec:
  replicas: 1
  selector:
    matchLabels: { app: aspnetcore }
  template:
    metadata:
      labels: { app: aspnetcore }
    spec:
      containers:
      - name: aspnetcore
        image: devopsjourneyacr.azurecr.io/aspnet:IMAGE_TAG     # remplacé par le pipeline
        ports: [{ containerPort: 80 }]
        resources:
          requests: { cpu: 100m, memory: 128Mi }
          limits:   { cpu: 250m, memory: 256Mi }
        env:
        - name: APPINSIGHTS_INSTRUMENTATIONKEY
          valueFrom: { secretKeyRef: { name: aikey, key: aisecret } }
---
apiVersion: v1
kind: Service
metadata:
  name: aspnetcore
spec:
  type: LoadBalancer        # Azure crée une IP publique
  ports: [{ port: 80 }]
  selector: { app: aspnetcore }
```

:::warn L'Ingress du dépôt d'origine ne fonctionne plus
Le fichier d'origine déclare un `Ingress` en `apiVersion: extensions/v1beta1`, **supprimée depuis Kubernetes 1.22**, et dépend de l'Application Gateway (coûteuse). On s'en passe : le `Service` de type `LoadBalancer` suffit pour exposer l'application. *(Si tu veux un Ingress : `apiVersion: networking.k8s.io/v1` et l'add-on **Application Routing** d'AKS, basé sur NGINX.)*
:::

**4.4 — Le stage de déploiement :**

```yaml
- stage: deploy
  dependsOn: build
  jobs:
  - job: deploy
    steps:
    - task: AzureCLI@2
      displayName: Déployer sur AKS
      inputs:
        azureSubscription: $(backendServiceArm)
        scriptType: bash
        scriptLocation: inlineScript
        inlineScript: |
          set -e
          az aks get-credentials -g devopsjourneyaks-rg -n devopsjourneyaks --admin
          kubectl create secret generic aikey --from-literal=aisecret="$(AIKEY)" \
            --dry-run=client -o yaml | kubectl apply -f -
          sed -i "s/IMAGE_TAG/$(Build.BuildId)/" pipelines/scripts/aspnet.yaml
          kubectl apply -f pipelines/scripts/aspnet.yaml
          kubectl rollout status deployment/aspnetcore --timeout=180s
```

:::tip `--dry-run=client -o yaml | kubectl apply -f -`
`kubectl create secret` échoue si le secret existe déjà (deuxième exécution du pipeline). Cette astuce génère le YAML du secret puis l'**applique**, ce qui crée **ou** met à jour : la commande devient rejouable. Même philosophie que `docker rm -f … || true` au projet 05.
:::

:::check
`kubectl get svc aspnetcore` affiche une `EXTERNAL-IP` après une à deux minutes : ouvre-la dans le navigateur. `kubectl describe pod -l app=aspnetcore | grep Image` montre le tag du dernier build.
:::

## Lab 5 — Le vrai CI/CD : déclenchement automatique

Remplace `trigger: none` par :

```yaml
trigger:
  batch: true            # si plusieurs commits arrivent pendant un run, un seul run suivant les regroupe
  branches:
    include: [ main ]
```

Modifie la page d'accueil de l'application (`Views/Home/Index.cshtml` ou équivalent), commit sur `main` : le pipeline démarre seul, construit une nouvelle image et la déploie. **C'est le cœur du DevOps : un commit = une mise en production contrôlée.**

## Lab 6 — Tester l'infrastructure avec InSpec

**InSpec** (Chef/Progress) permet d'écrire des **tests** sur l'infrastructure réelle : « ce Key Vault existe », « ce cluster AKS a bien 1 nœud », « ce groupe de ressources est en France Central ».

```ruby
# azure-inspec-tests/controls/azure_aks.rb
control 'aks-cluster' do
  describe azure_aks_cluster(resource_group: 'devopsjourneyaks-rg', name: 'devopsjourneyaks') do
    it { should exist }
    its('properties.provisioningState') { should cmp 'Succeeded' }
  end
end
```

Le dossier `labs/6-Testing-Infrastructure` fournit le profil et le stage de pipeline (qui lit les identifiants nécessaires dans Key Vault). Exécute-le, puis consulte l'onglet *Tests* du run Azure DevOps.

:::why Tester l'infrastructure
On teste le code applicatif ; pourquoi pas l'infrastructure ? Ces tests détectent les écarts (*drift*) entre ce qui est voulu et ce qui existe, et servent de documentation exécutable. Alternatives modernes : **Terratest** (Go), `terraform test` (intégré à Terraform depuis la 1.6), **Checkov** (analyse statique de sécurité).
:::

## Lab 7 — Monitoring et alertes

Dans le portail Azure :

- **Application Insights** (ressource `devopsjourney`) : *Live Metrics* (requêtes en temps réel), *Failures*, *Application map*, *Transaction search*.
- **Availability test** : *Availability → Add Standard test* → l'URL publique de l'application, testée toutes les 5 minutes depuis plusieurs régions, avec alerte si elle ne répond plus.
- **Container Insights** : cluster AKS → *Insights* → CPU/mémoire par nœud, par pod, logs des conteneurs (requêtes KQL dans Log Analytics).

```kusto
// Log Analytics : les 50 dernières lignes de log de l'application
ContainerLogV2
| where PodName startswith "aspnetcore"
| project TimeGenerated, LogMessage
| order by TimeGenerated desc
| take 50
```

## Dépannage

:::fix
- **`No hosted parallelism has been purchased or granted`** : voir l'encadré en début de projet.
- **`AuthorizationFailed` sur `Microsoft.Authorization/roleAssignments/write`** : l'identité de la service connection n'a pas le droit d'attribuer des rôles (étape 1.2).
- **Terraform : `Error acquiring the state lock`** : un run précédent a été interrompu. Dans le portail, sur le blob `terraform.tfstate`, *Break lease*. Ne le fais que si aucun autre run n'est en cours.
- **Nom d'ACR ou de storage déjà pris** : ils doivent être uniques au monde ; ajoute un suffixe.
- **Pod en `ImagePullBackOff`** : le rôle `AcrPull` n'est pas attribué (ou pas encore propagé : attends quelques minutes).
- **Quota de vCPU dépassé** : les abonnements d'essai ont des quotas faibles ; choisis une taille de VM plus petite ou une autre région.
:::

## Nettoyage

:::clean
1. Le plus simple : supprimer les **groupes de ressources** créés par Terraform (AKS, ACR, VNet, Log Analytics…). Le groupe `…-node-rg` (ou `MC_…`) des nœuds AKS est supprimé avec le cluster.
   ```bash
   az group list -o table
   az group delete -n <groupe> --yes --no-wait
   ```
   *(Ou mieux : ajoute un pipeline `terraform destroy`.)*
2. Supprime en dernier `devops-journey-rg` (le stockage de l'état).
3. Supprime le groupe Entra `devopsthehardway-aks-group` si tu ne le réutilises pas.
4. Vérifie *Cost Management* le lendemain.
:::
