## Ce qu'on construit

Le **même** pipeline que le projet 09, appliqué à une autre application : un clone de Zomato (le « Deliveroo » indien). L'objectif pédagogique est différent : **tu le fais seul**, à partir de tes notes du projet 09, puis tu **l'améliores** sur trois points que le tutoriel d'origine laisse de côté.

```ascii
 GitHub (fork Zomato-Clone) ──► Jenkins
     clean → checkout → SonarQube → Quality Gate (BLOQUANTE) → npm install
     → OWASP Dependency-Check → Trivy fs (BLOQUANT sur CRITICAL)
     → docker build (image durcie, multi-stage) → push Docker Hub → Trivy image
     → docker run -p 3000:… → e-mail
```

:::exo La règle du jeu
Ouvre ton `NOTES.md` du projet 09 et refais l'installation **sans** relire le projet 09 (sauf en cas de blocage). Note le temps passé : la deuxième fois doit être deux fois plus rapide. C'est exactement ce qu'on attend d'un ingénieur : capitaliser.
:::

## Étape 1 — L'infrastructure et les outils

Reprends les étapes 1, 2 et 7 du projet 09 : instance `t3.large`, Jenkins, Docker (groupe `docker` pour `jenkins`), SonarQube en conteneur, Trivy, plugins, outils (`jdk17`, `node16` ou `node20`, `sonar-scanner`, `DP-Check`, `docker`), credentials (`Sonar-token`, `docker`, `nvd-api-key`, e-mail).

Le Security Group doit ouvrir le port de l'application (**3000** dans le tutoriel, ou 8081 avec le Dockerfile durci ci-dessous).

## Étape 2 — Amélioration n°1 : un Dockerfile de production

Le Dockerfile d'origine utilise `node:16-slim`, installe toutes les dépendances, construit l'application… puis la lance avec **`npm start`**, c'est-à-dire le **serveur de développement** de Create React App. Résultat : une image lourde (~1 Go), un serveur non prévu pour la production, et toutes les dépendances de développement (avec leurs failles) embarquées.

Remplace-le par un build **multi-stage** servi par Nginx, avec un utilisateur non-root :

```dockerfile
# Étape 1 : construire les fichiers statiques
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build                     # produit /app/build

# Étape 2 : les servir avec Nginx, sans Node ni sources
FROM nginxinc/nginx-unprivileged:stable-alpine
COPY --from=build /app/build /usr/share/nginx/html
EXPOSE 8080                           # l'image "unprivileged" écoute sur 8080, utilisateur non-root
```

:::check Compare
```bash
docker images | grep zomato
trivy image <ancienne-image> | grep Total
trivy image <nouvelle-image> | grep Total
```
Note dans ton `NOTES.md` la taille et le nombre de vulnérabilités **avant/après**. La différence est en général spectaculaire (taille divisée par 20, vulnérabilités divisées par 10 ou plus). C'est un excellent argument d'entretien.
:::

:::warn `npm ci` et Node 20 sur un vieux projet
`npm ci` exige un `package-lock.json` cohérent avec `package.json`. Si le build échoue avec des erreurs OpenSSL (`ERR_OSSL_EVP_UNSUPPORTED`) typiques des vieux projets Create React App sur Node ≥ 17, ajoute `ENV NODE_OPTIONS=--openssl-legacy-provider` dans l'étape de build, ou reste sur `node:16-alpine` pour cette étape.
:::

## Étape 3 — Amélioration n°2 : des contrôles qui bloquent

```groovy
stage('Quality Gate') {
    steps {
        timeout(time: 5, unit: 'MINUTES') {
            waitForQualityGate abortPipeline: true, credentialsId: 'Sonar-token'
        }
    }
}
stage('Trivy FS') {
    steps {
        sh 'trivy fs --format table -o trivyfs.txt .'
        sh 'trivy fs --severity CRITICAL --exit-code 1 --ignore-unfixed .'    // échoue s'il reste du CRITICAL corrigeable
    }
}
stage('Trivy image') {
    steps {
        sh 'trivy image --format table -o trivyimage.txt $IMAGE:$BUILD_NUMBER'
        sh 'trivy image --severity CRITICAL --exit-code 1 --ignore-unfixed $IMAGE:$BUILD_NUMBER'
    }
}
```

:::why `--ignore-unfixed`
Certaines CVE n'ont **pas encore de correctif**. Bloquer le pipeline pour elles empêcherait toute livraison sans que tu puisses rien y faire. `--ignore-unfixed` ne retient que les failles **corrigeables** : tu peux agir (mettre à jour la dépendance ou l'image de base). Pour les autres, on documente une exception dans un fichier `.trivyignore`, avec une date de revue.
:::

Quand le pipeline échoue sur une faille, **corrige-la** (mise à jour de la dépendance avec `npm audit fix` ou `npm install <paquet>@<version>`, ou de l'image de base), commit, relance. C'est le vrai travail DevSecOps.

## Étape 4 — Amélioration n°3 : la détection de secrets

Ajoute un stage **gitleaks** juste après le checkout :

```groovy
stage('Secrets (gitleaks)') {
    steps {
        sh 'docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest detect --source /repo --no-git -v'
    }
}
```

Teste-le : ajoute dans un fichier une fausse clé AWS (`AKIAIOSFODNN7EXAMPLE` + une chaîne de 40 caractères) sur une branche, pousse, observe l'échec, puis supprime-la.

## Étape 5 — Déploiement et vérification

```groovy
stage('Déployer') {
    steps {
        sh '''
          docker rm -f zomato || true
          docker run -d --name zomato -p 3000:8080 $IMAGE:$BUILD_NUMBER
        '''
    }
}
```

:::check
- `http://<IP>:3000` affiche le clone de Zomato.
- Un pipeline volontairement « cassé » (fausse clé, dépendance vulnérable, code qui fait échouer la Quality Gate) **s'arrête** avant le déploiement.
- Ton `NOTES.md` contient le comparatif avant/après du Dockerfile.
:::
